> **状态**：现行　｜　日期：2026-10-07　｜　索引：[docs/README.md](../README.md) §1

> 三次复跑稳定，不是噪声」，并据此断言「M3 若什么都不改，等于把 27% 的开销继续留在外壳里」。

## 1. 裁决一：性能数字复核——「27%」是 3.4%

[S4 §2.3](S4-实施规格与落地顺序.md) 留了一条待测项：「1 KB 输入下，建表开销占总时长的百分比」。
上一条评论给出了一个数：**≈ 27%**，并据此把「M3 什么都不改」判为「收益为零」。

本次用同口径复跑（`wasm-gc` + `--release`，`@bench.monotonic_clock_start/end`，
3000 次循环取中位数，12 轮取样），拿到的是另一组数：

| # | 测的对象 | 中位数 | 备注 |
|:-:|---------|-------:|------|
| A | `Engine::new(standard, default)` 并**观察表内容** | 360 ns | 防 DCE：返回 `decode_table[65] + encode_table[0]` |
| B | 顶层 `let` 常量引擎并观察 | 17 ns | 取值的成本，不含建表 |
| C | 外壳 `encode(b"")` | 311 ns | 空输入 |
| D | 外壳 `encode(b"abc")` | 356 ns | 3 字节 |
| E | 外壳 `encode(1024 字节)` | 10 483 ns | |
| F | 外壳内部的 `engine()` + 观察 | 235 ns | 即「外壳建一次引擎」这一层 |
| G | 持常量引擎 + 内核 `encode_into(1024B)` | 3 294 ns | 无表建 |
| H | 每次新建引擎 + 内核 `encode_into(1024B)` | 3 429 ns | 有表建 |

**建表占比（按外壳整链路算）**：

```
0 B     : F / C = 235 / 311   = 75.5%
3 B     : F / D = 235 / 356   = 66.0%
1024 B  : F / E = 235 / 10483 =  2.2%
```

**「27%」差在哪**：它大概率是把「只建引擎」的绝对耗时（`A`）当分子、
把「建引擎 + 内核编码但**没算物化**」当分母算出来的。对照 `G/H` 两行——
建表在内核编码环节里确实占 `(3429-3294)/3429 = 3.9%`，
所以无论怎么算，**都不该出现 27%**。本文把它记为**不可复现的数字**，按 S5 §2.1 的纪律替换为实测值。

> **教训与 [S5 §2.1](S5-实施裁决与M1落地.md) 同一条**：量一个「占比」时，
> 分子与分母必须是**同一层**的成本——「只建表」的耗时除以「建表但不物化」的耗时，
> 得到的不是「建表占一次调用的比例」。

## 2. 裁决二：M3 的收益上界是 6%，不是「一次调用的一大块」

既然占比只有 2~3%（大输入）/ 66%（小输入），那么「把表缓存起来」能省多少？

| 输入 | 外壳当前耗时 | 换成顶层常量引擎的理论下界 | 收益上界 |
|------|-------------:|---------------------------:|---------:|
| 0 B | 311 ns | 311 − 235 + 17 = 93 ns | **70%**（但绝对值只有 218 ns） |
| 3 B | 356 ns | 356 − 235 + 17 = 138 ns | **61%**（绝对值 218 ns） |
| 1024 B | 10 483 ns | 10 483 − 235 + 17 = 10 265 ns | **2.1%** |

**但上表是「理论下界」，不是「可实现的收益」**——因为外壳里那次 `engine()`
已经把建表**与后续编码流水线重叠掉了**。同内核对照（`G` vs `H`，两者都只做编码不做物化）
给出的真实收益是 **3.9%**，且 `G` 与 `H` 的 min/max 区间互相包含，**在噪声内**。

> **这条推翻的是「M3 是纯赚的结构改动」这个隐含假设**：
> `Engine` 对象**已经在了**（M1 随 `decode_into` 一起落的，见 [S3 §2.3](S3-架构分层与子包职责.md)），
> 剩下的只是「外壳每次调用新建 vs 持一个常量」。
> 而后者**有真实的代码代价**：`Engine` 是含 `FixedArray` 的**引用语义**值，
> 一旦提到顶层就变成**模块级共享可变对象**——M2 起 `url_safe()` 已经有
> 「必须 `copy()` 再改」（[S5 §6.1](S5-实施裁决与M1落地.md)）的教训在前。

### 2.1 技术可行性：顶层 `let` 常量确实是「构造期一次」

上一版把这条列为「待实测项」。本次实测**成立**，且**不引入可变状态**：

```
顶层 `let e : Engine = Engine::new(standard(), Config::default())`
  · 建表只发生一次（后续取值 17 ns，不再付 360 ns）
  · 两个不同 test 用例里取到的是同一份内容（`table[65] == 0`、`symbols[62] == 43`）
  · 未观察到跨用例状态串扰
```

复跑见 [§6](#6-复跑方式)。**但「能做」不等于「该做」**——见 §2 的收益结论。

### 2.2 裁决

| 方案 | 收益（实测） | 代价 | 裁决 |
|------|-------------|------|------|
| **A. 维持现状**：外壳每调用一次 `Engine::new` | 0（基准） | 无 | ✅ **保留** |
| A′. 顶层 `let` 常量引擎 | 0 B/3 B 约 220 ns；1 KB **3.9%（噪声内）** | 模块级共享对象；为「纯函数外壳」引入一处例外 | ⏸ **不做**，理由见 §2.3 |
| B. 全局可变缓存（惰性单例） | 同 A′ | 动摇「测试不依赖执行顺序」铁律 | ❌ 不做 |

### 2.3 为什么 A′ 也不做（这是本文与上一版最大的分歧）

上一版主张「M3 若只补白盒测试、什么都不改，等于验收通过但收益为零」，因此要落 A′。
本文裁决**不做 A′**，三条理由：

1. **收益在噪声内**。1 KB 输入的实测收益 3.9%，`G`/`H` 的 min/max 区间互相包含。
   S4 §6.2 自己的判据写的是「性能不倒退……**不得比 M2 慢到噪声之外（说清是噪声）**」——
   按这条，A′ 的收益**说清是噪声之后就没有了**。为一个噪声级收益换一条纪律例外，不划算。
2. **小输入的绝对值不值得**。0 B/3 B 省下的 218 ns 是**每次调用**的常数项；
   但用到 base64 的场合（HTTP 头、JSON 字段、配置文件）单次调用的成本
   远不在 218 ns 这个量级上被感知。真正需要吞吐的调用方本来就该用 `encode_slice`
   自己持缓冲（M4 之后还有批量内核）。
3. **A′ 会把「纯函数外壳」变成「半纯函数」**。`Engine` 含 `FixedArray`，
   顶层 `let` 意味着全模块共享同一份表。今天它是只读的，但「只读」是**约定**而非**类型保证**
   ——`FixedArray` 是引用语义，任何一次「顺手改一下」都会污染全模块
   （这正是 `Alphabet::url_safe()` 踩过的坑）。**用一个纪律约定换 3.9% 的噪声收益，不值。**

> **因此 M3 的正确形态 = 「补上白盒判据」+「把这条实测结论写进口径」，不改实现。**
> 这不是「收益为零所以跳过」，是「**收益已被实测证伪，所以不做**」——
> 两者在文档上必须写清楚，否则下一轮又会有人重开这条。

## 3. 裁决三：正确性全量对拍——738 例，0 处不符

[S5 §2.3](S5-实施裁决与M1落地.md) 做过 crate 对拍（165 例）。本次独立做一遍，
**换一个参照物**：用 Python 手写判据复刻（不调 stdlib 的 `b64decode`，
而是按 RFC 4648 §3.5 的判据顺序自己实现），与 MoonBit 侧逐行比对。

**输入集**（738 例，与 S5 的 165 例不重叠、更密）：
- 基础串 `"Zm9vYgA0"` 的**所有前缀**（长度 0..=8）；
- 每个前缀 + 1 个特殊字节（9 种：`=` `_` `-` `!` `\n` `\x00` 空格 `+` `/`）；
- 长度 0..=7 的前缀 + 2 个特殊字节的两两组合（9 × 9）。

**比对口径**：变体名 + 所有字段值（`offset` / `byte` / 解码出的字节序列）全等。

```
keys=738  mismatches=0
```

> **对拍比的是「错误对象」，不是「有没有报错」**：offset 差一位、
> `InvalidPadding` 与 `InvalidByte` 混同、或成功时的字节序列差一个字节，都会立刻现形。

**顺带核了 [S5 §1.2](S5-实施裁决与M1落地.md) 那张 7 行的缓冲敏感性表**，逐格复跑一致：

| 输入 | `out[1]` | `out[2]` | `out[3]` |
|------|:--------:|:--------:|:--------:|
| `"Zm9v"` | `OutputSliceTooSmall` | `OutputSliceTooSmall` | `Ok(3)` |
| `"=Zm9v"` | `OutputSliceTooSmall` | `OutputSliceTooSmall` | `InvalidByte(0, b'=')` |
| `"Zm9vYg==="` | `OutputSliceTooSmall` | `OutputSliceTooSmall` | `OutputSliceTooSmall`（`out[16]` 才到 `InvalidByte(6, b'=')`） |
| `"Zm9v!"` | `InvalidByte(4, b'!')` | 同 | 同 |
| `"Z"` | `InvalidLength(1)` | 同 | 同 |
| `"Zh=="` | `InvalidLastSymbol(1, b'h')` | 同 | 同 |

**另外补测了三类 S5 没覆盖的容量语义**，全部正确：

1. `decode_slice` 缓冲**大于**实际需要时，绝不会越界写（`out[0..100]` 逐档试过）；
2. `encode_slice` 的 `need` 算式：长度 0..=12 × `padding ∈ {true,false}` 全扫，
   「恰好够」恒 `Ok`、「差一字节」恒 `Err`；
3. `decode_slice` 与 `decode` 的**成功/失败一致性**：29 组输入 × 缓冲 0..=8 全扫，
   无「slice 成功但 decode 失败」或「缓冲够却报 TooSmall」的错配。

### 3.1 本轮未发现的 bug，与一个方法论改进

738 例 + 容量语义全扫**没有抓到实现 bug**——M1 的四判据与错误优先级是稳的。
但**上一版评论里的性能数字（27%）没能复现**，这说明：
**对拍要有参照物，性能要有对照层。** 前者本次做到了（独立 Python 复刻），
后者上一版没做到（分子分母不同层）。

## 4. 裁决四：过期口径清账（7 处）

M1/M2 落地后，四篇规格里有 7 处「现状描述」没跟上。**这些不是笔误，是会误导动手的错**：

| # | 位置 | 过期写法 | 实测 |
|:-:|------|---------|------|
| 1 | [S1 §3.1](S1-rust-base64-移植可行性分析.md) 尾注 | 「`decode` 只有遇 `=` 即停 + 非法字符报错，**4 条判据一条都没有**」 | 四判据已落（M1），逐格反例在 `lib/base64_test.mbt` |
| 2 | [S1 §3.3](S1-rust-base64-移植可行性分析.md) 尾注 | 「`encode_table()` / `decode_table()` 每次调用都新建」 | 表已收进 `Engine`（`lib/internal/tables.mbt` + `engine.mbt`）；**外壳**每调用建引擎，占比见 §1 |
| 3 | [S2 §1](S2-现状基线与迁移缺口.md) | 「`lib/facade.mbt` 共 **156 行**，对外 **6 个符号**」 | **425 行 / 26 个 `pub`**（`moon info` 为准） |
| 4 | [S2 §1](S2-现状基线与迁移缺口.md) 表 | `decode(text, alphabet?) -> Result[Bytes, String]`、`encode(...)` 「⚠️ 部分」 | 均已换签名（M0）+ 补开关（M2）：`decode(BytesView, ...) -> Result[Bytes, DecodeError]` |
| 5 | [S2 §2.3](S2-现状基线与迁移缺口.md) 尾注 | 「`encode` **无法**产出无 padding 输出」 | `padding=false` 已落（M2）且有用例 |
| 6 | [S2 §5](S2-现状基线与迁移缺口.md) 三条复跑行 | 「判据 2/3/4 **现状**：`decode("Z")` = `Ok(b"")`……**先看它红**」 | 四条**全部已 `is_err() == true`**。「先看它红」做不到——它本来就绿 |
| 7 | [S4 §9.2](S4-实施规格与落地顺序.md) 同三条 | 同上 | 同上 |

**逐条实测（第 6/7 条）**：

```
decode("Z").is_err()          = true
decode("Zh==").is_err()       = true
decode("ZhA").is_err()        = true
decode("Zm9vYg===").is_err()  = true
```

即：这三条复跑行**既不是「现状」也不「能红」**——它们唯一的作用是让读者以为
「判据还没落」，从而重做一遍 M1。**按 S5 §2.1 那条教训的推广**：
更正一处口径后，要回头扫所有**依赖它的复跑行**，不能只改结论表。

> **另一层错**：这三行写的是 `@lib.decode("Z")`——`String` 字面量。
> M0 改成 `BytesView` 后它仍能编译（靠 deprecated 的字面量重载），
> 这正是它没被发现的原因：**门禁绿 ≠ 复跑行可复跑**。
> 处置见 [§5](#5-处置按本文口径改什么)。

### 5.1 为什么「补白盒判据」仍要做

即使实现不改，M3 承诺的验收里有一条是**此前完全没有测试**的
（`grep Engine lib/*_wbtest.mbt` → 空）：**表的内容与不变量**。
它不是「为改实现而写」，而是**回归护栏**：

- `decode_table` 对非法字节恒 `-1`、**padding 也必须是 `-1`**（否则 `=Zm9v` 变合法）；
- 标准表 `symbols[62] == '+'`、`symbols[63] == '/'`；URL-safe 表为 `'-'` / `'_'`；
- **「URL-safe 表是标准表的副本」**：改 URL-safe 表不得污染标准表
  （这正是 [S5 §6.1](S5-实施裁决与M1落地.md) 抓过的那个梗：`symbols[62]` vs `symbols[b'+']`）；
- `Engine::new` 两次得到的内容逐项相同。

**先证明它能红**：把 `Alphabet::url_safe()` 的 `symbols[62]` 退回 `symbols[b'+'.to_int()]`，
白盒用例必须抓住——这条复现 S5 §6.1 的原始 bug。

## 6. 复跑方式

统一前置：`export PATH="$HOME/.moon/bin:$PATH"`；后端 `wasm-gc`；`--release`。

### 6.1 性能（§1 / §2 的全部数字）

```bash
# 探针写在 lib/ 下的 *_test.mbt（黑盒；放 lib/internal 会看不见 @lib）
# 用 @bench.monotonic_clock_start / @bench.monotonic_clock_end（返回**微秒 Double**）
# 每个测点 3000~20000 次循环，取**多次运行的中位数**（单次无意义）
moon test --target wasm-gc --release

# 关键：拿「绝对耗时」对比时，必须让返回值被观察到（累加进 acc 后打印），
# 否则编译器会把整段删掉，得到假数字（实测差 2 倍以上）。
```

测点定义（照 §1 表）：`A`=`Engine::new` 并观察表；`B`=顶层常量取值并观察；
`C/D/E`=外壳 `encode` 空 / 3B / 1024B 并观察长度；`F`=外壳 `engine()` 并观察；
`G`=常量引擎 + 内核 `encode_into(1024B)`；`H`=新建引擎 + 内核 `encode_into(1024B)`。

### 6.2 正确性（§3 的 738 例）

```bash
# MoonBit 侧：对 738 个输入打印「键|判定」，判定串由 @lib.describe 产出
moon test --target wasm-gc --release | grep -E '^[PST][0-9]' | sort > /tmp/moon_verdicts.txt
# Python 侧：按 RFC 4648 §3.5 判据顺序**手写复刻**（不用 stdlib b64decode 当 oracle）
python3 scripts/…                                    # 见 S5 §2.3 的对拍方法
# 比对：变体名 + 全部字段；两侧键集合必须相等
diff <(sort /tmp/moon_verdicts.txt) <(sort /tmp/py_verdicts.txt)
```

> **两个坑（本次都踩过）**：
> 1. Python 侧复刻**必须把「完整 4 元组」那一相位的输出也拼进结果**，
>    只解后缀会得到「少 3 字节」的假不符（本次前 4 轮 diff 全是这个）；
> 2. 两侧的行序不同，比对前**必须各自排序**，直接 `diff` 会得到几千行噪声。
