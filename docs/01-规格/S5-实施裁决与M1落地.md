## 1. 裁决一：解码错误优先级 —— S4 §4.2 把 `decode_slice` 写反了

### 1.1 S4 的写法与实测的差别

S4 §4.2 的「判据间的次序」列了四条，其中第 2 条写「padding 出现在当前 4 元组的位置 0/1 →
`InvalidByte(该位置, padding)`」。**这条本身对，但它没区分 `decode` 与 `decode_slice`。**

`decode_slice` 多一个「输出缓冲够不够」的轴，而这条轴的**位置**在 crate 里是固定的：

```
crate `decode_helper` 的执行次序（照抄，逐条实测）
  ① complete_quads_len:
       a. 若 rem == 1，检查末字节：非法且非 padding → InvalidByte(len-1, byte)   ← 便利检查
       b. 算 input_complete_nonterminal_quads_len（跳过末组）
       c. 若 output.len() < quads/4*3 → OutputSliceTooSmall                      ← 缓冲检查
  ② decode_complete_quads: 逐组解码，非法字节 → InvalidByte(绝对下标)
  ③ decode_suffix: 判据 2 / 3 / 4（含「位置 0/1 的 padding」）
```

即：**rem==1 的便利检查与缓冲检查同在 ①，而在 ② 的逐组解码之前**；
**「位置 0/1 的 padding」在 ③，那是最靠后的一步**。

### 1.2 实测对照（crate 0.23.1，本机探针）

同一个输入，只改输出缓冲大小：

| 输入 | `out[1]` | `out[2]` | `out[3]` | 判据落点 |
|------|:--------:|:--------:|:--------:|---------|
| `"Zm9v"` | `OutputSliceTooSmall` | `OutputSliceTooSmall` | `Ok(3)` | ①c |
| `"=Zm9v"` | `OutputSliceTooSmall` | `OutputSliceTooSmall` | `InvalidByte(0, b'=')` | ①c → ② |
| `"Zm9vYg==="` | `OutputSliceTooSmall` | `OutputSliceTooSmall` | `OutputSliceTooSmall` | ①c |
| `"Zm9vYg==="`（`out[16]`） | — | — | `InvalidByte(6, b'=')` | ② |
| `"Zm9v!"` | `InvalidByte(4, b'!')` | 同 | 同 | ②（**先于** ①c） |
| `"Z"` | `InvalidLength(1)` | 同 | 同 | ①a（**先于** ①c） |
| `"Zh=="` | `InvalidLastSymbol(1, b'h')` | 同 | 同 | ③ |

**两条最容易写错的**：

1. **`"Zm9v!"` 与 `"Z"` 不看缓冲**——它们的判据在缓冲检查之前，所以多小的缓冲都报同一条错。
2. **`"=Zm9v"` 要看缓冲**——它的判据（位置 0 的 padding）在最后一步，而 `Zm9v` 这一组
   必须先被解码。`Zm9v` 要 3 字节，故 `out[3]` 才轮到 padding 判据。**差的那 1 字节不是 padding 的，是数据组的。**

> **照 S4 会怎样**：S4 没写这条轴的位置，实现者很容易把「位置 0/1 的 padding 检查」
> 提到缓冲检查之前（它读起来像「输入校验」，很自然前置）。于是 `decode_slice("=Zm9v", 2 字节)`
> 会报 `InvalidByte(0, b'=')` 而 crate 报 `OutputSliceTooSmall`——
> **一个只在「缓冲恰好不够」时才现形的分道**，测试很容易漏。

### 1.3 本库的落点

`lib/internal/decode.mbt` 的 `decode_into` 严格按 ①→②→③ 排布，且写明「这条不能挪」的理由。
用例 `decode_slice_distinguishes_input_from_capacity` 逐格覆盖上表。

## 2. 裁决二：S4 §4.3 那两格的真值 —— 都不是 S4 猜的值

S4 §4.3 把两格标为「**必须实测 crate 才能写死**」，理由是「padding 跨到了前一个 4 元组，走的是另一条分支」。
实测结论：**理由对，猜测错**。

| 输入 | S4 猜的 M1 目标 | crate 0.23.1 实测 |
|------|----------------|------------------|
| `"Zm9vYg==="` | `Err(InvalidByte(4, b'Y'))` | **`Err(InvalidByte(6, b'='))`** |
| `"Zm9vYmFy=="` | `Err(InvalidByte(4, b'Y'))` | **`Err(InvalidByte(8, b'='))`** |

S4 的理由是「padding 出现在位置 0/1 → 报 `InvalidByte(该位置, padding)`」——
但这两条的 **padding 都从末尾延伸进了前一个 4 元组**，触发的其实是另一条分支：

> **padding 之后又出现非 padding 字节 → 报第一个 padding 的位置**（crate `decode_suffix.rs:73-79`）

`"Zm9vYg==="` 的框法是 `Zm9v` / `Yg==` / `=`（rem = 3）：尾巴是 `Yg==` 之后还剩一个 `=`，
但它前面的 `==` 已经开始了 padding 段，于是报**第一个** `=`，即下标 6。`"Zm9vYmFy=="` 同理，`=` 从下标 8 开始。

而 S4 猜的 `InvalidByte(4, b'Y')` 是把「位置 0/1 的 padding」与「padding 后出现非 padding」
这两条混了——前者报的是 **padding 字节**，后者报的**也**是 padding 字节（不是 `Y`）。
两条分支的共同点是「报 padding 自己的坐标」，而不是「报紧邻的那个符号」。

### 2.1 S4 §4.3 的 12 格逐格实测（**全部本机复跑**）

| 输入 | S4 写的 M1 目标 | crate 实测（= 本库实现后） | 差异 |
|------|----------------|--------------------------|:----:|
| `""` | `Ok(b"")` | `Ok(b"")` | |
| `"Zg=="` | `Ok(b"f")` | `Ok(b"f")` | |
| `"Zg"` | `Ok(b"f")`（Indifferent 下） | **`Err(InvalidPadding)`** | **改** |
| `"Z"` | `Err(InvalidLength(1))` | `Err(InvalidLength(1))` | |
| `"Zh=="` | `Err(InvalidLastSymbol(1, b'h'))` | `Err(InvalidLastSymbol(1, b'h'))` | |
| `"ZhA"` | `Err(InvalidLastSymbol(1, b'h'))` | **`Err(InvalidPadding)`** | **改** |
| `"Zm9vYmFy="` | `Err(InvalidByte(8, b'='))` | `Err(InvalidByte(8, b'='))` | |
| `"Zm9vYg==="` | `Err(InvalidByte(4, b'Y'))` | **`Err(InvalidByte(6, b'='))`** | **改** |
| `"=Zm9v"` | `Err(InvalidByte(0, b'='))` | `Err(InvalidByte(0, b'='))` | |
| `"Zm9v!"` | `Err(InvalidByte(4, b'!'))` | `Err(InvalidByte(4, b'!'))` | |
| `"Zm9vYmFy\n"` | `Err(InvalidByte(8, 0x0A))` | `Err(InvalidByte(8, 0x0A))` | |
| `"Zm9vYmFy=="` | `Err(InvalidByte(4, b'Y'))` | **`Err(InvalidByte(8, b'='))`** | **改** |

**`"Zg"` 与 `"ZhA"` 那两格是本条最值得记的一课**：S4 §4.4 刚刚更正了
「骨架注释把默认值写成 `Indifferent`」，**却在 §4.3 照抄了那套错默认下才成立的期望值**。
crate 的默认是 `RequireCanonical`，`"Zg"` 缺 padding、`"ZhA"` 是 3 符号无 padding，
两者都先撞 `InvalidPadding`。同一条错在相邻两节里只改了一半。

### 2.2 三态语义（crate 实测，逐格）

| 输入 | `RequireCanonical`（默认） | `Indifferent` | `RequireNone` |
|------|:---:|:---:|:---:|
| `"Zg=="` | `Ok(b"f")` | `Ok(b"f")` | `Err(InvalidPadding)` |
| `"Zg="` | `Err(InvalidPadding)` | `Ok(b"f")` | `Err(InvalidPadding)` |
| `"Zg"` | `Err(InvalidPadding)` | `Ok(b"f")` | `Ok(b"f")` |
| `"ZhA"` | `Err(InvalidPadding)` | `Ok(b"f\x10")` | `Err(InvalidPadding)` |
| `"Zm9v"` | `Ok(b"foo")` | `Ok(b"foo")` | `Ok(b"foo")` |

即 `RequireCanonical` 的算式就是 crate 的 `(padding_count + morsels) % 4 == 0`：
`"Zg=="` → `2 + 2 = 4` ✅；`"Zg="` → `1 + 2 = 3` ❌；`"Zg"` → `0 + 2 = 2` ❌。

### 2.3 全量对拍结论

**方法**：Rust 侧建探针 crate（`base64 = { path = "/tmp/rb" }`，crate 0.23.1 `5b98ee1`），
MoonBit 侧建同构探针（`cmd/diff`），两侧对**同一批输入**各打印一行「输入 hex → 结果」，
再用脚本按**变体名 + 字段值**逐行比对。两侧探针跑完即删，未入库。

**输入集**：字母表前缀长度 `0..=8`，每种长度做三类注入——
① 后缀 +1 / +2 个特殊字节；② 前缀 +1 个特殊字节；
特殊字节集 = `=` `-` `_` `!` `\n` `\x00`（含 padding、URL-safe 符号、非法字符、控制字符）。

**结果**：

```
crate=165  本库=165  mismatches=0
```

165 例的**变体名、offset、byte 三要素全等**，0 处不符。
S4 §4.3 表里那 12 格、以及 S4 §4.4 的 `padding_mode` 三态，都包含在这批里。

> **这不是「跑通就算」**：对拍比的是**错误对象**，不是「是否报错」。
> offset 差一位、padding 与 InvalidByte 混同，都会立刻现形。

## 3. 裁决三：错误类型 re-export —— S4 §3.1 动作 5 在 MoonBit 里不成立

### 3.1 S4 的写法

S4 §3.1 动作 5：`DecodeError` 由 `lib/internal` **re-export** 到 `lib`
（「`pub typealias` 或直接 `pub` 使用」），S4 §3.2 承诺的对外形态是
`decode_slice → Result[Int, DecodeSliceError]`，调用方能写 `@lib.InvalidByte(...)`。

### 3.2 逐条实测（Minimal 探针，三包链 `internal → re → app`）

| 试法 | 结果 |
|------|------|
| `pub typealias X = @base.X` | ❌ 语法不存在（只有 `pub type X = ...`） |
| `pub suberror X = @base.X` | ❌ 解析错误 |
| `pub type X = @base.X`，当**类型**用 | ✅ `Result[Int, X]` 可声明 |
| `pub type X = @base.X`，写 `@re.InvalidLength(n)` | ❌ `Value InvalidLength not found in package re` |
| `pub type X = @base.X`，写裸 `InvalidLength(n)`（**第三方包**） | ✅ 可用（含嵌套 `suberror` 里做内层匹配） |

**结论**：MoonBit 的 `pub type X = @other.X` 是**重命名（`pub using`）**，
只搬**类型名**；**变体名不跟着走**。

### 3.3 变体到底在哪能「裸写」

变体在**定义包**里可读可构造；在**其它包**里只读 ——
**唯有类型推导能把它带进作用域时**才可裸写。实测三种位置：

| 所在的包 | `match Err(Bad(n))`（模式） | `Err(Bad(1))`（构造） | 说明 |
|---------|:---:|:---:|------|
| 定义包（`lib/internal`） | ✅ | ✅ | 变体属它 |
| 别名持有者（`lib/`） | ✅ | ❌ `Cannot create values of the read-only type` | 别名只带类型名，构造不了 |
| 第三方包（用户代码 / 包外测试） | ✅ | ✅ | 类型推导把变体一并带来 |

**这张表是本文最可复用的一条**：它解释了为什么「`@lib` 对外暴露 `DecodeError`」时，
**`lib/` 自己的测试反而是最受限的那个位置**。

### 3.4 还有一条更硬的：`internal` 包不可被外部 import

`moon` 拒绝 `cmd/main` / 根包 import `lib/internal`：

```
Cannot import internal package .../lib/internal@0.1.0 in .../base64-moon@0.1.0
due to internal visibility rules
```

于是**根包（README 文档测试的宿主）**这个位置同时受两条限制：

1. **不能**裸写变体名（它连 `internal` 都 import 不了，变体无从解析）；
2. **不能**对 `Result[_, DecodeError]` 做 `assert_eq(.., Ok(..))`——
   `Eq` / `Debug` 的 impl 由 `internal` 提供，此处看不见。

第 2 条是 M0 的隐藏地雷：S4 §3.3 提醒过「改 `decode` 签名会立刻让 README 变红」，
但**改成 `BytesView` 只是第一步**；把返回类型换成 `DecodeError` 后，
README 里那条 `assert_eq(@lib.decode(..), Ok(bytes))` **仍会红**，且原因与签名无关。

### 3.5 本库的落地形态

`lib/facade.mbt`：

- `pub type DecodeError = @internal.DecodeError`（及其余三个错误/配置类型）——**类型名**对外；
- `pub fn expect_*` 一组**断言器**：把「构造期望值 + 比较」都留在 `lib` 内，
  调用方只给「期望的形状」（如 `@lib.expect_invalid_byte(r, 4, 33)`）；
- `pub fn describe(e) -> String`：把错误渲染成可读串，供宿主展示，
  免去宿主为了打印而 import `internal`。

**第三方包**（真实用户）不受这些限制——它们可以直接 `Err(InvalidByte(4, b'!'))`。
这层 `expect_*` 是**为「持有别名的包」这个盲区补的**，不是对外 API 的主形态。

> **为什么不给 `internal` 补一组公共构造器**（`@internal.InvalidByte(4, b'!')` 那样）：
> 那会把「内部错误构造面」扩成对外契约，仅为测试服务；且用户代码本就不需要它。
> 宁可多几个 `expect_*`，也不扩公共面。

## 4. 裁决四：S4 漏了一条会踩红门禁的动作

S4 §3.3 的判据里写了「README 文档测试已同步」，但 §3.1 的**动作清单没有对应条目**。
照着动作清单改完签名就推，`moon test` 立刻红。本文把它补成动作清单里的显式一条（见 §5.1）。

同类漏项还有一处：S4 §3.1 只列了 `lib/facade.mbt` 的动作，
但 `cmd/main/main.mbt` 也调用了 `decode`——签名一改它就编译不过。
凡**调用点**都要进清单，不能只列**定义点**。

## 6. M1 实跑记录（本次）

### 6.1 一个被用例抓到的实现错

`Alphabet::url_safe()` 第一版写成：

```moonbit
symbols[b'+'.to_int()] = b'-'   // ← 错
symbols[b'/'.to_int()] = b'_'   // ← 错
```

**表的下标是 6 位值，不是字符的码点**。`b'+'.to_int()` 是 43，于是改掉的是
下标 43 那一格（**`r` 的槽位**——`q` 是 42；本文原写 `q`，已由
`lib/internal/tables_wbtest.mbt` 的白盒用例更正），标准的 `+` / `/` 仍在 62 / 63。表现为
`encode(b"\xfb\xff", alphabet=url_safe())` 输出 `"+/8="` 而不是 `"-_8="`——
被 `encode_urlsafe_uses_alt_chars` 用例当场抓住。正确写法是 `symbols[62]` / `symbols[63]`。

> **本轮补的白盒护栏**：`lib/internal/tables_wbtest.mbt` 把上面两条不变量
> （62/63 是什么、URL-safe 是独立副本）钉成了可红用例，不再只靠这一个黑盒用例。
>
> 同类还有一处**引用语义**的坑：`url_safe()` 必须 `copy()` 后再改。
> `FixedArray` 是引用语义，原地改会连带把标准表也改掉，
> 于是带不带 `alphabet=` 参数输出完全相同。

### 6.2 一处被 `Int` 位宽抓到的实现错

`decode_suffix` 的尾字节写回第一版用 `Int` 装拼好的 32 位值：

```moonbit
let mut packed : Int = (morsels[0] << 26) | ...
out[idx] = (packed >> 24).to_byte()
packed = (packed << 8) & 0x7FFFFFFF
```

**MoonBit 的 `Int` 是 31 位有效位 + 符号位**，而 base64 的最高字节常 ≥ 0x80
（如 `"-_8="` 的首字节 `0xFB`）。用 `Int` 装会立刻把最高位当符号：
`packed` 变成负数，`>> 24` 抽出负数、`<< 8` 丢掉 `0x80`——
实测表现为解出 `0xfb 0x7f`（应为 `0xfb 0xff`），被 `decode_round_trips` 抓住。

正确做法是**整段用 `UInt`**（32 位无符号，与 crate 的 `u32` 对齐）：

```moonbit
let mut packed : UInt = (morsels[0].reinterpret_as_uint() << 26) | ...
```

> 这条对**后续所有整数运算**都成立：凡是「按 32 位无符号语义处理」的位运算，
> 一律用 `UInt`，别用 `Int` 加掩码凑。掩码凑法（`& 0x7FFFFFFF`）只能挡住一部分，
> 挡不住最高位被当成符号位参与比较。
