## 1. 裁决一：M5 的形态与判据

### 1.1 M5 在 S4 里的原始定义与缺口

[S4 §8.1](S4-实施规格与落地顺序.md) 给了五条轴（长度 / 字母表 / 编码 padding /
padding_mode / 冗余位），但没有说**怎么把轴变成能断言的东西**；§8.2 只说「与 Rust 对拍」。

**原始定义的两处不够**：

1. **没有真值出处**——「跑一遍记下自己的输出」会被 AGENTS.md §三.2 铁律 3
   （禁止 `actual == actual`）直接否掉。矩阵必须由**独立于实现的东西**约束；
2. **没有落点文件**——只说 `lib/*_test.mbt`，没定文件名与夹带关系。

### 1.2 本轮的落地形态

| 项 | 决定 | 理由 |
|----|------|------|
| 文件 | `lib/base64_matrix_test.mbt`（**黑盒**，`*_test.mbt`） | 锁的是**公共契约**：只碰 `@lib.encode` / `@lib.decode` / `@lib.encode_slice` |
| 数据轴 | 文件内私有 `det_bytes(n)` / `det_lengths()` | **不进公共面**（见 §1.3） |
| 判据 | 四条**结构性不变量** + 一条 **CPython 定值** | 不变量独立于实现；定值提供「绝对锚点」 |
| 规模 | 单文件 ≤800 行（实测见 §6 的 `test-scale`） | AGENTS.md §三.1 |

**四条不变量**（S4 §8.1 的原文，本文把它变成可跑断言）：

| # | 不变量 | 断言方式 | 覆盖的轴 |
|:-:|--------|---------|---------|
| ① | 往返 `decode(encode(x,p),m) == x` | 逐长度扫，三种 `padding_mode` 各一遍 | 长度 × 字母表 × padding × mode |
| ② | 长度上界/精确 | `encode(x).length() == ((n+2)/3)*4`；无 padding 形另算 | 长度 × padding |
| ③ | 冗余位 | `Zh==` 严格错 / 宽容对；宽容集 ⊇ 严格集 | 冗余位 × 长度 |
| ④ | padding | `padding=false` 输出无 `=`；`RequireNone` 拒 `=` | padding × mode × 长度 |

**第 ⑤ 条是新增的**：`matrix_matches_python_reference` 把前 8 个长度的期望串
**硬编码**为 CPython `base64.b64encode` 的输出。这一条的作用不是「覆盖更多组合」，
而是给矩阵一个**不依赖本库任何实现的绝对参照**——四条不变量全是「自洽式」的，
若 encode 与 decode **错得一致**，不变量会全绿（典型：两者都把 `+` 写成 `-`）。
定值对拍专门堵这个洞。

### 1.3 数据轴为什么不导出

第一版把 `det_bytes` / `matrix_lengths` 写成了 `pub fn` 放在 `lib/`——
`moon info` 立刻把它们列进了 `.mbti`。**这是错的**，理由与 [S5 §3.5](S5-实施裁决与M1落地.md) 同源：

> 「那会把内部面扩成对外契约，仅为测试服务……宁可多几个 `expect_*`，也不扩公共面。」

修法是**把辅助挪进测试文件**：`*_test.mbt` 编译在包**外**，文件内的 `fn`
是黑盒私有实现细节，不会进 `.mbti`。复跑校验：

```bash
moon info && grep -c 'det_bytes\|det_lengths' lib/pkg.generated.mbti   # 期望 0
```

### 1.4 M5 的边界（本轮**没有**做的）

- **没有**与 rust-base64 对拍（S4 §8.2 提到）：S5 §2.3 已经对拍过 165 例、
  S6 §3 用 Python 手写判据对拍过 738 例。再跑一次 Rust 侧边际收益低，
  且需 `/tmp` 克隆（产物不入库）。**结论按已有对拍，不重复**。
- **没有**做属性测试 / fuzz（S1 §6 的 ⑧）：需先有 ① 的判据（本轮刚有），
  且 fuzz 基础设施属另一轮工作量。
- **没有**把矩阵扩到「全 64 符号 × 全配置」的笛卡尔积：按 AGENTS.md §三.2 铁律 6，
  判据是**独立真值点数**而非组合数。当前 `0..=64` 已覆盖 12 种余数组合，
  再展开只是重复（见 §1.5 的「为什么不是机械展开」）。

### 1.5 为什么长度集是 `0..=64` + 边界点，而不是别的

「3 字节 → 4 符号」的周期是 **3**，padding 的周期是 **4**，两者最小公倍数是 **12**。
`0..=64` 是 12 的 5 倍余 4，**必然覆盖全部 12 种余数组合**——这是「最小完备集」。

再加的大尺寸点 `{127..130, 255..257, 1023..1025, 4095, 4096}` 不是「更多用例」，
是**另一条轴**：它们让「整块快循环 vs 尾块」的分界进矩阵
（若将来重启 M4，正是这条轴会第一时刻报警）。

## 2. 裁决二：现状基线（本轮测量的起点）

统一口径（照 [S7 §6](S7-M4性能前提复跑与裁决.md)）：

1. **基准 = 手上这份代码的现状**：`@internal` 的 `va_quads`（= 现状 `decode_into` 的
   完整 4 元组段，逐符号查表 + `for k` 内循环）；
2. **交错 A/B**：每轮测全部变体，各取 **41–61 轮中位数**；
3. **防 DCE**：返回值累加后读出（否则编译器删掉整段）。

探针写在 `lib/internal/` 的临时 `*_wbtest.mbt`，跑完即删（不入库）。
尺寸 88 B / 5.4 KB / 185 KB，`wasm-gc` + `--release`。

**基线自检**：`va_quads` 与库 `decode_into` 在同段上的输出逐字节相同
（§3 的正确性检查已覆盖），且 `va_quads` 的绝对耗时与 [S7 §2.2](S7-M4性能前提复跑与裁决.md)
的「4 符号展开」量级一致（185 KB 约 19 ms / 60 次），口径自洽。

## 3. 裁决三：「32 位装载」实测为零收益，该思路关闭

[S7 §3.1](S7-M4性能前提复跑与裁决.md) 的最后一条待测项：

> | 换 32 位装载思路（如两个 `UInt` 拼接） | 未测；但 §2.2 的 UInt32 变体已显示 32 位路径能到 0.89–0.92× | ⏸ **待测**，且必须先把正确性做对 |

本轮把它测了，且**先把正确性做对**（S7 那次的 UInt32 变体就是「更快但错」）。

### 3.1 变体定义

| 代号 | 形态 | 说明 |
|:----:|------|------|
| **A** | 现状 | 逐符号查表 + `for k = 0; k < 4` 内循环 + `Int` 累积 |
| **B** | **32 位装载** | 4 次查表 → `(m0<<26)|(m1<<20)|(m2<<14)|(m3<<8)` 装进一个 `UInt` → `to_be_bytes()[0..3]` 取 3 字节 |
| **C** | 32 位装载 + 4 组超级块 | 一次吃 16 符号（4 个 B 块），crate `BLOCKS_PER_FAST_LOOP` 形状 |
| **D** | 32 位装载 + 批量检错 | 装载后 `(b0|b1|b2|b3) < 0` 一次判错，非法时再退化为逐符号定位 |
| **F** | 保留内循环 + 攒数组 | `for k` 内循环照旧，但把 4 个 morsel 先攒进 `FixedArray[Int]` 再拼 |
| **E/H** | **去内循环** | 4 条显式 `let m0..m3 = table[..]`，`Int` 累积（**不碰 `UInt`**） |

### 3.2 结果（三次复跑，41–61 轮中位数，数值为 **ratio = 变体 / A**，<1 即更快）

| 变体 | 88 B | 5.4 KB | 185 KB | 三次复跑一致性 | 正确性 |
|:----:|:----:|:------:|:------:|:--------------:|:------:|
| **B**（32 位装载） | 0.97–0.98 | 0.97–0.98 | 0.97–0.98 | ✅ 稳定 | ✅ |
| **C**（超级块） | 1.21–1.22 | 1.26–1.28 | 1.24–1.25 | ✅ 稳定 | ✅ |
| **D**（批量检错） | — | 0.77 | 0.77 | 单轮 | ✅ |
| **F**（留内循环 + 攒数组） | 1.52 | 1.52–1.53 | 1.52–1.53 | ✅ 稳定 | ✅ |
| **E / H**（去内循环） | **0.74–0.75** | **0.72–0.72** | **0.71–0.72** | ✅ 稳定 | ✅ |

### 3.3 三条结论

1. **「32 位装载」零收益，该思路关闭**。B = 0.97–0.98，落在噪声内，
   与 [S7 §2.3](S7-M4性能前提复跑与裁决.md) 的根因判断一致：`wasm-gc` 上
   `UInt`/`UInt64` 的装箱开销把位运算省下的那点抹平了。
   **S7 §3.1 表里「32 位路径能到 0.89–0.92×」那个信号是误读**——
   那次快的不是「32 位装载」，是**它顺手少做了检查**（尾部错就是这么来的）。
2. **C（超级块）更慢**（1.21–1.28×）：与 [S7 §2.2](S7-M4性能前提复跑与裁决.md) 的
   `s32` 超级块（1.50–1.56× 慢）同向，只是本轮 B 的装载更省，故倍数小些。
   **方向一致：块越大越慢**。
3. **D（批量检错）到 0.77×**：它比 B 快**不是**因为装载，而是因为它**合并了 4 次分支**。
   这条是意外收获，指向下面 §4 的真因。

## 4. 裁决四：「去内循环」1.37×——实测与未落地理由

### 4.1 归因实验（185 KB，41 轮中位数）

把「可能的快因」逐条隔离，看谁是真的：

| 变体 | 相对 A | 证明了什么 |
|:----:|:------:|-----------|
| **F**：保留 `for k` 内循环，只把结果攒进数组 | **1.52×** | 内循环**本身就是成本**，不是「没攒数组」 |
| **H**：去掉内循环，4 条显式 `let`，逐条判错 | **0.71×** | 去掉内循环 → 直接快 1.4× |
| **E**：`(acc<<6)|m` 累积形态（与 H 同构，仅写法不同） | **0.72×** | 与 H 等价，说明差异来自**循环消除**而非具体算式 |

**关键读数**：`F` 比 `A` 还慢 52%，说明现状那个 `for k = 0; k < 4` 不但没被展开，
还在每次迭代里付了循环控制开销（且它挡在查表与位运算之间，阻断了流水线重叠）。

### 4.2 正确性（这是本轮与 S7 那次的关键区别）

| 检查 | 方法 | 结果 |
|------|------|------|
| 逐字节一致 | 15 个长度（含 0/1/2/3/…/129/1024）下与库 `decode_into` 的前缀逐字节比 | ✅ 全等 |
| 长度一致 | 每个变体产出 `quads_end/4*3` 字节 | ✅ |
| **错误 offset 一致** | 在完整 4 元组内 9 个位置注入 `!`，比「变体报的下标」与「库报的 offset」 | ✅ 9/9 相同 |
| 非完整段不越界 | 尾巴（`quads_end` 之后）的错误**不由这里报**，交给 `decode_suffix` | ✅ 行为一致 |

> **为什么错误 offset 必须逐格核**：S7 那次的「更快」变体就是**尾部错了一个 6 字节块**。
> 快而错没有价值。本轮把「快」与「对」分开验：先证对，再谈快（§4.3 的复跑命令含这一步）。

### 4.3 为什么本轮**不**把它落进 `lib/`

三条，都是纪律层面的：

1. **实现变更是独立 PR 的事**（[S4 §7.2](S4-实施规格与落地顺序.md) 的「M4 不得与 M3 同 PR」同理）：
   本文是**裁决 + 测量**篇，落地要走「先写差分基线 → 改实现 → 复跑差分」。
   混在一起时一旦差分红了分不清是谁的锅。
2. **它需要一个黄金值基线**：按 [S4 §9.3](S4-实施规格与落地顺序.md)，实现变更前
   必须先把**当前输出**固化成字面量断言。本轮刚落的 M5 矩阵**正是这个基线**
   （四条不变量 + CPython 定值）——它让下一轮改 `decode_into` 时有个能立刻报警的网。
3. **收益的量级要先说清**：1.37× 是**热循环段**的比值，不是**端到端**的。
   §6 的性能口径说明：完整 4 元组段在 88 B 输入里只占一部分，端到端倍数会更小。
   落地前应补一条端到端对照，避免又出现 [S6 §1](S6-性能实测与M3裁决.md) 那种
   「分子分母不同层」的错。

> **因此本文的处置是**：把「去内循环」列为**证据充分、待独立落地**的性能项，
> 写明形态（§4.1 的 H/E）、正确性证据（§4.2）与未落地的理由（本节）。
> **不要**据此直接改 `decode_into`——先起一个带差分的 PR。
> > **（2026-10-08 补）该 PR 已由 [S10](S10-去内循环落地与端到端对照.md) 交付**：
> > 两步走（先差分基线、再改实现），形态在 H 之上加了「合并判错 + 冷路径外提」。

### 4.4 与 S7 的关系：不是推翻，是补完

[S7](S7-M4性能前提复跑与裁决.md) 的结论是「**chunk 化**（更宽的装载）是负收益」——
本文**完全支持**：B 零收益、C 更慢，方向一致。
S7 没有说「`decode_into` 的循环形态已最优」；本文补上的正是那一格：
**瓶颈不在装载宽度，在循环是否展开**。

> 两条合起来是一句话：**`wasm-gc` 上「加宽一次读的量」不值钱，「少绕一圈循环」很值钱。**

## 6. 复跑方式

统一前置：`export PATH="$HOME/.moon/bin:$PATH"`；后端 `wasm-gc`；`--release`。

### 6.1 M5 矩阵（§1）

```bash
bash scripts/test.sh                  # 跑全部测试（含 lib/base64_matrix_test.mbt）
moon test --target wasm-gc --release  # 后端口径复跑
```

判据：矩阵全绿；且反例能红（见 §6.3 的负向验证）。

### 6.2 定值对拍（§1.2 第 ⑤ 条）

```bash
# Python 侧黄金值（stdlib base64，零依赖）——与 det_bytes 同一数据式子
python3 -c "import base64;[print(n, base64.b64encode(bytes((i*37+11)&0xFF for i in range(n))).decode()) for n in range(8)]"
```

### 6.3 负向验证（**先证明能红**，AGENTS.md §三.2 铁律 5）


## 7. 边界（本文不做什么）

- **不改 `lib/` 实现**：§4 的加速项是「待落地」，本文只给实测与形态，不动 `decode_into`。
  （该加速项已由 [S10](S10-去内循环落地与端到端对照.md) 独立落地。）
- **不重述 S1–S7**：只裁决 M5 形态与那条待测项，冲突时以本文实测为准。
- **不重复已有对拍**：Rust 侧 165 例（S5）/ Python 侧 738 例（S6）**不重跑**，
  M5 的定值对拍只取 CPython 前 8 长度作**绝对锚点**，不取代已有对拍。
- **§2–§4 的数字是同机相对量**，与 [ISSUE #3](https://cnb.cool/tryandrun/moonbit_dev/base64-moon/-/issues/3) 的历史口径**不可混比**（S2 §5 已立此规矩）。
- **不解禁 SIMD**：本文既没解禁，也没降低门槛——B/C 的负收益进一步说明
  「加宽装载」在 `wasm-gc` 上不是出路。
