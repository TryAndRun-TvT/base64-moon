# S7 · M4 性能前提复跑与裁决

> **状态**：现行　｜　日期：2026-10-07　｜　索引：[docs/README.md](../README.md) §1

> 一句话结论：**M4 的「解码 1.6–2.0×」前提不成立，且方向是反的。**
> 本次按可复跑口径复跑了三种 chunk8 形态与两种 chunk6 形态，
> **在当前 `decode_into` 的 4 符号展开基线上，全部更慢**（正确形态 1.53–1.64×，即慢 53%~64%）；
> 唯一「更快」的变体（UInt32 累积，0.89–0.92×）**输出是错的**。
> 根因不是算法，是 **`UInt64` 在 `wasm-gc` 上的成本**压过了位运算省下的开销。
>
> **与上一版评论的关系**：上一版说「chunk8 是 0.78×（慢 22%）」——**方向对，数值不可复现**。
> 本次同口径测得 **1.53–1.64×**。两个数都不是 S1 §6.1 的 1.6–2.0×。
> 数字结构见 [§2](#2-裁决一m4-的收益前提复跑为负)，方法论教训见 [§4](#4-为什么-s1-量出了-1620)。

## 2. 裁决一：M4 的收益前提复跑为负

[S6 §7](S6-性能实测与M3裁决.md) 留着这句：「**不承诺 M4 的收益**：
M4（批量内核 1.6–2.0×）是 S1 §6.1 的实测结论，本轮**未复跑**」。
本次把它复跑了。

### 2.1 复跑口径（三个不变量，缺一个数字就不可比）

1. **基准必须是「手上这份代码的现状」**，不是历史版本——基线取仓库真实的
   `@internal.decode_into` / `encode_into`（持一个 `Engine`，不含 `Engine::new`）；
2. **交错 A/B**：每一轮同时测全部变体，各取 **21 轮中位数**——跨轮漂移（wasm-gc 的 GC）
   会同时打在所有变体上，相除后抵消；
3. **防 DCE**：把返回值累加进 `Ref` 并读出来，否则编译器删掉整段（[S6 §6.1](S6-性能实测与M3裁决.md)已记）。

每轮 40 次迭代，尺寸 88 B / 5.4 KB / 185 KB，`wasm-gc` + `--release`。

### 2.2 结果（185 KB，三次复跑区间）

| 变体 | ratio（基准 = 库 `decode_into`） | 正确性 |
|------|:---:|:---:|
| 复刻「4 符号展开」（= 现状） | **0.99–1.02**（等价，口径自洽 ✅） | ✅ |
| `c8`：8 符号 → `UInt64` → 6 字节 | **1.54–1.63×** 慢 | ❌ 尾部错 |
| `c8b`：`accum.to_be_bytes()[..6]`（S4 §7.1 字面形状） | **1.53–1.64×** 慢 | ✅ |
| `s32`：32 符号超级块（crate `BLOCKS_PER_FAST_LOOP=4` 形状） | **1.50–1.56×** 慢 | ❌ 尾部错 |
| `c8` + **UInt32 累积**（不碰 `UInt64`） | **0.89–0.92× 快** | ❌ 尾部错 |

编码侧（185 KB）：`c6` = 6 字节 → `UInt64` → 8 字符，**1.53–1.79× 慢**。
5.4 KB 同向：解码 1.34–1.68× 慢，编码 1.63–1.69× 慢。88 B 因单次 ~0.5 µs 落进时钟分辨率，不取用。

**三条结论**：

1. **方向反了**。按现状基线，chunk8/chunk6 **不是提速，是降速 50%~64%**。
   S1 §6.1 的「1.6–2.0×」在当前代码上**不复现**；
2. **「更快」与「正确」在这次测量里不共存**。唯一低于 1.0 的变体（UInt32 累积）
   尾部字节是错的——不是「忽略错误处理」的小瑕疵，是最后一块 6 字节没写对；
3. **`be[..6]` 是唯一正确的 6 字节取法**。S4 §7.1 写的 `accum.to_be_bytes()[..6]`
   **字面是对的**（`m0<<58 … m7<<16` 把 48 位 payload 摆在 bits 16..63，故取 `be[0..6]`）。
   用 `be[2..8]` 会静默错位——**但 S4 没写错，是读的人容易读错**：
   它只说「拷 6 字节」，靠 `[..6]` 表达起点。这条**已就地补一句显式说明**（见 [§5](#5-处置按本文口径改什么)）。

### 2.3 根因：不是算法，是 `UInt64` 在 `wasm-gc` 上的成本

把 chunk8 拆成两半单独测（185 KB）：

| 只做哪一半 | 耗时 |
|---|---:|
| 只做「8 符号 → `UInt64`」装载 | ≈ 490–540 µs |
| 只做「4 符号展开」（现状那半） | ≈ 465–470 µs |

**装载那一半本身就比现状整段慢。** `UInt64` 在 `wasm-gc` 上是装箱值，
每次 `<<`/`|` 都要走引用路径；而 32 位 `Int`/`UInt` 是未装箱的。
现状的「4 符号 → `Int` 累积 → 拆 3 字节」全程 32 位，恰好绕开了这个成本。

> **这是 [S6 §1](S6-性能实测与M3裁决.md) 那条教训的姊妹版**：
> S6 立的是「**量占比时分子分母必须同层**」，本文加一条
> 「**量倍数时基准必须是手上这份代码的现状**」。
> 两条合起来是一句话：**先定义清楚你在跟谁比、比什么。**

## 3. 裁决二：M4 的形态必须重定

既然解码侧的 chunk 化是负收益，M4 的「唯一证据充分的性能项」这个定位**不再成立**。

### 3.1 三个候选方向，各自的证据状态

| 方向 | 证据状态 | 建议 |
|------|---------|------|
| 解码 chunk8 / 超级块 | **已实测证伪**（1.5×+ 降速，且 `UInt64` 是结构性成本） | ❌ 不做 |
| 编码 chunk6 | **已实测证伪**（1.6–1.8× 降速，同因） | ❌ 不做 |
| 换 32 位装载思路（如两个 `UInt` 拼接） | 未测；但 §2.2 的 UInt32 变体已显示 32 位路径能到 0.89–0.92× | ⏸ **待测**，且必须先把正确性做对 |
| `V128` SIMD128 | [S2 §4](S2-现状基线与迁移缺口.md) 的恢复条件是「M4 交付且数字可复跑」 | 🚫 **条件更硬了**：M4 数字复现为负，不该解禁 |

### 3.2 因此 M4 的正确处置 = **不做 chunk 化，把口径改成实测**

这不是「M4 砍掉」，是「**M4 的原假设已被实测证伪，按 S6 §2.3 的先例结清**」：

- 「收益已被实测证伪，所以不做」 ≠ 「收益为零所以跳过」——
  两者在文档上必须分清，否则下一轮还会有人重开 M4；
- **M1 落地时那笔收益已经顺手兑现了**：`decode_into` 的 `while i < quads_end`
  就是「4 符号展开」，S1 §6.1 当年量的「升到 4 符号展开」的收益**在 M1 已到账**。
  M4 想在**已经提速过的基线**上再加，这次没加成。

> **一旦哪天要重启性能工作，先跑本文 §6 的对照**，
> 而不是照 S4 §7.1 的形状直接落笔——那条形状已实测为负收益。

## 4. 为什么 S1 量出了 1.6–2.0%

S1 §6.1 的对照写得清楚：一侧是「逐字符累积 + `Buffer::write_byte`」，另一侧是
「4 字符 → 3 字节展开」。**它是对的**——那确实是 1.6–2.0×。

问题出在**归账**：

> S1 量的时候（2026-10-07 前），仓库里**还没有** M1 的那段循环。
> 于是「升到 4 符号展开」的收益被记成了 **M4 的账**；
> 而 M1 落地 `decode_into` 时**顺手就把这笔收益兑现了**（`while i < quads_end` 就是 4 符号展开）。
> M4 再要做的 chunk8，是在**已经兑现过收益的基线**上继续加。

**S1 的文字没错，是「M4 承诺的 1.6–2.0×」这个承接错了**——
S2 §4 → S4 §7 → S6 §7 一路把 S1 的「4 字符展开」翻译成了「M4 要做的事」，
而 M1 已经把它做完了。

**处置**：S1 §6.1 数字**保留**（它作为「逐字符 vs 4 符号」的对照仍然成立，可复跑），
但在承接处加一句「**该收益已在 M1 兑现；M4 的 chunk 化另测为负，见 S7**」。

## 6. 复跑方式

统一前置：`export PATH="$HOME/.moon/bin:$PATH"`；`wasm-gc` + `--release`；探针**不入库**（跑完即删）。

```bash
# 1) 阻塞项：确认 docs-index 已绿（本文已修）
bash scripts/gates.sh

# 2) 复跑本文 §2 的对照：探针写成 lib/ 下的临时 *_test.mbt（黑盒；放 lib/internal 看不见 @lib）
#    口径三要素（缺一则数字不可比）：
#      · 基准 = 持 Engine 调 @internal.{decode,encode}_into，**不含 Engine::new**
#      · 交错 A/B：每轮测全部变体 × 21 轮取中位数（抵消 wasm-gc GC 的跨轮漂移）
#      · 防 DCE：返回值累加进 Ref 并读出，再打印
moon test --target wasm-gc --release

# 3) 正确性必须逐字节比：只比「完整 4 元组」覆盖的前缀（尾部归 decode_suffix）
#    实测会现形的三条：c8 / s32 / UInt32 变体尾部各差一个 6 字节块
```

**判据（本文 §2.2 的数字以此为准）**：

| 结论 | 期望 |
|------|------|
| 复刻「4 符号展开」 vs 库 `decode_into` | ratio ∈ [0.95, 1.05]（**等价性自检**，不在此区间说明探针写错了） |
| `c8b`（正确形态） vs 库 `decode_into` | ratio > 1.4（**负收益**） |
| `c6` vs 库 `encode_into` | ratio > 1.4（**负收益**） |

> **88 B 不取用**：单次 ~0.5 µs 已经落进 `monotonic_clock` 的分辨率 + GC 抖动里，
> 中位数跨轮漂移 > 50%。**小于 1 µs 的测点不要拿来算倍数**——这是本次踩到的第二个坑。

## 7. 边界（本文不做什么）

- **不改实现**：本文的裁决是「不做 chunk 化」，故本次无 `lib/` 改动（除探针跑完即删）。
- **不重述 S1–S6**：只裁决 M4 的性能前提，冲突时以本文实测为准。
- **§2 的数字是同机相对量**，与 [ISSUE #3](https://cnb.cool/tryandrun/moonbit_dev/base64-moon/-/issues/3) 的历史口径**不可混比**（S2 §5 已立此规矩）。
- **不解禁 SIMD**：恰恰相反，M4 数字复现为负使 S2 §4 的恢复条件更硬。
- **不承诺时间表**：重启性能工作的前提是「先跑本文 §6 拿到新对照」。
