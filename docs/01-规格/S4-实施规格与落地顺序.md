## 2. 目标形态总览

### 2.1 三个包的最终形态

```
lib/internal/          内核：BytesView → FixedArray[Byte]，零分配、零 String
  alphabet.mbt         Alphabet（64 符号 + padding）+ 6 张预置表 + 构造期校验
  tables.mbt           build_encode_table(64) / build_decode_table(256)
  config.mbt           Config + DecodePaddingMode + 3 个具名构造器
  error.mbt            DecodeError(4) / DecodeSliceError(2) / EncodeSliceError(1) / ParseAlphabetError(4)
  engine.mbt           Engine：持字母表 + 配置 + 两张表；e_standard() / e_url_safe()
  encode.mbt           encoded_len / encode_into（内部不带 padding）
  decode.mbt           decoded_len_estimate / decode_into / decode_suffix
  pad.mbt              add_padding（唯一写 padding 字节的地方）
lib/                   外壳：物化 + 命名参数（唯一 pub 面）
  facade.mbt           encode / decode / decode_slice / encode_slice + Alphabet 变体开关
cmd/main/              宿主：往返演示 + 不可解的错误展示
```

**与 S3 的两处差异（都已在本仓库实证）**：

1. **新增 `pad.mbt`**。`add_padding` 在 crate 里是 `encode.rs` 的自由函数，
   而本仓库的 `encode_into` 必须**不写 padding**（同 crate 纪律），否则 `encode_slice` 的
   `OutputSliceTooSmall` 判定会被 padding 搅乱。所以 padding 单独成文件，**只有一个写点**。
2. **`engine.mbt` 不提供「默认引擎」全局量**。S3 §2.2 提醒过「不得做成全局可变状态」，
   但更严的写法是：`Engine` 不暴露全局单例，外壳用**不带缓存的纯函数形态**（见 §2.3）。

### 2.2 内核的硬边界（M1 起不可破）

| 边界 | 内容 | 违反后果 |
|------|------|---------|
| 零分配 | 内核函数不得 `Buffer` / `Bytes::from_array` / 任何堆分配 | 内核不再能对齐 `&mut [u8]`，S1 §9 的分层模板作废 |
| 零 `String` | 内核签名里不得出现 `String` / `Char` | base64 输出非 ASCII 时 `Bytes → String` 恒错（S1 §5.3） |
| 单向依赖 | `internal` 永不 import `lib` | MoonBit 拒绝 import 环，直接编译失败 |
| 表在 `Engine` 上 | 建表只发生在 `Engine::new` | 每次调用现建 = S2 §3 P1 的可测损失 |

### 2.3 一个待定问题：默认引擎要不要缓存

S3 §2.2 的写法是「外壳内部持一个默认引擎」。但 MoonBit 里让「纯函数」复用同一个引擎，
只有两条路，**都有代价**：

| 方案 | 写法 | 代价 |
|------|------|------|
| **A. 每调用建表**（建议） | `encode` 内部 `Engine::new(standard(), Config::default())` 再调内核 | 每次调用建 64+256 项表（S2 §3 P1 的损失仍在） |
| B. 全局缓存 | `let default_engine : Engine = Engine::new(...)` | 全局可变/惰性初始化状态；AGENTS.md §三.2 铁律 7「测试不得依赖执行顺序」会被动摇 |

**建议 A，并把它写成明账**：M3 的完成判据只承诺「表不再每次现建**于内核层**」，
不承诺「外壳纯函数零建表」。理由是 MoonBit 目前没有 `const fn`（S1 §3.3），
「编译期展开表」这条路不存在；而引入全局缓存的收益（小输入下省一次 320 项写）
**没有实测支撑**，不值得用它换掉「测试不依赖执行顺序」这条铁律。

> **这是一条待实测项，不是结论**：M4 交付后应补一条口径——「1 KB 输入下，
> 建表开销占总时长的百分比」。测不出显著占比，就一直用方案 A。
> 复跑：对同一输入分别跑「外壳 `encode`」与「直接持 Engine 循环调 `encode_into`」，比对总时长。

### 3.2 `decode_slice` 的返回类型：为什么先用 `DecodeSliceError`

S2 §2.4 只写了 `Result[Int, DecodeError]`，但 crate 的 `decode_slice` 返回的是
`DecodeSliceError`（2 变体：`DecodeError(e)` / `OutputSliceTooSmall`）——
输出缓冲不够**不是解码错误**，混进 `DecodeError` 会让调用方无法区分「输入坏」和「我给小了」。

**建议**：M0 就把 `DecodeSliceError` 定出来（骨架里已无此类型，本文补上），
`decode_slice` / `encode_slice` 各用各的：

- `decode_slice` → `Result[Int, DecodeSliceError]`（`{ DecodeError(DecodeError), OutputSliceTooSmall }`）
- `encode_slice` → `Result[Int, EncodeSliceError]`（`{ OutputSliceTooSmall }`）

`decode`（分配版）对 `DecodeSliceError` 做 `unreachable` 式展开——因为缓冲是按估算值分配的。

## 4. M1 —— 四条判据 + 结构化错误（可信度）

**目标**：`decode` 的语义与 crate 对齐；4 类错误可定位。**不改性能**。

### 4.1 落笔顺序（严格按此序，不许跳）

```
① 写「能红」用例 → moon test 见红（记录红在哪一行）
② 落 decode.mbt 的 4 判据（先写清楚，不优化）
③ 骨架期 warnings：移除 -6（DecodeError 变体已被构造）
④ 全量差分：与官方 core / Python base64 对拍长度 0..600
⑤ gates.sh 全绿
```

### 4.2 四条判据的规格

| # | 判据 | 错误 | 判定位置 | 现状 |
|:-:|------|------|---------|:----:|
| 1 | 输入含非字母表字节 | `InvalidByte(offset, byte)` | 每个 4 元组 decode 时 | ⚠️ 有报错，**无 offset** |
| 2 | 末尾有效符号数 `% 4 == 1` | `InvalidLength(input_index + n)` | `decode_suffix` 入口 | ❌ 缺 |
| 3 | 末符号低位冗余位非零 | `InvalidLastSymbol(offset, byte)` | `decode_suffix` 尾部 | ❌ 缺 |
| 4 | padding 不合 `padding_mode` | `InvalidPadding` / `InvalidByte` | `decode_suffix` padding 段 | ❌ 缺 |

**判据间的次序（照 crate 实测，不是猜的）**：

1. `rem == 1` 且末字节**非法且非 padding** → 先报 `InvalidByte`（**不是** `InvalidLength`）。
   这是 crate 的「用户便利」设计：`"Zm9vYmFy\n"` 报的是 `InvalidByte(8, 0x0A)` 而不是 `InvalidLength`。
2. padding 出现在**当前 4 元组的位置 0/1** → `InvalidByte(该位置, padding)`。
3. padding 之后又出现非 padding 字节 → 报**第一个** padding 的位置。
4. 以上都过了，才轮到 `padding_mode` 的三态检查，最后才是冗余位检查。

**冗余位判据的算式（照 crate `decode_suffix.rs` 实测写法，勿自行化简）**：

```
leftover_bytes = morsels_in_leftover * 6 / 8        // 2 符号→1 字节；3 符号→2 字节
leftover_num   = (m0 << 26) | (m1 << 20) | (m2 << 14) | (m3 << 8)
mask           = 0xFFFFFFFF >> (leftover_bytes * 8)
若 !allow_trailing_bits 且 (leftover_num & mask) != 0  → InvalidLastSymbol
```

> 为什么是「先拼成一个 32 位整数再统一收尾」而不是「逐符号算」：
> `Zh==` / `ZhA` 两个例子的**错误来源是同一个**——第二个符号的低 4 位被丢弃。
> 逐符号算会写出两套相似代码，而这里只写一遍，用 `mask` 表达「本不该有值的位」。

### 4.3 判据 ↔ 用例矩阵

**左半 = 现状实测**（本机 `moon 0.1.20260920`，2026-10-07 复跑，命令见 §9.2）；
**右半 = M1 目标**（错误变体照 crate `DecodeError` 语义）。

| 输入 | 现状实测 | M1 目标 | 覆盖判据 |
|------|---------|---------|:-------:|
| `""` | `Ok(len=0)` | `Ok(b"")` | 空输入边界 |
| `"Zg=="` | `Ok(len=1)` | `Ok(b"f")` | padding 正常路径 |
| `"Zg"` | `Ok(len=1)` | `Ok(b"f")`（`Indifferent` 下） | 缺 padding 容忍 |
| `"Z"` | `Ok(len=0)` ❌ | `Err(InvalidLength(1))` | 2 |
| `"Zh=="` | `Ok(len=1)` ❌ | `Err(InvalidLastSymbol(1, b'h'))` | 3 |
| `"ZhA"` | `Ok(len=2)` ❌ | `Err(InvalidLastSymbol(1, b'h'))` | 3 |
| `"Zm9vYmFy="` | `Ok(len=6)` ❌ | `Err(InvalidByte(8, b'='))` | 4（padding 后无字节） |
| `"Zm9vYg==="` | `Ok(len=4)` ❌ | `Err(InvalidByte(4, b'Y'))`¹ | 4（>2 个 padding） |
| `"=Zm9v"` | `Ok(len=0)` ❌ | `Err(InvalidByte(0, b'='))` | 4（padding 在位置 0） |
| `"Zm9v!"` | `Err(...)`（**无 offset**） | `Err(InvalidByte(4, b'!'))` | 1（**offset 必须为 4**） |
| `"Zm9vYmFy\n"` | `Err(...)`（**无 offset**） | `Err(InvalidByte(8, 0x0A))` | 1 |
| `"Zm9vYmFy=="` | `Ok(len=6)` ❌ | `Err(InvalidByte(4, b'Y'))`¹ | 4 |

> ¹ **这两格必须实测 crate 才能写死**。`"Zm9vYmFy=="` 的 4 元组从 0 起是 `Zm9v`/`YmFy`/`==`——
> 最后一个 4 元组的**位置 0 就是 padding**，crate 的 `decode_suffix` 在「padding 出现在位置 0/1」
> 分支上抛 `InvalidByte(该位置, padding)`。但 `"Zm9vYmFy=="` 的 padding **跨到了前一个 4 元组**，
> 走的是另一条分支。M1 落地前**必须**用 crate 跑一遍这两个输入、把变体与字段值抄下来，
> 不许两边都写「或」——一个断言只能有一个真值。

> **现状里已经对的两条别改坏**：`"Zm9v!"` 与 `"Zm9vYmFy\n"` 现状**已经返回 `Err`**，
> 只是错误里**没有 offset**。M1 的任务是把它们升级成带 offset 的结构化错误，
> **不是**「把漏检的补上」——别把已经对的路径写成新的回归。

### 4.4 `padding_mode` 三态的语义（照 crate `new()` 实测）

| 模式 | 语义 |
|------|------|
| `Indifferent`（**crate 的 `RequireCanonical` 之外的第二常用**） | 0~2 个 padding 都可；>2 仍错（由位置判据拦下） |
| `RequireCanonical`（**`Config::default()` 的默认值**） | `(padding_bytes + morsels) % 4 == 0` 才合法 |
| `RequireNone` | 出现任何 padding → `InvalidPadding` |

> ⚠️ **本仓库骨架 `lib/internal/config.mbt` 的注释写错了默认值**：
> 它写「padding_mode 默认 `Indifferent`」，但 crate `GeneralPurposeConfig::new()` 实测是
> **`RequireCanonical`**。M2 落地时**必须改注释与实现**，并把默认值写进 S2 §2.3 的缺口表。
> 这一条是**本次原文核对发现的**，不是转述。

### 4.5 判据（完成口径）

| 判据 | 命令 | 期望 |
|------|------|------|
| 每条判据都有「能红」的反例 | `git log -p lib/base64_test.mbt` 可见先加断言后改实现 | 两个 commit，或同一 PR 内的描述留痕 |

| `-6` 已归还 | `cat lib/internal/moon.pkg` | 不再有 `-6` |

## 6. M3 —— 引擎对象与表缓存（性能项，行为零变化）

**目标**：把 `encode_table()` / `decode_table()` 的「每调用现建」收敛到 `Engine::new` 一次。

### 6.1 动作

1. `tables.mbt`：`build_encode_table(Alphabet) -> FixedArray[Byte]`（64 项）、
   `build_decode_table(Alphabet) -> FixedArray[Int]`（256 项，非法字节 `-1`，**padding 也必须是 `-1`**）。
2. `engine.mbt`：`Engine::new(alphabet, config)` 建两张表；`Engine` 只读。
3. `encode_into` / `decode_into` 改为**收 `Engine`**（S3 已预留该形参）。
4. 外壳：按 §2.3 方案 A，每次调用建一次引擎（**明账**，不藏）。
5. **移除 `-9`**（`struct_never_constructed`）。

### 6.2 完成判据（**这是 M3 唯一可接受的验收方式**）

> **先有差分，再改实现**：`encode` / `decode` 的 M2 版输出**逐字节**是 M3 版的黄金值。

| 判据 | 命令 | 期望 |
|------|------|------|
| 输出逐字节不变 | 见 §9「M3 差分」 | 长度 0..600 全扫，两版输出完全相同 |
| 表只建一次 | 白盒用例：`Engine::new` 两次得到的两表内容相同，且 `decode_table` 中 padding 为 `-1` | 新增 `*_wbtest.mbt` |
| `-9` 已归还 | `cat lib/internal/moon.pkg` | 不含 `-9` |
| 性能不倒退 | `bash scripts/gates.sh` + §9 性能口径 | 不得比 M2 慢到噪声之外（说清是噪声） |

### 6.3 回退条件

若 M3 与 M2 在**任意长度**上出现一个字节差异，**立刻回退 M3**，把差异长度记进本文
（这是回归用例的黄金输入），不要「顺手修一下」。

## 7. M4 —— 批量内核（唯一证据充分的性能项）

**目标**：编码「3 字节 → 4 字符」、解码「4 字符 → 3 字节」展开。
S1 §6.1 实测：解码侧 **1.6–2.0×**，编码侧顺带；**不依赖 SIMD**。

### 7.1 写法规格（照 crate 0.23.1 实测形状）

| 侧 | 快循环 | 尾块 |
|----|--------|------|
| 编码 | 一次读 6 字节（`UInt64`）出 8 字符，`BLOCKS_PER_FAST_LOOP = 4` → 一次 24 字节出 32 字符 | 逐 3 字节组，最后按 `rem ∈ {1,2}` 收尾 |
| 解码 | 一次读 8 字节（`UInt64`）出 6 字节（`decode_chunk_8`），4 块 = 32 字节出 24 字节；剩余用 `decode_chunk_4`（4→3） | 最后 0~4 字节交给 `decode_suffix` |

**关键约束（照 crate，别自创）**：

1. 快循环**只吃完整的组**（编码 `%3==0`，解码 `%4==0`），最后一组**永远**留给尾块——
   它可能带 padding。
2. `decode_chunk_8` 的 `accum` **左移对齐**：`m0<<58, m1<<52, …, m7<<16`，
   然后 `accum.to_be_bytes()[..6]` 直接拷 6 字节。**不要**改写成逐字节拼装。
3. 错误 offset 一律用**绝对输入坐标**，不许用「循环内相对下标」。
4. 快循环里**不检查 padding**：padding 只可能出现在末尾，由 `decode_suffix` 全权处理。

### 7.2 完成判据

| 判据 | 命令 | 期望 |
|------|------|------|
| 与 M3 输出逐字节相同 | §9「M4 差分」 | 全长度一致 |
| 性能改善可复跑 | §9「性能」 | 解码 ≥1.5×（低于此值要写清是环境噪声还是回归） |
| 编码侧不回退 | 同上 | 编码不得慢于 M3 |
| 门禁 | `bash scripts/gates.sh` | 全绿 |

> **M4 不得与 M3 同 PR**：M3 是「实现不变、结构变」，M4 是「实现变、结构不变」。
> 混在一起时，一旦差分红了分不清是谁的锅。

## 8. M5 —— 语义矩阵（持续护栏）

**目标**：把「长度全扫 × 配置叉积」固化成测试，让后续任何改动都过一遍。

### 8.1 矩阵设计（**不是机械展开**，按独立真值点算）

| 轴 | 取值 | 独立真值点 |
|----|------|-----------|
| 输入长度 | `0..=64` 逐长度 + `{128, 129, 130, 1023, 1024, 1025, 4096}` | 72 |
| 字母表 | `Standard` / `UrlSafe` | ×2 |
| 编码 padding | `true` / `false` | ×2 |
| 解码 padding_mode | `Indifferent` / `RequireCanonical` / `RequireNone` | ×3 |
| 冗余位 | `false` / `true` | ×2 |

**判据不是「跑了多少个组合」，而是「覆盖了多少条不变量」**（AGENTS.md §三.2 铁律 6）：

1. **往返不变量**：`decode(encode(x, padding=p), mode=m) == x`（在合法组合内）；
2. **长度上界**：`encoded_len(n)` 恒 ≥ 实际输出长度，且 `< encoded_len(n) - 4` 时不成立；
3. **冗余位不变量**：把末符号替换为同值的非规范符号（如 `Zg` → `Zh`），
   `RequireCanonical` 下必错、`allow_trailing_bits=true` 下必对；
4. **padding 不变量**：`padding=false` 的输出恒 `% 4 != 0`（当 `n % 3 != 0`）。

### 8.2 与 Rust 对拍（产物不入库）

对拍对象：`rust-base64` 0.23.1（本机 clone 到 `/tmp`，**不入库**）与 Python3 `base64`。
对拍产物写入 `/tmp`，**不提交**（AGENTS.md §一）。

| 判据 | 命令 |
|------|------|
| 长度全扫对拍 | 见 §9「M5 对拍」 |
| 错误类型对拍 | 对 §4.3 的 9 条输入，逐条比对错误**变体名与字段值** |

> **对拍不通过的处置**：先怀疑**本库**。crate 的 `engine/tests.rs` 有 2182 行语义矩阵，
> 它比我们新写的用例更可能对。要推翻它，必须给出「crate 的哪条判据不符合 RFC」的明确出处。

## 9. 复跑方式（本文所有判据的命令全集）

统一前置：`export PATH="$HOME/.moon/bin:$PATH"`（或 `bash scripts/setup-moonbit.sh`）。

### 9.1 门禁与静态检查

| 结论 | 命令 |
|------|------|
| 全量门禁 | `bash scripts/gates.sh` |
| 只跑指定阶段 | `STAGES="check test" bash scripts/gates.sh` |
| 公共 API 快照 | `moon info && cat lib/pkg.generated.mbti`（**产物，勿入库**） |
| 未归还的 warnings 编号 | `cat lib/internal/moon.pkg` |
| 测试规模护栏 | `bash scripts/test-scale.sh` |

### 9.2 判据现状（M1 之前；M1 落地后这三条应改为「已具备」）

**注**：现状的 `decode` 收 `String`，M0 会改成 `BytesView`——下表按**现状签名**写，
M0 之后把 `"…"` 换成 `b"…"` 即可。

| 结论 | 命令 |
|------|------|
| 一次拿到 §4.3 全部 12 格现状值 | 在 `lib/probe_tmp_test.mbt` 写 `@lib.decode(...)` 的 `match` + `println`，`moon test` 后删（**黑盒测试必须放 `lib/` 下、文件名「非 `_test.mbt` 结尾」不生效**——放 `lib/*_test.mbt`） |
| `decode("Z")` 应为 `Err` | 在 `lib/base64_test.mbt` 加 `assert_true(@lib.decode("Z").is_err())` 后 `moon test`（**加之前先看它红**） |
| `decode("Zh==")` 应为 `Err` | 同上，替换为 `"Zh=="` |
| `decode("Zm9vYg===")` 应为 `Err` | 同上，替换为 `"Zm9vYg==="` |
| 三条一起复跑 | `bash scripts/test.sh`（复跑完删除，**勿把审计用例当正式验收**） |

> **探测文件放哪（实测踩坑）**：想临时打印 `@lib.decode(...)` 必须放在 **`lib/` 包下、名字以 `_test.mbt` 结尾**
> （黑盒）。放 `lib/internal/` 会因看不见 `lib` 报 `[4020] Package "lib" not found`；
> 名字不以 `_test.mbt` / `_wbtest.mbt` 结尾则**根本不参与编译**，`moon test` 会「全绿但没跑」。

> **写法纪律（本次修正）**：上面三条**故意只写「加什么断言」不写「打印什么值」**——
> S2 §5 早前那版写的是 `inspect(@lib.decode("Z"), content="\"?\"")`，
> 既不能在仓库外跑（`@lib` 是包别名），也不是可断言的期望。
> **复跑命令要么能在仓库根敲，要么写明「加进哪个文件的哪一行」。**

### 9.3 M3 / M4 差分（**先有黄金值再改实现**）

```bash
# 1) 在 M2 版上生成黄金值（输出写 /tmp，不入库）
export PATH="$HOME/.moon/bin:$PATH"
moon test --target wasm-gc          # 先确认 M2 版全绿
# 2) 把 lib/base64_test.mbt 里 encode/decode 的用例断言值抄成硬编码字面量
#    （长度 0..=64 全扫 + 长样本），moon test 记下红/绿
# 3) 落 M3 或 M4 的实现，重跑同一批断言：必须全绿
# 4) 有任何一条红 → 立刻回退该阶段，把差异输入记进本文 §6.3
```

> **为什么不做「跑两版自动 diff」**：MoonBit 里没有「同时装载两个版本同一个包」的机制；
> 硬做要起两个工作区。**用「M2 的输出写成字面量」当黄金值**是最省事且最不易错的做法——
> 它同时也满足 AGENTS.md §三.2 铁律 3「禁止 `actual == actual`」。
