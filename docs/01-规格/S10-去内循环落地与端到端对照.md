> **状态**：现行　｜　日期：2026-10-08　｜　索引：[docs/README.md](../README.md) §1

> 一句话结论：把 [S9 §4](S9-M5语义矩阵与32位装载裁决.md) 登记为**待独立落地**的
> 「去内循环」**落了**，并按它的落地纪律走了两步：**先差分基线，再改实现**。
> 本轮把 S9 的形态又推进一档——**判错合并 + 冷路径外提**（S9 未测），

> 少绕一圈循环很值钱」；本文给它补上落地侧的第二句——
> **「少绕一圈」的正确性，靠差分基线守；靠人看是守不住的。**

## 2. 落地纪律：先差分基线，再改实现

[S9 §4.3](S9-M5语义矩阵与32位装载裁决.md) 写了三条，本文逐条照做：

| S9 的要求 | 本文的落地 |
|-----------|-----------|
| ① 实现变更是独立 PR 的事，别与裁决篇混 | ✅ 两个提交：基线一个、实现一个（同一 PR） |
| ② 需要一个黄金值基线（把**当前输出**固化成字面量断言） | ✅ 见 §2.1 |
| ③ 补**端到端**对照（热段比值 ≠ 端到端） | ✅ 见 §4.3 |

### 2.1 差分成两层，各锁各的

| 文件 | 层 | 锁什么 | 为什么不能合一 |
|------|----|--------|---------------|
| `lib/internal/decode_differential_wbtest.mbt` | 白盒 | `decode_into` 的**判定串**（含错误变体 + offset），41 个长度逐字面量 | 内核私有；黑盒看不见，会混入 `Engine::new` 与物化 |
| `lib/base64_differential_test.mbt` | 黑盒 | 公共契约的**密集定值**：41 长度编码串 + 可解长度解码字节 | 对外面的承诺必须黑盒锁；与 encode 侧配成往返锚点 |

**与 M5 矩阵的分工**（[S9 §1.2](S9-M5语义矩阵与32位装载裁决.md)）：

- 矩阵锁的是**四条结构性不变量**（往返 / 长度 / 冗余位 / padding）+ 8 个 CPython 定值。
  它的问题在**[S9 §1.2](S9-M5语义矩阵与32位装载裁决.md) 自己写着**：不变量是「自洽式」的，
  `encode` 与 `decode` **错得一致**时会全绿；
- 本文的差分基线是**密集定值**（41 个长度），专堵「错得一致」与「只在长输入上错」。
  两者**不互相替代**，是同一张网的两层网眼。

### 2.2 黄金值出处（AGENTS.md §三.2 铁律 1）

- **全部来自 CPython `base64`**（独立参照，**不是**本库输出——铁律 3 禁 `actual == actual`）；
- 数据式子 = `det_bytes(i) = (i*37+11)&0xFF`，与 M5 矩阵**同源**（便于交叉引用）；
- 生成命令见 [§5.2](#52-黄金值生成)。

## 3. 实现形态：为什么是「合并判错 + 冷路径外提」

### 3.1 与 S9 变体 H 的差别

[S9 §3.1](S9-M5语义矩阵与32位装载裁决.md) 的变体 H 是「4 条显式 `let` + **逐符号**判错」。
本文在它之上再试了三档（探针，跑完即删）：

| 形态 | 185 KB 热段比值（vs 旧 `for k`） | 说明 |
|------|:---:|------|
| S9 变体 H：逐符号 4 个 `if` | 0.683–0.686 | S9 的形态 |
| **合并判错（`acc < 0`）+ 冷路径内联** | 0.736–0.743 | ❌ **反而更慢**：定位代码进热路径，寄存器压力吃掉收益 |
| **合并判错 + 冷路径外提**（本文采用） | **0.645–0.648** | ✅ 比变体 H 再快约 6% |
| 合并判错、**不报 offset**（仅探针，不正确） | 0.644–0.652 | 与「外提」基本同速——外提是**零成本**的 |

**结论**：把 4 个逐符号分支并成 1 个 `acc < 0` 是收益源；把定位逻辑**提出热循环**
（几乎）不花成本。两者都要。

### 3.2 合并判错的前提（这条是「承重墙」）

`acc = (b0<<18)|(b1<<12)|(b2<<6)|b3`，morsel ∈ `{-1} ∪ [0,63]`。

> **`acc < 0` ⟺ 「四个 morsel 里至少一个为 `-1`」**

成立依赖 MoonBit 的 `Int` 是 **31 位有效位 + 符号位**（见 `decode_suffix` 里 `UInt` 那条注释）：
`-1` 的位模式全 1，故任一 `b<0` 都把 `acc` 高位置 1；反向全 `[0,63]` 时 `acc ≤ 0xFFFFFF` 恒 ≥ 0。

**这条不改写成注释，改写成穷举测试**（`merged_check_equivalence_exhaustive`）：
覆盖 `(-1) ∪ [0,63]` 的全部 **65⁴ = 17 850 625** 种组合。

> **为什么不抽样**：抽样漏掉的那一格恰好是最坏情况（例如**只有 `b3` 为负**——
> 它在最低位，是「低位负值会不会被高位 0 盖掉」的那一格）。
> 注释会漂移、测试会红——这是 [S9 §1.3](S9-M5语义矩阵与32位装载裁决.md) 那类教训的又一次应用。

### 3.3 改后仍能红（AGENTS.md 铁律 5）

改实现**之后**，基线必须仍能抓错。两种注入实测：

| 注入 | 结果 |
|------|------|
| `acc = (b0<<18)|…|(b3<<1)`（末尾错位 1 位） | **9 条红** |
| 冷路径 `InvalidByte(start, …)`（offset 不加上 `k`） | **1 条红**（精确 offset 断言） |

> 只「10 条红」里那 1 条是 offset 断言抓的——**没有它，第 2 种注入会静默通过**
> （结果字节全对，只有 offset 错）。这正是 S7 §2.2「快而错没有价值」的另一面：
> 慢一点但位置准，比快一点但位置漂更有价值。

### 3.4 边界：本轮**没有**做的事

- **不改 `decode_suffix`**：尾巴那段（判据 2/3/4）本就只在末 1~4 符号上跑，不是热点；
  且它是错误语义最密的地方，动它的收益/风险比不成比例。
- **不改编码侧**：`encode_into` 已是 3 字节组展开，无内循环；
  [S7 §2.2](S7-M4性能前提复跑与裁决.md) 的 `c6`（6 字节装载）已实测为 **1.53–1.79× 慢**。
- **不碰 `UInt`/`UInt64`**：S7 §2.3 已定根因（`wasm-gc` 上装箱成本），本文全程 32 位 `Int`。

## 4. 实测

### 4.1 口径（三个不变量，缺一个数字就不可比）

照 [S7 §2.1](S7-M4性能前提复跑与裁决.md)：

1. **基准 = 手上这份代码的现状**：本文的对照是「**旧 `decode_into` 本体**」（含 `for k`）
   vs「新 `decode_into` 本体」——都**不含** `Engine::new`，故是**同层**对照；
2. **交错 A/B**：每轮同时测两版，各取 **41 轮中位数**；
3. **防 DCE**：返回值累加后读出。

尺寸 88 B / 5.4 KB / 185 KB；`wasm-gc` + `--release`；探针跑完即删（不入库）。

### 4.2 内核段（同层对照）

三次复跑，数值为 **ratio = 新 / 旧**（<1 即更快）：

| 输入 | ratio | 加速 |
|------|:-----:|:----:|
| 88 B | 0.748–0.766 | **1.31–1.34×** |
| 5.4 KB | 0.699–0.702 | **1.42–1.43×** |
| 185 KB | 0.718–0.728 | **1.37–1.39×** |

**与 S9 的对账**：S9 §3.2 报 0.71–0.75×（变体 H）。本文 0.70–0.77×，同向且**长输入更优**——
差异来自 §3.1 的「合并判错 + 冷路径外提」。

> **88 B 这次的数可以用**（与 S7 §6 的告诫不冲突）：S7 说「<1 µs 的测点不要算倍数」，
> 而本文的 88 B 测点是**每轮 2000 次循环取中位数**（单次约 0.2 µs × 2000 = 400 µs），
> 已远高于时钟分辨率与 GC 抖动。**那条告诫针对的是「单次直测」，不是「批量取中位数」。**

### 4.3 端到端（S9 §4.3 点名要补的）

**含** `Engine::new`（外壳的「每调用建一次引擎」）+ 缓冲分配 + `Bytes` 物化：

| 输入 | 外壳-equivalent ratio | 加速 |
|------|:---------------------:|:----:|
| 88 B | 0.855–0.865 | **1.16–1.17×** |
| 5.4 KB | 0.752–0.759 | **1.32–1.33×** |
| 185 KB | 0.773–0.776 | **1.29×** |

**三条读法**：

1. **端到端确实更小**（88 B 从 1.33× 缩到 1.16×）——常数项（建表 + 分配 + 物化）不随输入缩小，
   把比值往 1 拉。这正是 S9 §4.3 担心的「重犯 S6 §1 分子分母不同层」；
2. **但缩短是有限的**，5.4 KB / 185 KB 仍有 1.29–1.33×——常量项占比随尺寸下降，收益就露出来；
3. **88 B 那格最该警惕**：1.16× 的绝对值只有百来 ns 量级，**别把它当卖点**。
   引用本节的数字时，请带上尺寸。

### 4.4 正确性

| 检查 | 方法 | 结果 |
|------|------|------|
| 41 长度逐字面量 | 差分基线（§2.1） | ✅ 全等 |
| 错误 offset 逐格 | 差分基线含 `InvalidByte(offset, byte)` 断言 | ✅ 全等 |
| 合并判错等价性 | 65⁴ 穷举 | ✅ 等价 |
| 对外接口 | `moon info` 前后 `.mbti` | ✅ **无变化**（内核私有改动） |

- **这条是本文最推荐的下一步**：它不改善绝对值，但它降低「下一轮又量错」的概率——
  而本仓三次性能翻车**全部**是口径问题，不是算法问题。

**优先级 C：语义侧的剩余接口面**（与本轮性能无关，独立可做）

- crate 预置六张表（Standard / UrlSafe / Crypt / Bcrypt / IMAP-MUTF7 / BinHex）中，
  本库对外只暴露前两张（[S1 §9](S1-rust-base64-移植可行性分析.md) 的 API 兼容边界）。
  要不要补其余四张，取决于是否有真实调用方——**没有调用方之前不做**。
- `encode_slice` / `decode_slice` 已有；crate 的分块节律（`chunked_encoder` 的节律部分）
  仍挂起（[S1 §1](S1-rust-base64-移植可行性分析.md) 表中列为「可做」）。

### 6.3 不做什么（明确边界）

- **不重启 M4**：chunk 化两次被证伪。要重启，先跑 [S7 §6](S7-M4性能前提复跑与裁决.md) 拿新对照。
- **不解禁 SIMD**：M4 未交付，恢复条件未满足。
- **不把「去内循环」的收益卖给通用调用方**：端到端 88 B 只有 1.16×，
  真要吞吐的调用方该用 `decode_slice` 自持缓冲（[S6 §2.3](S6-性能实测与M3裁决.md) 的同一理由）。

## 7. 边界（本文不做什么）

- **不重述 S1–S9**：只落地 S9 的待办项 + 汇总进度，冲突时以本文实测为准。
- **不改 `decode_suffix` / 编码侧 / `UInt` 路径**：理由见 §3.4。
- **§4 的数字是同机相对量**，与 [ISSUE #3](https://cnb.cool/tryandrun/moonbit_dev/base64-moon/-/issues/3)
  的历史口径**不可混比**（S2 §5 已立此规矩）。
- **不承诺时间表**：只给顺序与判据，节奏由迭代决定。
