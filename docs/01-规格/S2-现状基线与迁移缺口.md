# S2 · 现状基线与迁移缺口

> **状态**：现行　｜　日期：2026-10-07　｜　索引：[docs/README.md](../README.md) §1

> 一句话结论：本仓库现在的 `lib/facade.mbt`（骨架期原名 `lib/base64.mbt`）是**能过 RFC 4648 §10 官方向量的骨架**，
> 但它**只覆盖了正确性判据的 1/4**——解码侧缺「末尾 2~4 符号 + padding 模式 + 冗余位」三段校验；
> 且**签名形态与移植目标不一致**（`decode` 收 `String` 而应为字节视图、错误类型是不可编程的 `String`）。
> 性能侧的真缺口是**批量内核**（解码 4 字符展开实测 1.6–2.0×），**不是**物化路径。
> 本文把每一项缺口写成**可勾选的验收项**，作为向 S1 规划的实现顺序落地的路线图。

## 2. 正确性缺口（优先级最高）

> 本章的判据全部以 [S1 §3](S1-rust-base64-移植可行性分析.md#3-逐层对照能搬什么要改什么) 的

> [S1 §9](S1-rust-base64-移植可行性分析.md#9-移植目标api-兼容的边界含-no_std)。

### 2.1 解码判据：四缺三

`general_purpose/decode_suffix.rs`（170 行）把 RFC 4648 §3.5 拆成四条判据。
逐条对照本仓库现状：

| # | 判据 | crate 的错误类型 | 本仓库 | 佐证 |
|---|------|-----------------|:------:|------|
| 1 | 输入中混入非字母表字节 | `InvalidByte(offset, byte)` | ✅ 已具备 | `lib/base64_test.mbt` 的 `decode_reports_invalid_byte_with_offset`；**实测**：`decode(b"Zm9v!")` → `Err(InvalidByte(4, b'!'))` |
| 2 | 末尾有效符号数为 1（`len % 4 == 1`） | `InvalidLength(len)` | ✅ 已具备 | **实测**：`decode(b"Z")` → `Err(InvalidLength(1))`；字段是**输入总长**（`b"AAAAZ"` → `InvalidLength(5)`） |
| 3 | 末尾符号的**低位冗余位非零** | `InvalidLastSymbol(offset, symbol)` | ✅ 已具备 | **实测**：`decode(b"Zh==")` → `Err(InvalidLastSymbol(1, b'h'))`；`allow_trailing_bits=true` 时 → `Ok(b"f")` |
| 4 | padding 数量/位置不符合 `DecodePaddingMode` | `InvalidPadding` / `InvalidByte` | ✅ 已具备 | **实测**：`decode(b"Zm9vYg===")` → `Err(InvalidByte(6, b'='))`（报**第一个** padding 的位置） |

> **为什么判据 3 重要**：`morsels_in_leftover * 6 / 8` 决定输出字节数，`mask = !0u32 >> (leftover_bytes_to_append * 8)`
> 决定「哪些位本不该有值」。没有这条检查，`Zm9vYmFy`、`Zm9vYmFy=`、`Zm9vYmFy==` 会被当成同一个东西——
> 而 RFC 恰恰要求它们可区分（crate 的 `decode_malleability_test_case_*` 系列专门测这个）。

**验收方式**：新增 `*_test.mbt`，对每条判据给出「**能红**」的反例（AGENTS.md §三.2「负向优先于正向」）。
四判据已于 M1 落地，逐格真值与 crate 对拍结论见 [S5 §2](S5-实施裁决与M1落地.md).

### 2.2 错误可定位性

当前错误类型是 `String`（`Err("invalid base64 character: !")`）——**人有得看，程序没法用**。
crate 的 `DecodeError` 携带 `offset` / `byte` / `symbol_value`，调用方能知道「第 17 个字节坏了」。

**建议形态**：`pub suberror DecodeError` + 变体携带结构化字段，`String` 只作展示（`Debug`）。
这是**对外契约变更**，按 AGENTS.md §三.2 须先体现在 `*_test.mbt`。

|------|-------|:------:|

### 2.4 签名决策：`decode` 的入参、返回与定长输出

这是 **M1 之前必须落定**的一组决策——它不改行为，但决定后续所有实现的函数签名。
依据是 [S1 §5.3](S1-rust-base64-移植可行性分析.md#53-string-是-utf-16字节与字符之间没有免费的桥) 的实测：
**MoonBit 的 `Bytes → String` 是重解释（一对字节 = 一个 code unit），不是解码**。

| 决策点 | 现状 | 目标 | 理由 |
|--------|------|------|------|
| `decode` 入参 | ~~`String`~~ → **`BytesView`**（M0 已落） | **字节视图**（`BytesView`） | 对齐 crate 的 `AsRef<[u8]>`；`String` 是 UTF-16，用它当字节源是错的前提 |
| `decode` 返回 | ~~`Result[Bytes, String]`~~ → **`Result[Bytes, DecodeError]`**（M0 已落） | **`Result[Bytes, DecodeError]`** | 对齐 crate 的 `Vec<u8>`；返回 `String` 会立刻撞上非 UTF-8 结果无法物化 |
| 定长输出 | 无 | **`decode_slice(Bytes, FixedArray[Byte]) -> Result[Int, …]`** | 对齐 crate 的 `&mut [u8] -> usize`；这是**唯一**能避开输出二次拷贝的形态 |
| `encode` 入参 | `Bytes` | `Bytes`（不变） | 已是字节视图，对齐 `AsRef<[u8]>` |

**为什么这不是「优化空间」而是「签名约束」**：crate 的 `encode_slice(input, &mut [u8]) -> usize`
之所以成立，是因为 Rust 有可直接写的 `&mut [u8]`；MoonBit 的 `FixedArray[Byte]` 能做到同等语义，
但 `decode` 返回 `Bytes` 那条路**没有**零拷贝物化（`Bytes → String` 是重解释）。
形态定不下来，M1 的 4 条判据无从落笔——**这也是「先贴判据再改代码」的原因**。

> `encode` 侧不受此约束：输出天然全 ASCII，但注意**即便如此也没有捷径**——
> [§3](#3-性能缺口) 实测「批量物化」与「逐字符」同速，所以 `encode` 走常规逐字符输出即可。

## 3. 性能缺口

**口径**：**输入字节 / 秒**，等长循环取总时长，MoonBit `0.1.20260920`、`wasm-gc`、`--release`。
旧的 [ISSUE #3 实测](https://cnb.cool/tryandrun/moonbit_dev/base64-moon/-/issues/3) 是另一套口径，两处**不可直接比较**。
本节数字的复跑方式见 [§5](#5-复跑方式)，结构性成因见 [S1 §6.1](S1-rust-base64-移植可行性分析.md#61-一处必须更正的量物化路径不是提速点)。

| # | 缺口 | 成因 | 是否真瓶颈（实测） |
|---|------|------|------|
| P1 | 表每次调用现建 | `encode_table()` / `decode_table()` 在函数体内 `FixedArray::make` | 小输入占比可见；与「引擎对象」方案二选一 |
| P2 | **批量内核缺失** | 无「4 字符 → 3 字节」/「3 字节 → 4 字符」展开 | ⚠️ **原判已修正**：「4 符号展开」的收益 M1 已兑现；其上的 chunk 化实测为负（[S7](S7-M4性能前提复跑与裁决.md)）。**真瓶颈改判为「`for k` 内循环未展开」**（[S9 §4](S9-M5语义矩阵与32位装载裁决.md)）——**已由 [S10](S10-去内循环落地与端到端对照.md) 落地**（内核 1.37× / 端到端 1.29×） |
| P3 | 逐字符物化输出 | `StringBuilder::write_char` / `Buffer::write_byte` 每单位一次调用 | ❌ **不是瓶颈**：批量物化与逐字符**同速**；换 **UTF-8 字节载体**亦**同速**（0.99–1.07×），三组独立对照见 [S11 §2.1](S11-UTF8替代UTF16的可行性裁决.md) |
| P4 | 无向量路径 | 从未尝试 `V128` | ⏸ 不进首版（用户既定约束）；且 `wasm-gc` **不会自动向量化** |

### 3.1 两条实测结论（推翻旧口径）

**① 物化路径不是提速点。** 编码侧两条路（`46 B / 4 KB / 136 KB`，MB/s）：

| 实现 | 46 B | 4 KB | 136 KB |
|---|---:|---:|---:|
| `StringBuilder::write_char` 逐字符 | 187 | 322 | 170 |
| `FixedArray[Char]` 批量 + `String::from_array` | 209 | 306 | 152 |

差异在噪声内，大输入下批量版**略慢**。原因见 [S1 §5.3](S1-rust-base64-移植可行性分析.md#53-string-是-utf-16字节与字符之间没有免费的桥)：
`String` 必须逐 code unit 落地，「定长 + 批量」省下的只是循环形态。

**② 真提速在批量内核。** 解码侧（`88 B / 5.4 KB / 185 KB` 输入，输出长度已校验一致）：

| 实现 | 88 B | 5.4 KB | 185 KB | 相对 |
|---|---:|---:|---:|---:|
| 逐字符累积 + `Buffer::write_byte`（现做法） | 275 | 433 | 298 | 1.0× |
| **4 字符 → 3 字节展开** | **550** | **728** | **488** | **1.6–2.0×** |

**顺序纪律（修正）**：`P1 → P2 → P4(搁置)`，**P3 不再是性能项而是签名项**（见 §2.4）。
早前把 P3 列为「主导项」的说法**作废**——那是把「重解释捷径」的产物长度变化误当成提速
（那条路输出长度都不同，不是同一测量对象）。

| ~~**M4**~~ ❌ | ~~**批量内核**（4 字符展开 / 4 字节展开）~~ | ~~P2~~ | **已实测证伪，不做 chunk 化**：原「1.6–2.0×」在 M1 已兑现，其上的 chunk8/chunk6 复跑为 **1.5×+ 降速**（[S7](S7-M4性能前提复跑与裁决.md)） |
| ~~**M5**~~ ✅ | 语义矩阵（长度全扫 × 配置叉积） | — | 已落：四条结构性不变量 + CPython 定值对拍，见 `lib/base64_matrix_test.mbt` 与 [S9](S9-M5语义矩阵与32位装载裁决.md) |
| — | ~~SIMD128 编码/解码路径~~ | P4 | **不进首版**（用户既定约束）。恢复条件见下 |

**M0 是前置（签名），M1–M2 是「可信度」，M3–M4 是「性能」，M5 是「持续护栏」。**
M0 / M1 / M2 / M3 / **M5** 已落地（M5 见 [S9](S9-M5语义矩阵与32位装载裁决.md)）；
**M4 经实测证伪，不做**（见上行表注与 [S7](S7-M4性能前提复跑与裁决.md)）。
**性能侧那条已落地**：「去内循环」已进 `lib/`（[S10](S10-去内循环落地与端到端对照.md)）——
内核段 1.31–1.43×、端到端 1.16–1.33×（随尺寸变化，88 B 最小）。
性能线至此收口（详见 S10 §6.1）。

> **SIMD 的恢复条件**（不是删除，是挂起）：① M4 交付且数字可复跑；② 明确需要
> `wasm-gc` 单目标下的更大吞吐；③ 接受「装载需手工拼 lane」的约束
> （[S1 §5.2](S1-rust-base64-移植可行性分析.md#52-结论有指令缺装载)）与 `@v128` 实验性告警的处置成本。
>
> **条件 ① 已更硬，不是已满足**：M4 的 chunk 化经 [S7](S7-M4性能前提复跑与裁决.md) 实测为负收益
> （1.5×+ 降速），**不构成「M4 交付」**。SIMD 仍处于挂起态，**不解禁**。
> 真要重启，先跑 S7 §6 的对照拿到新数字。
>
> **条件 ② 的判据已在新证据下重述（2026-10-08）**：[E1 §3.4](../02-证据/E1-外部对照基线与分向根因.md)
> 实测**外部对照在 wasm 上也拿不到手写向量指令**——`base64` crate 的 AVX2 引擎被
> `target_arch` 门控在 `x86_64`/`aarch64`，`wasm32` 不在名单内；给 Rust 开满 `+simd128`
> 也只换来 ~1.2–1.9×（LLVM 自动向量化），远不及 native AVX2 的 2–4×。
> 含义：**「追平 AVX2」不是本项目该设的参照系**；若真做 `@v128`，参考基准应是
> 「wasm 上各方都只能用的标量 + 有限向量化」。但这**不改变挂起结论**——
> 是否解禁仍取决于条件 ①（要有可信标量基线先收口）与真实的浏览器端吞吐需求。

## 5. 复跑方式

| 结论 | 复跑命令 |
|------|---------|
| 当前对外 API 清单 | `export PATH="$HOME/.moon/bin:$PATH" && moon info && cat lib/*.mbti`（`.mbti` 为构建产物，勿入库） |
| 当前测试规模与结果 | `bash scripts/test.sh` |
| 当前门禁是否全绿 | `bash scripts/gates.sh` |
| 判据 2：`decode(b"Z")` → `Err(InvalidLength(1))` | 正式用例 `decode_rejects_one_trailing_symbol`；复跑 `bash scripts/test.sh` |
| 判据 3：`decode(b"Zh==")` → `Err(InvalidLastSymbol(1, b'h'))` | 正式用例 `decode_rejects_nonzero_trailing_bits`；复跑同上 |
| 判据 4：`decode(b"Zm9vYg===")` → `Err(InvalidByte(6, b'='))` | 正式用例 `decode_padding_modes`；复跑同上 |
| 四判据真值表（12 格 × 三态） | 见 [S5 §2](S5-实施裁决与M1落地.md)；对拍方法见 [S6 §3](S6-性能实测与M3裁决.md) |
| 表是否每次现建 | 内核层**不再**现建（`lib/internal/engine.mbt` 持表）；外壳每调用建一次引擎，占比与裁决见 [S6 §1–§2](S6-性能实测与M3裁决.md) |
| 物化两条路是否同速（§3.1①） | 同一输入跑 `StringBuilder::write_char` 与 `FixedArray[Char]` + `String::from_array`，等长循环比对总时长 |
| 换 UTF-8 字节载体是否提速（P3 的第三组对照） | 同一输入跑「逐字符 `write_char`」与「先收 `FixedArray[Byte]` 再逐字节 `write_char`」，口径与结论见 [S11 §6.1](S11-UTF8替代UTF16的可行性裁决.md) |
| `String` 有无 UTF-8 版（换载体的前提） | 见 [S11 §2.3](S11-UTF8替代UTF16的可行性裁决.md)：core 只有 `String` / `StringView`，无 `Utf8String` |
| 批量内核的倍数（§3.1②） | 同一 base64 输入跑「逐字符累积」与「4 字符展开」，比对总时长 + 输出长度。**注意基线**：现库已是「4 符号展开」，故这条量的是「逐字符 → 4 符号」；再往上的 chunk 化见 [S7 §6](S7-M4性能前提复跑与裁决.md) |
| `Bytes → String` 是重解释（§2.4 前提） | `b"ABCDEFGH".to_unchecked_string().length()` 应为 `4`（不是 `8`） |
| 性能口径 | 统一「**输入字节 / 秒**」，`wasm-gc` + `--release` + 等长循环；两处数字不可与 ISSUE #3 口径混比 |

> **负向优先**：上表「判据 2/3/4」的正确复跑方式是**先看它变红**（AGENTS.md §三.2 铁律 5），
> 而不是直接补实现——先证明测试能抓住问题，再动代码。
