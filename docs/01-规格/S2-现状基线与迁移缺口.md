# S2 · 现状基线与迁移缺口

> **状态**：现行　｜　日期：2026-10-07　｜　索引：[docs/README.md](../README.md) §1

> 一句话结论：本仓库现在的 `lib/base64.mbt` 是**能过 RFC 4648 §10 官方向量的骨架**，
> 但它**只覆盖了正确性判据的 1/4**——解码侧缺「末尾 2~4 符号 + padding 模式 + 冗余位」三段校验，
> 性能侧缺「引擎对象 + 定长输出 + 一次性物化」，向量侧**完全没有**。
> 本文把每一项缺口写成**可勾选的验收项**，作为向 S1 规划的实现顺序落地的路线图。

## 0. 本文的作用

[S1 · rust-base64 移植至 MoonBit 的可行性分析](S1-rust-base64-移植可行性分析.md) 回答「该不该做、能做什么」；
本文回答「**现在差多少、按什么顺序补、补完怎么验**」。

- **不重复 S1 的对照分析**，只在需要时引用其章节。
- 每个缺口都给出**可复跑的验收命令**与**当前实测结果**（[§5](#5-复跑方式)）。
- 状态标记：`已具备` / `部分` / `缺失`。

## 1. 当前实现的盘点

`lib/base64.mbt` 共 124 行，对外 4 个符号：

| 符号 | 形态 | 状态 |
|------|------|:----:|
| `Alphabet`（`Standard` / `UrlSafe`） | `pub enum` | ✅ 已具备 |
| `Alphabet::standard()` / `Alphabet::url_safe()` | 构造函数 | ✅ 已具备 |
| `Alphabet::is_url_safe()` | 查询 | ✅ 已具备 |
| `encode(data, alphabet?)` | 返回 `String`，**总是带 `=`** | ⚠️ 部分 |
| `decode(text, alphabet?)` | 返回 `Result[Bytes, String]` | ⚠️ 部分 |

内部私有：`encode_table` / `decode_table`（均**每次调用现建**）、`encode` 用 `StringBuilder::write_char` 逐字符输出。

## 2. 正确性缺口（优先级最高）

### 2.1 解码判据：四缺三

`general_purpose/decode_suffix.rs`（170 行）把 RFC 4648 §3.5 拆成四条判据。
逐条对照本仓库现状：

| # | 判据 | crate 的错误类型 | 本仓库 | 佐证 |
|---|------|-----------------|:------:|------|
| 1 | 输入中混入非字母表字节 | `InvalidByte(offset, byte)` | ✅ 已具备（报字符但**无 offset**） | `lib/base64_test.mbt` 的 `"Zm9v!"` 用例 |
| 2 | 末尾有效符号数为 1（`len % 4 == 1`） | `InvalidLength(len)` | ❌ **缺失** | **实测**：`decode("Z")` → `Ok(b"")`（应为 `Err`） |
| 3 | 末尾符号的**低位冗余位非零** | `InvalidLastSymbol { offset, symbol, symbol_value }` | ❌ **缺失** | **实测**：`decode("Zh==")` → `Ok(b"f")`；`decode("ZhA")` → `Ok(b"f\x10")`（非规范编码被照收） |
| 4 | padding 数量/位置不符合 `DecodePaddingMode` | `InvalidPadding` / `InvalidByte` | ❌ **缺失** | **实测**：`decode("Zm9vYg===")` → `Ok(b"foob")`（多出的 `=` 被静默吞掉） |

> **为什么判据 3 重要**：`morsels_in_leftover * 6 / 8` 决定输出字节数，`mask = !0u32 >> (leftover_bytes_to_append * 8)`
> 决定「哪些位本不该有值」。没有这条检查，`Zm9vYmFy`、`Zm9vYmFy=`、`Zm9vYmFy==` 会被当成同一个东西——
> 而 RFC 恰恰要求它们可区分（crate 的 `decode_malleability_test_case_*` 系列专门测这个）。

**验收方式**：新增 `*_test.mbt`，对每条判据给出「**能红**」的反例（AGENTS.md §三.2「负向优先于正向」）。

### 2.2 错误可定位性

当前错误类型是 `String`（`Err("invalid base64 character: !")`）——**人有得看，程序没法用**。
crate 的 `DecodeError` 携带 `offset` / `byte` / `symbol_value`，调用方能知道「第 17 个字节坏了」。

**建议形态**：`pub suberror DecodeError` + 变体携带结构化字段，`String` 只作展示（`Debug`）。
这是**对外契约变更**，按 AGENTS.md §三.2 须先体现在 `*_test.mbt`。

### 2.3 编码侧开关

| 开关 | crate | 本仓库 |
|------|-------|:------:|
| 是否追加 `=` 填充 | `encode_padding` | ❌ 缺失（恒为 true） |
| 解码是否容忍冗余位 | `decode_allow_trailing_bits` | ❌ 缺失 |
| padding 检查强度 | `DecodePaddingMode` 三态 | ❌ 缺失 |

> 注意 URL-safe 场景**惯例无 padding**：`decode` 已能容忍缺 padding，但 `encode` 无法产出无 padding 输出，
> 这是与官方 core 的 `encode(..., padding=false)` 相比的直接功能缺口。

## 3. 性能缺口

口径：与 [ISSUE #3 实测](https://cnb.cool/tryandrun/moonbit_dev/base64-moon/-/issues/3) 同源，具体数字以该处为准，本文只列**结构性成因**。

| # | 缺口 | 成因 | 预期影响 |
|---|------|------|---------|
| P1 | 表每次调用现建 | `encode_table()` / `decode_table()` 在函数体内 `FixedArray::make` | 小输入占比高；与「引擎对象」方案二选一 |
| P2 | 逐字符物化输出 | `StringBuilder::write_char` 每个输出字符一次调用 | **主导项**：ISSUE #3 测得纯算术 0.19 ms 而全流程 4.40 ms |
| P3 | 标量逐字符循环 | 无 6 字节批量读 / 无展开 | 中等；P2 修好后才看得见 |
| P4 | 无向量路径 | 从未尝试 `V128` | 大输入的另一档，但**必须后置**（见 S1 §6） |

**顺序纪律**：`P1 → P2 → P3 → P4`。理由：P4 的收益最大但最难验，若在 P2 未修时做 P4，
等于用「物化开销占主导的基线」去衡量向量化的边际收益，**测出来的数字没有意义**。

## 4. 迁移路线图（可勾选）

| 阶段 | 内容 | 涉及缺口 | 完成判据 |
|:----:|------|---------|---------|
| **M1** | 补齐解码 4 判据 + 结构化错误 | 2.1 / 2.2 | 四条判据各有「能红」的反例用例；`moon test` 全绿 |
| **M2** | 补齐编码/解码配置开关 | 2.3 | `encode(..., padding=false)` 与 `decode(..., padding_mode=...)` 有对应用例 |
| **M3** | 引入引擎对象（表缓存）+ 定长输出 + 一次性物化 | P1 / P2 | 输出逐字节不变；性能改善另在性能篇记录 |
| **M4** | 标量内核批量读 + 展开 | P3 | 与 M3 版本逐字节相同；长度全扫差分测试 |
| **M5** | SIMD128 编码路径 | P4 | 与标量路径**逐字节差分**通过（所有长度 × 两字母表 × 两 padding） |
| **M6** | SIMD128 解码路径 | P4 | 同上；且非法输入必须回退标量报**精确 offset** |
| **M7** | 语义矩阵（长度全扫 × 配置叉积） | — | 见 [§5](#5-复跑方式) 的对拍命令 |

**M1–M2 是「可信度」，M3–M4 是「基础性能」，M5–M6 是「进阶性能」，M7 是「持续护栏」。**
只有 M1 做完，后面每一步的性能数字才值得相信——这是本文与 S1 §8 一致的核心纪律。

## 5. 复跑方式

| 结论 | 复跑命令 |
|------|---------|
| 当前对外 API 清单 | `export PATH="$HOME/.moon/bin:$PATH" && moon info && cat lib/*.mbti`（`.mbti` 为构建产物，勿入库） |
| 当前测试规模与结果 | `bash scripts/test.sh` |
| 当前门禁是否全绿 | `bash scripts/gates.sh` |
| 判据 2 现状：`decode("Z")` = `Ok(b"")` | `inspect(@lib.decode("Z"), content="\"?\"")`，应见 `Diff: -? / +Ok(b"")` |
| 判据 3 现状：`decode("Zh==")` = `Ok(b"f")` | `inspect(@lib.decode("Zh=="), content="\"?\"")`，应见 `+Ok(b"f")` |
| 判据 3 另一枚：`decode("ZhA")` = `Ok(b"f\x10")` | 同上，替换为 `"ZhA"`（输出含非 UTF-8 字节，正是 redundancy 被无检吞掉的证据） |
| 判据 4 现状：`decode("Zm9vYg===")` = `Ok(b"foob")` | `inspect(@lib.decode("Zm9vYg==="), content="\"?\"")` |
| 三条一起复跑 | 把上述三行加进 `lib/base64_test.mbt` 后 `bash scripts/test.sh`（复跑完请删除，勿把审计用例当正式验收） |
| 表是否每次现建 | 读 `lib/base64.mbt` 的 `encode_table` / `decode_table` 函数体 |
| 输出是否逐字符物化 | 读 `lib/base64.mbt` 的 `encode`，统计 `write_char` 调用点 |

> **负向优先**：上表「判据 2/3/4」的正确复跑方式是**先看它变红**（AGENTS.md §三.2 铁律 5），
> 而不是直接补实现——先证明测试能抓住问题，再动代码。
