# S12 · 编码物化路径优化：裁决与落地

> **状态**：现行　｜　日期：2026-10-15　｜　索引：[docs/README.md](../README.md) §1

> 一句话结论：外壳 `encode` 的 `StringBuilder()` **没传容量**，在「base64 输出长度
> 不是 2 的幂」这一常态下会「翻倍增长到位 + 末尾再拷一次」。补上
> `size_hint = 2 * 符号数` 后容量**恰好**等于长度，两笔账同时消掉——
> 同进程隔离 A/B 下**端到端编码 0.75–0.78×**（n≥64K，越大越省；小尺寸在噪声内）。
> 这是**一行改动**，输出逐字节不变，**已落地**（[§5](#5-落地了什么)），
> 性质是「分配策略」而非「物化方法」。
>
> **一句话方法论**：[S2 §3.1①](S2-现状基线与迁移缺口.md) 比过「批量物化 vs 逐字符」，
> 结论是两者同速；本文补上它没比的那一维——**物化给不给容量**。
> 「物化方法不省时间」不等于「物化不花钱」；钱花在**分配**上。

## 1. 结论速览

| 项 | 现状（改动前） | 本文建议 | 状态 |
|----|------|---------|:----:|
| `lib/facade.mbt` 的 `encode` 物化 | `StringBuilder()`（**默认容量 1 槽**） | `StringBuilder(size_hint = 2 * total)` | ✅ 已落地 |
| 增长次数 | `⌈log2(符号数)⌉` 次翻倍，产生成串临时数组 | **0 次** | ✅ |
| `to_string` 出口 | 容量 > 长度时**再拷一次**（`len != data.length()`） | 容量 == 长度 → **零拷贝分支** | ✅ |
| 端到端编码比值 | 1.00×（基线） | **0.75–0.78×**（n≥64K；小尺寸噪声内，见 §3.1 / §3.5） | ✅ 实测 |
| 输出 | — | **逐字节不变**（`assert_eq(encode(s), encode_old(s))`） | ✅ |

**一句话**：贵的**不是**把字节变成字符那圈循环（[S2 §3.1①](S2-现状基线与迁移缺口.md) 已证同速），
而是**没告诉 `StringBuilder` 要装多少**——它只能猜（翻倍），猜完还因「装少了」在出口再拷一次。

## 2. 根因：默认 `StringBuilder` 的两笔账

`lib/facade.mbt` 改动前的物化（`encode` 尾部）：

```moonbit
let sb = StringBuilder()          // ← 没传 size_hint
for i = 0; i < total; i = i + 1 {
  sb.write_char(out[i].to_int().unsafe_to_char())
}
sb.to_string()
```

### 2.1 第一笔：`size_hint` 是**字节**语义，不是字符数

`encoding/base64` 的 core 实现同样写 `StringBuilder(size_hint~)`，但**本库没写**。
补之前必须先认清构造器语义（`builtin/stringbuilder_buffer.mbt`，wasm-gc 上生效的实现）：

```moonbit
pub fn StringBuilder::StringBuilder(size_hint? : Int = 0) -> StringBuilder {
  let initial = if size_hint < 1 { 1 } else { (size_hint + 1) / 2 }  // ← 半
  let data : FixedArray[UInt16] = FixedArray::make(initial, 0)
  ...
}
```

内部缓冲是 `FixedArray[UInt16]`（**每槽 2 字节**），故 `size_hint` 按**字节**折算成槽位：
`槽数 = (size_hint + 1) / 2`。

- 传 `size_hint = 符号数`（core 的写法）→ 槽数 ≈ 符号数 / 2，**只装一半**，仍要增长一次；
- 传 `size_hint = 2 * 符号数` → 槽数 = 符号数，**恰好装下**。

> 这一行是本轮最容易踩错的地方：把「字符数」当 `size_hint` 直接填，会少一半容量。
> 本文的口径是 **`2 * total`**。

### 2.2 第二笔：输出长度**不是 2 的幂**

`total = (n + 2) / 3 * 4`：`n = 65536` → `total = 87384`。默认构造器从 1 槽起翻倍：
`1, 2, 4, …, 65536, 131072`。于是：

- **增长**：到 131072 才停下——中间每个旧数组都成垃圾；
- **出口再拷**：`to_string` 只在 `len == data.length()` 时零拷贝（`builtin/stringbuilder_buffer.mbt:181-193`）。
  此处 `87384 != 131072`，故**额外分配一个 87384 槽数组并拷贝**。

**一个反直觉的观测**：当 `total` 恰是 2 的幂时（如 `total = 65536`），默认路径**恰好**增长到
`data.length() == len`，白捡零拷贝分支——此时它看起来「没差」。这正是 §3.5 里
「用 2 的幂做尺寸会低估现状」的原因，也是本轮测量必须先纠正的口径。

## 3. 证据：五组交错 A/B

**口径**（缺一个数字就不可比，对齐 [bench/README §2](../../bench/README.md)）：
`wasm-gc` + `--release`；**交错** A/B；41 轮取**中位数**；结果被读回**防 DCE**；
同数据式 `det(i) = (i * k + c) & 0xFF`。工具链 `moon 0.1.20261012`。
探针为**临时文件**（跑完即删，不入库）。

### 3.1 端到端编码（改动后 vs 改动前）

`new` = 现状 `@lib.encode`（已带 `size_hint`）；`old` = 复刻的改动前形态
（建引擎 + 无容量物化，见 [§6.1](#61-端到端-ab改动后-vs-改动前)）。三次复跑：

| 输入 n | 输出符号数 | new | old | **new/old** |
|-------:|----------:|----:|----:|----------:|
| 1024 | 1368 | 2.84–2.86 µs | 3.41–3.44 µs | **0.83–0.84** |
| 8192 | 10924 | 21.08–21.24 µs | 22.88–22.96 µs | **0.92** |
| 65536 | 87384 | 207–212 µs | 317–340 µs | **0.63–0.66** |

### 3.2 跨产物同进程 A/B（`git worktree` 出改动前产物）

§3.1 的 `old` 是**同一进程里复刻的旧形态**——它回答「容量这一维值多少」，
但不包含「编译单元被重新生成」的效应。要回答「**落地这一行，产物到底快多少**」，
必须在同一进程里对**两份独立构建的产物**交错计时（口径见
[bench/README §6.6](../../bench/README.md)：双产物交错 + self 对照 + 产物对账）。

**产物对账先行**（先证明两侧在算同一件事）：

| 判据 | 结果 |
|------|------|
| 13 尺寸编码串 / 往返校验和 | pre 与 post **逐位相同** |
| `encode_slice` / `decode_slice` **函数体**（解析 wasm code section） | **逐字节相同** |
| self 对照（同一份 pre 产物两份实例） | 0.98–1.01 ⇒ 交错无系统偏差 |

**端到端 post/pre**（稳态三跑，去掉首轮冷启动）：

| 方向 | n=1024 | n=8192 | n=65536 | n=262144 |
|------|-------:|-------:|--------:|---------:|
| 编码 | 0.96–1.01 | 0.96–1.01 | **0.75–0.78** | **0.75–0.78** |
| 解码 | 0.85–0.99 | 0.85–0.88 | **0.72–0.74** | **0.74–0.76** |
| 往返 | 0.86–1.03 | 0.86–0.87 | **0.70–0.78** | **0.74–0.79** |

**三组数字为何不同，必须分清**：

| 口径 | 数字 | 它回答什么 |
|------|------|-----------|
| §3.1 同进程复刻 `old` | 0.63–0.92× | **纯容量效应**（同一编译单元内换写法） |
| §3.2 跨产物 A/B | 编码 **0.75–0.78×** | **落地这一行的产物级收益**（含编译重生成） |
| §3.2 跨产物 A/B | 解码 **0.72–0.79×** | **编译副作用，不是本文目标**（见 §3.3） |

> **小尺寸不可单独引用**：n=1024 的三跑区间横跨 1.00（0.86–1.03）——
> 容量差异被固定成本稀释。**只报 n≥64K 的四格。**

### 3.3 一个必须写清的副作用：解码为何也变快

本文**没有碰 `decode` 一行**，但跨产物 A/B 显示它也快了 **0.72–0.79×**。
把这件事随手归给「容量优化」会**高估**那一行，故定位过程与结论如下
（完整版含每步的排除对象，见 [E1 §10.7.4](../02-证据/E1-外部对照基线与分向根因.md)）：

| 步 | 动作 | 结果 |
|:-:|------|------|
| ① | 对比两侧 `decode_slice` 的 wasm 函数体 | **逐字节相同** |
| ② | 同进程只测 decode、交换加载顺序 | 比值不变（0.78× 稳定） |
| ③ | pre 产物与自身第二实例交错 | 0.98–1.01 |
| ④ | pre 源码上**只改一行注释**重编译 | 产物与 pre **md5 相同**，比值 1.00 |
| ⑤ | pre 源码上**只切 `size_hint` 一行** | decode **0.77–0.80×** |

**结论**：`size_hint` 那一行改变了整个编译单元的代码生成——harness 产物里
MoonBit 运行时的大函数被重写（某临时量槽位重编号，并插入 `i32.const 2; local.get 7; i32.mul`，
正是 `2 * total` 的乘 2）；`decode` 路径**共享**这部分运行时代码，于是**连带变快**。

> **引用纪律**：**「编码 0.75–0.78×」可归因给本文；「解码 0.78×」是编译副作用，不可。**
> 后者依赖编译器的内联/分配决策，换工具链版本可能消失（本仓「工具链不钉死」是已知取舍）。

### 3.4 物化-only（隔离内核，只换容量）

剥离 `encode` 内核，只在同一份已编码符号缓冲上物化，三个变体对照——
**`none` / `half`（`size_hint = 符号数`，core 风格）/ `exact`（`size_hint = 2 × 符号数`）**：

| 符号数 | none | half | exact | exact/none | exact/half |
|-------:|-----:|-----:|------:|-----------:|-----------:|
| 1368 | 3.55–3.73 µs | 3.11–3.45 µs | 3.52–3.60 µs | 0.95–0.99 | 1.04–1.09 |
| 10924 | 28.77–29.42 µs | 28.77–29.12 µs | 28.15–28.87 µs | 0.97–0.99 | 0.97–1.00 |
| 87384 | 392–432 µs | 273–289 µs | 263–282 µs | **0.62–0.68** | 0.93–0.98 |

三条读数：

1. **`exact` 稳定快于 `none`**（大输入 0.62–0.68×），与 §3.1 端到端同向、同量级；
2. **`half` 已能拿回大头**（`exact/half ≈ 0.93–0.98`）——它把增长从 ~17 次降到 1 次、
   且落到 `len` 后出口零拷贝；`exact` 再省掉那**最后一次重分配**；
3. **小输入上 `exact` 与 `none` 接近**（0.95–0.99×）——容量差异被固定成本稀释，
   这正是「引用数字必须带尺寸」的理由。

### 3.5 口径陷阱：用 2 的幂做尺寸会低估现状

若把尺寸选成 2 的幂（`total = 65536`），`none` 路径也会白捡零拷贝：

| total | none | exact | exact/none |
|------:|-----:|------:|-----------:|
| 65532（非 2 幂） | 259–264 µs | 207 µs | **0.78–0.80** |
| 65536（2 的幂） | 214–218 µs | 201 µs | **0.92–0.94** |

用**真实输出长度**（非 2 的幂）才是现实口径；用 2 的幂会把收益说小一半。

### 3.6 容量边界：`2*total` 是唯一的恰好点

`size_hint` 与实测 µs（n = 65536，total = 87384）：

| `size_hint` | 槽数 `(h+1)/2` | 是否恰好 | 实测 |
|------------|--------------:|:--------:|-----:|
| `2t - 1` | 87383 | 少 1 格 | 259 µs（仍要增长一次） |
| **`2t`** | **87384** | **恰好** | **263 µs** |
| `2t + 1` | 87385 | 多 1 格 | 310–322 µs（**出口再拷一次**） |
| `t` | 43692 | 一半 | 274–299 µs |
| `4t` | 174768 | 双倍 | 369 µs（多分配 + 出口再拷） |

**读法**：`2t` 是**唯一**同时免掉「增长」与「出口再拷」的点。多给一格也会掉出零拷贝分支
（`len != data.length()`），比不给还慢——**容量不是「越多越保险」，是「恰好才对」**。

## 4. 为什么其它方案不采纳

### 4.1 解码侧为何不动

同口径把 `decode` 拆成三层（`cur` = `@lib.decode`；`mat` = 分配 + `decode_slice` + `Bytes::from_array`；
`kernel` = 只 `decode_slice`；`copyOnly` = 单独那一步 `Bytes::from_array`）：

| 输入 n | cur | mat | kernel | copyOnly | 物化占比 |
|-------:|----:|----:|-------:|---------:|--------:|
| 1024 | 2.10 µs | 2.11 µs | 1.70 µs | 0.35 µs | 19.8% |
| 8192 | 14.52 µs | 14.55 µs | 12.13 µs | 2.35 µs | 16.6% |
| 65536 | 97.32 µs | 114.13 µs | 95.84 µs | 18.32 µs | 16.0% |

- 解码 **80%+ 在内核**，物化只占 **16–20%**，与编码侧 E1 的 51–72% **不同量级**；
- 唯一可省的是那一步 `Bytes::from_array` 拷贝，但它是**返回不可变、定长 `Bytes` 的代价**——
  要么换返回类型（破坏公共契约），要么走「重解释」捷径（改产物长度，见 [S2 §3.1①](S2-现状基线与迁移缺口.md) 作废的那条）。
  **代价与收益不成比例，本轮不动。**

**结论**：优化集中在**编码外壳**，且**只改容量**。

### 4.2 已评审关闭项

| 候选 | 做法 | 处置 | 依据 |
|------|------|------|------|
| A. 批量物化（`FixedArray[Char]` + `String::from_array`） | 换物化方法 | ❌ 不做 | 实测 **1.18–1.28× slower**（§6.2 探针）；且 `String::from_array` 内部仍是 `StringBuilder`，白绕一层 |
| B. `FixedArray[Byte]` → `to_unchecked_string` 重解释 | 半字节补零后当 UTF-16 直接读 | ❌ 不做 | 依赖字节序 / UTF-16 内存布局，**非类型安全**；且产物长度语义会漂（[S11 §2.3](S11-UTF8替代UTF16的可行性裁决.md)） |
| C. `@ascii.decode` 物化 | 借 core ascii 解码器 | ❌ 不做 | 探针 `0.88–1.12×`，**无稳定收益**，还多一层依赖与异常路径 |
| D. 表元素类型（`Byte`/`UInt16` 替 `Int`） | 改查表元素宽度 | ❌ 关闭 | 探针 `Int/Byte/UInt16` 比值 ≈ **1.0**（表访存非瓶颈） |
| E. 内核直接写 `UInt16`（省中间 `out`） | 把 UTF-16 语义下沉 `lib/internal` | ❌ 不做 | 违反分层：内核出参是 `FixedArray[Byte]`，对齐 Rust `&mut [u8]`（[S3](S3-架构分层与子包职责.md)） |
| F. 直接 `FixedArray[UInt16]` + `unsafe_fixedarray_uint16_to_string` | 绕开 `StringBuilder` 逐字符 | ❌ 不可做 | 该 intrinsic 在 core 是**包私有**（`fn`，非 `pub`），本包**无法引用**（实测 `The value identifier ... is unbound`） |

> **A 与本文的分工**：A 说「换个**写法**不值钱」，本文说「同一个写法，**喂对容量**很值钱」。
> 二者共同约束出唯一动作：**保持逐字符，只补 `size_hint`。**

///| 复刻改动前的 `encode` 形态（建引擎 + 无容量物化）。
fn encode_old(data : Bytes) -> String {
  let engine = @internal.Engine::new(
    @internal.Alphabet::standard(),
    @internal.Config::new(true, false, @internal.DecodePaddingMode::require_canonical()),
  )
  let view = data[:]
  let out = FixedArray::make(@internal.encoded_len(view), b'\x00')
  let written = @internal.encode_into(engine, view, out)
  let total = written + @internal.add_padding(written, engine.alphabet.padding, out)
  let sb = StringBuilder()
  for i = 0; i < total; i = i + 1 {
    sb.write_char(out[i].to_int().unsafe_to_char())
  }
  sb.to_string()
}

///|
fn probe_us(f : () -> Int, inner : Int) -> Double {
  let t0 = @bench.monotonic_clock_start()
  let mut acc = 0
  for _j = 0; _j < inner; _j = _j + 1 { acc = acc + f() }
  let us = @bench.monotonic_clock_end(t0)
  ignore(acc)
  us / inner.to_double()
}

///| 端到端 A/B + 正确性断言 + 负向（容量多一格即慢）。
test "probe_e2e_ab" {
  for n in [1024, 8192, 65536] {
    let src = Bytes::from_array(
      FixedArray::makei(n, i => ((i * 37 + 11) & 0xFF).to_byte()),
    )
    let inner = if n >= 65536 { 20 } else { 200 }
    assert_eq(encode(src), encode_old(src))       // 先证不变
    let a : Array[Double] = []
    let b : Array[Double] = []
    for r = 0; r < 41; r = r + 1 {
      if r % 2 == 0 {
        a.push(probe_us(() => encode(src).length(), inner))
        b.push(probe_us(() => encode_old(src).length(), inner))
      } else {
        b.push(probe_us(() => encode_old(src).length(), inner))
        a.push(probe_us(() => encode(src).length(), inner))
      }
    }
    a.sort(); b.sort()
    println("PROBE-E2EAB n=~\{n} new=~\{a[20]} old=~\{b[20]} ratio=~\{a[20]/b[20]}")
  }
}

## 7. 边界（本文不做什么）

- **不碰内核**（`lib/internal/*`）与解码路径（§4.1）；
- **不引入** `@ascii` / 重解释 / `UInt16` intrinsic 一类为省「方法」的改动（§4.2 A–F）；
- **不把「每调用建一次引擎」一起改**（[S6 §2](S6-性能实测与M3裁决.md) 已裁决：收益 3.9%，噪声内，不做）；
- **不动 `encode_slice` 的契约**：它是「零物化」形态，本就该由调用方自持缓冲；
- **不改公共 API**：`.mbti` 零变化是对外承诺，本文的改动在函数体内。
- **不把「解码也变快」算作本文收益**（§3.3）：那是编译副作用，换工具链可能消失。
- **不引用 n<64K 的 A/B 比值**：区间横跨 1.00，容量差异被固定成本稀释（§3.2）。
