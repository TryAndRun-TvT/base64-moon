# S11 · 「UTF-8 替代 UTF-16」的可行性裁决

> **状态**：现行　｜　日期：2026-10-13　｜　索引：[docs/README.md](../README.md) §1

> 一句话结论：**提问成立、前提要拆开、结论是「不做」——但「不做」的不是同一件事。**
> 把问题拆成三问之后，实测给出的是三个不同的答案：
> ① **编码侧**「`String` 是 UTF-16 所以物化慢」——**实测证伪**：改成 UTF-8 字节载体再物化，
> 与现在的逐 `char` 写**同速**（比值 0.99–1.07×，噪声内），因为两种载体都只是「64 个 ASCII 值
> 写进宿主缓冲」的一次循环，差别不在载体、在循环次数；
> ② **解码侧**「`String` 入参要反物化成字节」——**这里才有量级**：`@utf8.encode(String)`
> 比手写一次 ASCII 扫描慢 **1.36–2.41×**，也就是说**这条路的优化空间在「别经过 `String`」，
> 不在「换个字符串载体」**；
> ③ **「MoonBit 有没有 UTF-8 字符串」**——**没有**。`String` 就是 UTF-16，
> core 不提供 `Utf8String`；`Bytes::to_unchecked_string` 是**重解释**（实测 `"Zm9vYmFy"` 往返变 4 个字符），
> 走它就是错。**故「UTF-8 替代 UTF-16」在本项目里唯一可行的落法，是「继续把字节留在字节层」**——
> 而这正是 M0 已经做过的事（`decode` 收 `BytesView`）。

**与 rust-base64 的关系**（这是问题的起点）：crate 的 `encode` 是
`vec![0; n] → 写字节 → String::from_utf8(buf)`（实测 `src/engine/mod.rs:148`）——
它的输出载体是**字节**，`String` 只是一次**零拷贝校验**（`from_utf8` 对纯 ASCII 只验证不搬）。
**本库之所以不同，不是「选了 UTF-16」，而是「没有可零拷贝构造的 String」**（[S1 §5.3](S1-rust-base64-移植可行性分析.md)）。
这个差别**能不能消掉**，以及**消掉值多少**，就是本文要回答的。

## 1. 结论速览

| # | 提问 | 形态 | 实测 | 裁决 |
|:-:|------|------|------|:----:|
| ① | 编码输出改成「UTF-8 字节载体再物化」 | 写完 `Bytes` 再逐字节 `write_char` 进 `StringBuilder` | 与现形态**同速**（0.99–1.07×） | ❌ **不做**（无收益） |
| ② | 同上，但用「字节 → `String` 零拷贝」 | `Bytes::to_unchecked_string()` | **快** 1.22–1.33×，但**输出是错的** | ❌ **不做**（错） |
| ③ | 解码入参别经过 `String` | 现状 `decode_string` 走 `@utf8.encode` | `@utf8.encode` 本身占该路 45–62%；手写扫描快 **1.36–2.41×** | ✅ **已做**（主入口 `decode` 本来就是 `BytesView`） |
| ④ | MoonBit 换个 UTF-8 版 `String` | core 是否提供 | **不存在**；`String` 即 UTF-16，无第二个字符串类型 | 🚫 **不可做**（载体不存在） |

**一句话**：**问对了方向，但选错了杠杆。** 编码侧「载体」不是成本，循环次数才是；
解码侧的成本**恰恰来自「必须先把 UTF-16 变成字节」**——而这一格**已经被主入口绕开了**
（`decode` 收 `BytesView`）。真正剩下的优化空间是**把 `decode_string` 的转调做便宜**
（或直接劝调用方别用），**不是把 `String` 换成 UTF-8**。

## 2. 逐条实测

口径三要素（与 [S7 §2.1](S7-M4性能前提复跑与裁决.md) / [S10 §4.1](S10-去内循环落地与端到端对照.md) 同源）：

1. **同层对照**：四条路都含「建引擎 + 建输出缓冲 + 写字节」，只差**物化那一步**的形态；
2. **交错 A/B**：每轮同时测全部形态，取 **41 轮中位数**；三跑区间一并报出；
3. **防 DCE**：返回值累加进局部量后 `ignore`（否则整段被删）。

尺寸 1 KB / 8 KB / 64 KB / 256 KB；`wasm-gc` + `--release`；
探针写在 `lib/` 下（黑盒，能看见 `@lib`），**跑完即删、不入库**。

### 2.1 编码侧：载体不是成本（提问 ①② 的答案）

四条路（`n` = 输入字节数，数值 = **ns / 次**，三跑中位数）：

| 形态 | 1 KB | 8 KB | 64 KB | 256 KB |
|------|-----:|-----:|------:|-------:|
| **内核 `encode_slice`**（零物化，对照下界） | 2.63 | 18.39 | 149.50 | 695.31 |
| **现状**：`StringBuilder` 逐 `char`（UTF-16 载体） | 4.99 | 35.38 | 351.09 | 1637.90 |
| **UTF-8 字节载体** → 逐字节 `write_char` | 5.36 | 35.82 | 347.94 | 1662.63 |
| ~~UTF-8 字节载体 → `to_unchecked_string()`~~ | 6.12 | 45.30 | 429.78 | 2177.24 |

**相对现状的比值**（> 1 即更慢）：

| 形态 | 1 KB | 8 KB | 64 KB | 256 KB |
|------|:----:|:----:|:-----:|:------:|
| UTF-8 字节载体 → 逐字节写 | 1.074 | 1.013 | **0.991** | 1.015 |
| UTF-8 字节载体 → 重解释 | 1.227 | 1.281 | 1.224 | 1.329 |

**三条读法**：

1. **提问 ① 证伪**：比值在 **0.99–1.07×** 之间抖动、无尺寸趋势、跨轮区间互相包含——
   与 [S1 §6.1](S1-rust-base64-移植可行性分析.md#61-一处必须更正的量物化路径不是提速点) 「批量物化与逐字符同速」
   是**同一个结论的第三次复现**（前两次：`FixedArray[Char]`、本轮：`FixedArray[Byte]`）。
   **原因也同一个**：MoonBit 的 `String` 必须逐 code unit 落地，
   把 64 个 ASCII 值先攒在 `Byte` 数组里、再逐个搬进 `StringBuilder`，
   **只是把同一圈循环写了两遍**——载体是 `Byte` 还是 `Char` 不改变循环次数。
2. **提问 ② 不是「快」而是「错」**：`to_unchecked_string` 那条**确实更快**
   （1.22–1.33×），但它**不做 ASCII 解码**——它按「一对字节 = 一个 code unit」重解释
   （[S1 §5.3](S1-rust-base64-移植可行性分析.md#53-string-是-utf-16字节与字符之间没有免费的桥)）。
   实测：`"Zm9vYmFy"`（8 字节 ASCII）经这条路得到的是**长度 4** 的串（`"敚癶扡"` 一类的乱码），
   不是 `"Zm9vYmFy"`。**「更快」与「对」在这里不可兼得**——与 [S7 §2.2](S7-M4性能前提复跑与裁决.md)
   的 `UInt32` 变体是同一类陷阱。
3. **内核占外壳的 42–53%（64 KB 处 0.426、256 KB 处 0.425）**：即物化确实还占一半左右——
   **和 [E1 §5.1](../02-证据/E1-外部对照基线与分向根因.md) 的 51–72% 同向**（本文口径含 `Engine::new`，
   E1 那格是端到端切片，两者不是同一个分母，只作量级互校）。

> **所以本节否掉的是「换载体」，不是「优化物化」。** 物化还占一半，但**这一半不来自 UTF-16**：
> 它在「必须逐 code unit 写一遍」这件事本身。要动它，得动 `String` 的构造语义（core 的事，见 §4）。

### 2.2 解码侧：成本在「必须经过 UTF-16」，而这格已被绕开（提问 ③ 的答案）

解码输入的三种取字节方式（`n` = **原始数据**字节数，数值 = **ns / 次**，三跑中位数）：

| 形态 | 1 KB | 8 KB | 64 KB | 256 KB |
|------|-----:|-----:|------:|-------:|
| `StringBuilder` 出串 + `@utf8.encode`（**现状 `decode_string` 走这条**） | 7.97 | 60.51 | 689.53 | 2953.27 |
| `StringBuilder` 出串 + 手写一次 ASCII 扫描 | 5.81 | 46.38 | 584.09 | 2451.62 |
| **仅 `@utf8.encode`**（不含出串） | 4.26 | 30.63 | 242.76 | 1088.42 |

**读法**：

1. **`@utf8.encode` 本身就不便宜**：它是「UTF-16 → UTF-8」的通用转换
   （逐 code unit 带 `code < 0x80 / < 0x800 / 代理对` 三级分支，见 core `encoding/utf8/encode_nonjs.mbt`）。
   对我们的输入（**全是 ASCII**）而言，这些分支**一次都不会走真**，但**每次都要判**。
   手写扫描（ASCII 恒等）比它快 **1.36–2.41×**（比值随尺寸上升，64 KB/256 KB 处最明显）。
2. **但这一格不该被优化，该被绕开**：`@utf8.encode` 只在 **`decode_string`（便利形态）**
   这条路上出现。主入口 `decode` 收 `BytesView`（[S2 §2.4](S2-现状基线与迁移缺口.md) 的 M0 决策）——
   调用方本来就该自己决定字节来源，**根本不该有「String → 字节」这一步**。
3. **这正好回答了提问的原意**：如果解码入参是「UTF-16 的 `String`」，
   那这一步**必然**要付「把 UTF-16 抠成字节」的钱；**入参是字节视图，这笔钱就是 0**。

### 2.3 提问 ④：MoonBit 里有没有「UTF-8 字符串」这个物种

**没有。** 三条实测（探针 `probe_capability`，跑完即删）：

| 探针 | 结果 | 含义 |
|------|------|------|
| `"Zm9vYmFy"` → `@utf8.encode` → `to_unchecked_string()` | **`DIFFERENT`**（长度 8 → **4**） | 重解释，**不是**恒等 |
| `@utf8.decode_lossy(b"\xff\xfe\xfd").length()` | `3` | `decode_lossy` 能装任意字节，但**它是解码不是重解释**（再 `encode` 回去 ≠ 原字节） |
| core 是否导出第二个字符串类型 | `pkg.generated.mbti` 只有 `String` / `StringView` | **无 `Utf8String` / `Utf8Str` 一类** |

**结论**：在 MoonBit 里，「让 base64 的字符串载体变成 UTF-8」**没有目标物**——
不是「做了慢」，是**做不了**。唯一能表达「UTF-8 形态」的类型是 `Bytes` / `BytesView`，
而本库的**主入口本来就是它们**。

## 3. 与 rust-base64 的差别：不是「选了 UTF-16」，是「没有零拷贝构造」

这是提问的起点，值得单列。crate 的 `encode` 实测（`src/engine/mod.rs:148`）：

```rust
let encoded_size = encoded_len(input_bytes.len(), engine.config().encode_padding())?;
let mut buf = vec![0; encoded_size];            // 字节缓冲
encode_with_padding(input_bytes, &mut buf[..], engine, encoded_size);
String::from_utf8(buf).expect("Invalid UTF8")   // 只「校验」，不搬
```

关键在最后一行：`String::from_utf8(Vec<u8>)` 对**已经是合法 UTF-8 的字节**是
**复用同一块内存**（`Vec<u8>` 的 buffer 直接变成 `String` 的 buffer），
它只在「走到这一步才发现非法」时才复制/报错。base64 输出恒为 ASCII ⊂ UTF-8，
所以这一步**实际成本是一次校验扫描，不是一次拷贝**。

对照本库（[S1 §5.3](S1-rust-base64-移植可行性分析.md#53-string-是-utf-16字节与字符之间没有免费的桥)）：
MoonBit 的 `String` 是 **UTF-16**，`Bytes → String` 的两条「捷径」
（`to_unchecked_string`、`Buffer::write_bytes` + `to_string`）都是**重解释**
（一对字节 = 一个 code unit）。**重解释对 ASCII 恒错**（§2.3 第 1 行）。
唯一正确的构造是**逐 `Char` 写**——于是 Rust 那一步的「O(1) 换头」在本库变成「O(n) 重写」。

> **这才是「utf-16 vs utf-8」在本题里真正咬人的地方**：
> 不是循环体里多了几个分支，而是**丢掉了「字节缓冲直接充当字符串缓冲」这个零拷贝构造**。
> 但它**不能被「换载体」修好**（§2.1 已测：换载体同速），
> 只能被「**永不经过 String**」绕开（§2.2 已测：主入口绕开后成本为 0）。

## 4. 代价与边界：真要动这一格，动的是什么

| 路径 | 代价 | 状态 |
|------|------|:----:|
| 换 UTF-8 载体（`FixedArray[Byte]` 攒 → 逐字节写 `String`） | 与现状同速；**白改一遍** | ❌ 不做 |
| `Bytes → String` 零拷贝 | **输出错**（重解释 ASCII） | ❌ 不做 |
| `String` 换成 UTF-8 版 | **core 无此类型** | 🚫 不可做 |
| 主入口继续收 `BytesView`，把「转字节」的责任留给调用方 | **已落地**（M0）；`decode_string` 保留为便利形态并标注「非主入口」 | ✅ 现状 |
| 「`String` 构造能零拷贝接管 `Bytes`」（core 级改动） | 本库管不到；且会改变 `String` 的全局语义 | ⏸ **不可作为本库动作** |

**一条可选的收尾**（未落地，登记备选）：`decode_string` 的转调可以**绕过
`@utf8.encode` 的通用分支**，改成「先断言全 ASCII，再一次扫描」——
按 §2.2 的量级估，能省这条便利路上的 45–62%。**但这条路的收益上限被「便利形态不该被依赖」锁死**：
真要吞吐的调用方应该走 `decode`。**故本轮不做，只登记。**

> **同格上的另一条路已另行落地**：本文否掉的是「换**载体**」；物化那一半里
> 「**容量**」这一维由 [S12](S12-编码物化路径优化裁决与落地.md) 单独立篇并**已落地**
> （`size_hint = 2 × 符号数`，端到端编码 0.63–0.92×）。两篇合起来才是这一格的完整账：
> 「方法不省时间」+「容量很省钱」。

> **不做 ≠ 收益为零**：[S6 §2.3](S6-性能实测与M3裁决.md) 那条纪律在此适用——
> 「**收益已被实测证伪，所以不做**」与「**收益为零所以跳过**」必须分清。
> 本文是前者：**换载体这条路被三组对照证伪**（同速 / 错 / 无载体），不是「没想到要做」。

## 7. 负向验证（AGENTS.md §三.2 铁律 5）

**「提问 ② 更快但是错的」必须被验证为「错」**，否则本文的裁决就只是「我觉得它错」：

| 注入 | 结果 |
|------|------|
| `to_unchecked_string` 那条路的输出与逐 `char` 路比 `length()` | 实测 **4 vs 8**（`"Zm9vYmFy"`）⇒ 断言先红，故不可用 |
| 把「逐字节写」误改成「`Buffer` 攒 + 重解释」 | 上面那条断言立刻抓；`verify_roundtrip` 一类跨实现校验和也会红 |

> **这正是 [S10 §3.3](S10-去内循环落地与端到端对照.md) 那类教训的应用**：
> 「更快但错」必须用断言钉住，不能靠「读代码觉得不对」。

## 8. 边界（本文不做什么）

- **不改 `lib/` 实现**：裁决是「不做换载体」，故无生产代码改动（探针跑完即删）。
- **不重述 S1–S10**：只裁决「UTF-8 替代 UTF-16」这一问。
- **不动 `String` 的全局语义**：`String` 是 UTF-16 是 core 的决定；本文只谈**本库能不能绕开它**。
- **不承诺 `decode_string` 的优化**：§4 的「可选收尾」只登记，落地要走独立 PR 且先补负向用例。
- **§2 的数字是同机相对量**，与 [ISSUE #3](https://cnb.cool/tryandrun/moonbit_dev/base64-moon/-/issues/3)
  的历史口径**不可混比**（[S2 §5](S2-现状基线与迁移缺口.md) 已立此规矩）。
- **不解禁 SIMD**：本文与向量路径无关，既没解禁也没降门槛。
