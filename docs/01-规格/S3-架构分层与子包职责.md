# S3 · 架构分层与子包职责

> **状态**：现行　｜　日期：2026-10-07　｜　索引：[docs/README.md](../README.md) §1

> 一句话结论：本项目按**「零分配内核 + 物化外壳」**分三层——
> `lib/internal/`（slice 进 slice 出，不碰 `String`）、`lib/`（物化 + 默认引擎）、`cmd/main/`（演示宿主）。
> 分层不是审美选择，是 [S1 §9](S1-rust-base64-移植可行性分析.md#9-移植目标api-兼容的边界含-no_std) 的
> `no_std` 分档与 [S2 §2.4](S2-现状基线与迁移缺口.md#24-签名决策decode-的入参返回与定长输出) 的签名约束
> **共同逼出来的**：内核必须零分配（才能对着 Rust 的 `&mut [u8]`），外壳才能对外发 `String`。
> 本文是路径级实现规格：**每个文件放什么、为什么放这里、它的 TODO 何时兑现**。

## 0. 本文回答什么

- [S1](S1-rust-base64-移植可行性分析.md)：**该不该做、能做什么**（决策依据）。
- [S2](S2-现状基线与迁移缺口.md)：**现在差多少、按什么顺序补**（缺口与路线图 M0–M5）。
- **本文**：**代码落在哪**——目录 → 包 → 文件 → 职责 → 与 M0–M5 的对应。

三者关系：S1 给约束，S2 给顺序，本文给**落点**。三者冲突时以 S1 的实测为准。

## 1. 三层结构（为什么是三层）

```
lib/internal/   内核：BytesView → FixedArray[Byte]，零分配、零 String     ← 内核
      ↑ （可以 import）
lib/            外壳：String / Bytes 物化 API + 默认引擎                 ← 门面
      ↑ （可以 import）
cmd/main/       宿主：演示 + 往返验证，唯一 executable                    ← 宿主
```

**依赖方向单向**：`cmd/main` → `lib` → `lib/internal`。
`lib/internal` **永不**反向 import `lib`（MoonBit 禁止 import 环，AGENTS.md §二.1）。

三条硬边界，每条都有出处：

| 边界 | 内容 | 出处 |
|------|------|------|
| **内核不分配** | 内核只收发 `BytesView` / `Bytes` / `FixedArray[Byte]` | Rust 的 `encode_slice` / `decode_slice` 不受 `alloc` 门控 → [S1 §9](S1-rust-base64-移植可行性分析.md#9-移植目标api-兼容的边界含-no_std) |
| **内核不碰 `String`** | `Bytes → String` 是重解释非解码，且 `String` 是 UTF-16 | [S1 §5.3](S1-rust-base64-移植可行性分析.md#53-string-是-utf-16字节与字符之间没有免费的桥) |
| **物化只在外壳** | 逐 `Char` 写是唯一正确的 ASCII 物化路径；且它**不是**提速点 | [S1 §6.1](S1-rust-base64-移植可行性分析.md#61-一处必须更正的量物化路径不是提速点) |

> **第二层的动机别搞错**：把物化从内核挪到外壳，**不是为了变快**（实测同速），
> 而是为了**内核能对齐 Rust 的 slice 签名**。把它当性能项会得出错误结论。

## 2. `lib/internal/` —— 零分配内核

包定位于 `lib/internal/moon.pkg`。**设计原则**：一个文件 = 一个职责，
文件名即职责名，不设「入口文件」（同包共享命名空间，AGENTS.md §二.1）。

| 文件 | 职责 | 对齐 Rust | 兑现阶段 |
|------|------|-----------|:--------:|
| `alphabet.mbt` | 字母表**数据结构**（64 符号 + padding 字符） | `alphabet::Alphabet` | M3 |
| `tables.mbt` | 建两张表（64 编码表 / 256 反查表） | `const fn` 展开的预置表 | M3 |
| `config.mbt` | `Config` + `DecodePaddingMode`（编码 padding / 冗余位 / padding 强度） | `GeneralPurposeConfig` | M2 |
| `error.mbt` | `pub suberror DecodeError`（4 类可定位错误） | `DecodeError` | M1 |
| `engine.mbt` | `Engine`：**表的持有者**（建一次用多次） | `GeneralPurpose` | M3 |
| `encode.mbt` | 编码内核：`encoded_len` + `encode_into` | `encode_slice` | M1 → M4 |
| `decode.mbt` | 解码内核：`decoded_len_estimate` + `decode_into` + `decode_suffix` | `decode_slice` + `decode_suffix.rs` | M1 → M4 |

### 2.1 为什么 `error.mbt` 用 `suberror` 而不是 `enum`

`suerror` 能同时挂 `Result[_, DecodeError]` 与 `raise` 两种调用风格，且可 `derive(Debug)`
把「展示」与「契约」分开——`String` 只作展示，结构化字段才是契约
（[S2 §2.2](S2-现状基线与迁移缺口.md#22-错误可定位性)）。

### 2.2 为什么表要挂 `Engine` 而不是每次现建

MoonBit 没有 `const fn`，表只能构造期生成；每次 `encode` / `decode` 现建就是
[S2 §3 P1](S2-现状基线与迁移缺口.md#3-性能缺口) 的可测损失。`Engine` 把表缓存起来，
**纯函数外壳内部持一个默认引擎**，于是「有没有引擎」对使用者透明。

> 纪律：`Engine` **不得**做成全局可变状态——测试不得依赖执行顺序（AGENTS.md §三.2 铁律 7）。

### 2.3 骨架期的 warnings 处置（**M1–M3 落地后须逐条移除**）

骨架只定形态不写实现 → 静态分析看不到构造点，`moon check --deny-warn` 会红。
`lib/internal/moon.pkg` 里按「**逐一列出编号 + 说明为何可关**」处理，不用大范围 `-a`：

| 编号 | 告警 | 可关理由 | 移除时机 |
|:----:|------|---------|:--------:|
| `-6` | `unused_constructor` | `DecodeError` / `DecodePaddingMode` 变体待 M1/M2 构造 | M1 / M2 |
| `-9` | `struct_never_constructed` | `Alphabet` / `Config` / `Engine` 待 M3 构造 | M3 |

**纪律**：每个 TODO 兑现时，**同一 PR 内**移除对应编号。留在配置里 = 埋雷。

## 3. `lib/` —— 公共 API 外壳（facade）

| 文件 | 职责 | 可见性 |
|------|------|--------|
| `facade.mbt` | 对外 API：`Alphabet` / `encode` / `decode` + 纯函数转调内核 | 唯一 `pub` 面 |

**现状是「M0 前基线」**：`encode` / `decode` 仍自带实现（能过 RFC 4648 §10 官方向量），
按路线图逐步替换为内核调用。`lib/facade.mbt` 顶部与各 `pub fn` 的 doc comment 里
已标注 `TODO(M0..M3)`，**实现时以那些 TODO 为准**。

> **形态纪律**：新开关一律走**命名参数**（`padding?` / `padding_mode?`），
> **不要**新增 `encode_unpadded()` 这类自由函数——那会固化 rust-base64 已废弃的 8 个自由函数（[S1 §9](S1-rust-base64-移植可行性分析.md#9-移植目标api-兼容的边界含-no_std)）。

### 3.1 对外签名目标（M0 落定）

| 现签名 | 目标签名 | 理由 |
|--------|---------|------|
| `decode(String, alphabet?) -> Result[Bytes, String]` | `decode(BytesView, alphabet?, padding_mode?, allow_trailing_bits?) -> Result[Bytes, DecodeError]` | `String` 是 UTF-16；`Err(String)` 程序没法用 |
| `encode(Bytes, alphabet?) -> String` | `encode(Bytes, alphabet?, padding? : Bool = true) -> String` | URL-safe 惯例无 padding，现状做不到 |
| —（缺） | `decode_slice(BytesView, FixedArray[Byte]) -> Result[Int, DecodeError]` | 定长输出，对齐 Rust `&mut [u8] -> usize` |

`decode(String, ...)` 保留为**便利重载**（薄转调），不是主入口。

## 4. `cmd/main/` —— 演示宿主

`main.mbt` 只做一件事：**往返演示**（`@utf8.encode` → `@lib.encode` → `@lib.decode` → `@utf8.decode_lossy`）。
它是 `scripts/build-and-run.sh` 的验证对象，**不承载逻辑**——
逻辑放进来就会绕过黑盒测试面（AGENTS.md §三.2）。

## 5. 测试的落点纪律

| 载体 | 放哪 | 锁什么 |
|------|------|--------|
| `*_test.mbt` | 所属包内 | **黑盒**：只碰 `pub` API（`lib/base64_test.mbt`） |
| `*_wbtest.mbt` | 所属包内 | **白盒**：私有实现与**形态**（`lib/base64_wbtest.mbt`、`lib/internal/error_wbtest.mbt`） |
| 源码内联 `test {}` | 实现旁 | 单行不变量 |

**骨架期的白盒有个特殊职责**：M1 的几百行实现落地前，用最小的**形态护栏**把
`DecodeError` 的变体签名钉死（`lib/internal/error_wbtest.mbt`）。
否则形态被悄悄改动，差异会被实现淹没。

> 两者**不可混用**（AGENTS.md §二.1）：`*_test.mbt` 编译在包外，看不见私有符号。

## 7. 与路线图的对应（谁在哪个阶段改哪个文件）

| 阶段 | 主要落点 | 完成判据（引自 [S2 §4](S2-现状基线与迁移缺口.md#4-迁移路线图可勾选)） |
|:----:|---------|------------------------------------------------------------------|
| **M0** | `lib/facade.mbt`（签名） | 目标签名写入本文与 README；后续实现据此落笔 |
| **M1** | `internal/{error,decode}.mbt` | 四条判据各有「能红」的反例；`moon test` 全绿 |
| **M2** | `internal/config.mbt` + facade 命名参数 | `padding=false` 与 `padding_mode=...` 有对应用例 |
| **M3** | `internal/{engine,tables,alphabet}.mbt` | **输出逐字节不变**；表不再每次现建；移除 `-6-9` |
| **M4** | `internal/{encode,decode}.mbt` | 与 M3 版逐字节相同；长度全扫差分；性能另记 |
| **M5** | `lib/*_test.mbt` 扩展 | 长度全扫 × 配置叉积；与 Rust 对拍（产物不入库） |

## 8. 边界（本文不做什么）

- **不承诺时间表**：只给落点与阶段对应，节奏由迭代决定。
- **不重复 S1 / S2 的论证**：本文只做「目录 → 职责」映射，冲突时以 S1 实测为准。
- **不写实现**：骨架里所有 `abort("TODO(...)")` 的兑现顺序见 §7。
- **README 与本文的分工**：README 只给「项目结构 + 入口链」，**路径级职责表在本文**。
