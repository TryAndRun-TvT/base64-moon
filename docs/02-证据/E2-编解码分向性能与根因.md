# E2 · 编解码分向性能与差距根因（本库为何比 Rust/JS 慢）

> **状态**：现行　｜　日期：2026-10-08　｜　索引：[docs/README.md](../README.md) §1.5

> 一句话结论：[E1](E1-外部对照基线.md) 只报了**往返**（encode + decode 合成一个数），
> 掩盖了「哪条腿慢」。本次把编解码**拆开**各自计时，得到三条新事实：
> ① 本库**编码快、解码慢**（同尺寸下编码 61–113 MB/s，解码 54–88 MB/s），
> 与 [E1 §3.3](E1-外部对照基线.md) 的「解码是弱腿」同向且更直接；
> ② 与 Rust 的差距里，**内核只占一小半**——大尺寸下内核仅慢 ~2×，
> 端到端却慢 6–9×，差额几乎全部来自**外壳的 `StringBuilder` 物化**；
> ③ 因此「离 Rust 多远」的问题，**主战场不在 SIMD、不在内核**，而在**外壳的分配与物化**。
>
> **一句话方法论**：本轮的产出不是又一张表，而是把 **[E1](E1-外部对照基线.md) 的「往返单口径」
> 拆成「往返 + 编码 + 解码」三口径**，并引入**同机拆解**（e2e vs slice vs 物化）
> 定位差额来源。这与三次翻车（[S6 §1](../01-规格/S6-性能实测与M3裁决.md) /
> [S7 §6](../01-规格/S7-M4性能前提复跑与裁决.md) / [S9 §3.3](../01-规格/S9-M5语义矩阵与32位装载裁决.md)）
> 是同一类纪律：**先把口径拆到能归因，再谈快慢**。

## 0. 本文回答什么 / 与 E1 的关系

| 篇目 | 回答 |
|------|------|
| [E1](E1-外部对照基线.md) | 本库 vs 外部实现**到底快多少**（往返单口径 + 内核段 + 体积 + 稳定性） |
| **本文** | **拆到分向**：编码多快 / 解码多快；以及**差距从哪来**（内核 vs 外壳物化） |

**冲突时的优先级**：本文的数字与 [E1](E1-外部对照基线.md) **同机、同口径、同一次构建**，
两者互为交叉验证（往返 ≈ 编码 + 解码，见 §2.3）；**二者不冲突**。
跨机 / 跨次仍不可比（[E1 §6](E1-外部对照基线.md)）。

**不回答**：不给「本库很快」的结论；不承诺绝对值；不评各家 API 设计；
不重述 [E1](E1-外部对照基线.md) 已给的体积与稳定性数据。

## 1. 结论速览（三句话）

1. **编码与解码是两条不同的腿**：本库编码 61–113 MB/s、解码 54–88 MB/s，
   编码普遍快于解码 **15–30%**，且**大尺寸下解码衰减更快**（编码 113→61，
   解码 84→54）。对外引用**必须分向说**，不能只给往返。
2. **同名次、同方向**：与 [E1 §3.3](E1-外部对照基线.md) 一致——同平台比官方 core 快 3–5×，
   跨平台比 rust-base64 慢 5–9×。分向让这条结论**更硬**：它是两条腿各自成立，不是合成的假象。
3. **差距的空间分布是反直觉的**：与 Rust 的差距，**内核段只占 25–50%**，
   其余全在**外壳**（`StringBuilder` 物化 + 输出缓冲分配）。
   这意味着**下一步优化优先级应是外壳**，而非继续磨热循环（[S10](../01-规格/S10-去内循环落地与端到端对照.md) 已把内核磨到 1.37×）。

## 2. 分向实测

### 2.1 口径扩展（在 [E1 §2](E1-外部对照基线.md) 三条不变量之上）

[E1](E1-外部对照基线.md) 的「往返」把编码与解码**合成一个数**——好处是 6 家都能算，
坏处是**一条腿的差异会被另一条掩盖**。本次新增两个被测量：

| 层 | 被测量 | 参与方 | 为什么这样切 |
|----|--------|--------|-------------|
| **往返（端到端）** | 一次 encode + 一次 decode | **全部 6 家** | [E1](E1-外部对照基线.md) 已有，作为交叉验证 |
| **编码（端到端）** | 一次 encode | **全部 6 家** | 让「编码多快」成为可引用的一行 |
| **解码（端到端）** | 一次 decode | **全部 6 家** | 让「解码多快」成为可引用的一行（本库弱腿） |

**关键纪律：分向**不相减**来推往返。** 三段各自独立计时（各自预热、各自交错 A/B、各自中位数）。
理由：`encode` 与 `decode` 各自内部都有「建引擎 / 分缓冲 / 物化」，相减会把共有成本算错两次。
三者只在**量级一致性**上互校（§2.3），不互推。

### 2.2 实测（p50，ms/次；比值 = 该家 / 本库，>1 即比本库慢）

### 2.3 三条读法

1. **本库编码 > 解码**：所有尺寸下 `encode` 快于 `decode`（吞吐 61–113 vs 54–88 MB/s）。
   与 [E1 §3.3](E1-外部对照基线.md)「解码是弱腿」一致，且**分向表让这条成为直接证据**，
   不再只能从内核段间接读出。
2. **与 Rust 的差距方向一致，幅度分向**：编码慢 4.8–9.1×、解码慢 4.3–7.1×。
   解码差距**在小尺寸更大**（7.1× @1K vs 4.3× @256K），因为解码有额外的后缀判据分支。
3. **纯 JS 的对照出现「翻盘」**：`js-base64` 在 n=65536/262144 的**编码**上反超本库
   （1.06× / 0.94×）。这**不是噪声**（[E1 §3.5](E1-外部对照基线.md) 的抖动 ±10%），
   而是真实信号——恰好落在 §3 要解释的「物化成本」上：那两家 JS 的编码输出是
   **原生字符串**，没有本库这种「逐字符 `write_char`」的中间层。

> ⚠️ **必须诚实标出**：本库在**编码方向**已不是「比所有 JS 实现都快」——
> n≥64K 时 `js-base64` 反超。这与 [E1 §3.4](E1-外部对照基线.md) 的提醒同源：
> **优势随尺寸收窄，且分向后各自不同**。

### 2.4 稳定性（分向的比值区间）

与 [E1 §3.5](E1-外部对照基线.md) 同一台机、同一口径，两次独立跑的分向比值区间：

| 方向 | vs rust-base64（n=1024 / 8192 / 65536 / 262144） |
|------|--------------------------------------------------|
| 编码 | 0.21–0.21 / 0.20–0.20 / 0.15–0.15 / 0.11–0.12 |
| 解码 | 0.23–0.24 / 0.24–0.24 / 0.18–0.18 / 0.14–0.14 |

**读法**：与 Rust 的分向比值**稳定**（±5% 内，与 [E1 §3.5](E1-外部对照基线.md) 同量级）。
与 JS 的比值抖动更大（±10%），故 §2.3 第 3 条的「`js-base64` 编码反超」
在 n=65536 是**临界**（1.06×，需谨慎引用），在 n=262144 更明确（0.94×）。

## 3. 根因：差距为什么这么大

### 3.1 同机拆解（本库内部，p50，ns/次）

用一次性的白盒探针**拆开本库自己的三个层次**（探针跑完即删，复跑见 §5.1）：

| n | 端到端 encode | `encode_slice`（含输出缓冲分配） | 差额 = 物化 (`StringBuilder`) | 空调用（仅引擎构造） |
|---:|---:|---:|---:|---:|
| 1024 | 5 318 | 2 591 | **2 727（51%）** | 274 |
| 8192 | 37 566 | 18 240 | **19 326（51%）** | 200 |
| 65536 | 523 976 | 145 381 | **378 596（72%）** | 193 |

| n | 端到端 decode | `decode_slice`（含输出缓冲分配） | 差额 = 物化 (`Bytes::from_array`) |
|---:|---:|---:|---:|
| 1024 | 3 220 | 2 396 | **824（26%）** |
| 8192 | 20 712 | 17 454 | **3 258（16%）** |
| 65536 | 162 222 | 137 076 | **25 146（16%）** |

**读法（这是本文的核心）**：

- **编码的物化是主成本**：`StringBuilder` 逐字符 `write_char` 占了端到端的 **51–72%**，
  且**随尺寸放大**。内核（`encode_slice`）反而只占 28–49%。
- **解码的物化次要**：`Bytes::from_array` 只占 16–26%，解码的成本**主要在 `decode_slice`**。
  这解释了 §2.3 的第 3 条：解码不能靠省物化来救，编码可以。
- **引擎构造是常数项**：~200–274 ns/次，与尺寸无关——这正是
  [S6 §1–§2](../01-规格/S6-性能实测与M3裁决.md) 判为「复用引擎收益仅 3.9%」的同一笔账，
  本文再次确认它**不是**大头。

### 3.2 与 Rust 的距离：内核 vs 外壳

把 [E1 §3.3](E1-外部对照基线.md) 的内核段放在这张图里（内核段 = 零分配 `*_slice`）：

| n | 内核 enc (moon/rust) | 端到端 enc (moon/rust) | 内核占比 |
|---:|---:|---:|---:|
| 1024 | 2.10× | 4.80× | 44% |
| 8192 | 1.80× | 5.00× | 36% |
| 65536 | 1.84× | 6.83× | 27% |
| 262144 | 1.90× | 9.02× | 21% |

**读法**：

- **内核只慢 ~1.8–2.1×**，端到端却慢 4.8–9.0×——差额**几乎全部**是外壳（物化 + 分配 + 引擎）。
- 内核占比**随尺寸下降**（44%→21%）：大尺寸下外壳物化的绝对成本线性增长，
  而内核的相对劣势是常数。
- **结论**：要缩小与 Rust 的差距，**主战场在外壳，不在 SIMD，也不在热循环**。
  这与 [S10](../01-规格/S10-去内循环落地与端到端对照.md) 的「内核 1.37×、端到端 1.29×」
  不冲突——S10 说的是「同机自比还剩多少」，本文说的是「与 Rust 的差距在哪一段」。

### 3.3 平台税：跨平台那一档怎么理解

比 rust-base64 慢 5–9×、比 node Buffer 慢 2.3–5.6×，这部分**不全是实现问题**：

- **rust-base64 / node Buffer 没有 GC**：输入输出都是**线性内存**里的连续 `&[u8]`，
  编码输出可以**直接写进调用方缓冲**（`encode_slice`），不经过任何 GC 对象。
- **本库跑在 wasm-gc 的 GC 对象上**：`Bytes` / `FixedArray` 是 GC 数组，
  外壳每次 `encode` 都要「建引擎 → 建输出 `FixedArray` → 逐字符塞进 `StringBuilder` → 物化 `String`」。
  这几步在 Rust 侧根本不发生（`encode` 返回 `String` 也只是一次线性内存写入）。
- **可量化的部分**：§3.1 的物化差额（51–72%）正是「平台税里可优化的那一块」；
  剩下的「GC 对象访问 vs 线性内存访问」是**结构性**的，短期无解。

> **这条决定了优化路线**：外壳物化可攻（§4），GC 对象访问不可攻（至少不在本库层面）。

## 4. 差距归因小结与下一步

| 段 | 本库 vs Rust | 可攻性 | 依据 |
|----|-------------|--------|------|
| **外壳 · 编码物化**（`StringBuilder`） | **这里是最大单点**，占端到端 51–72% | ✅ 可攻 | §3.1 |
| **外壳 · 输出缓冲分配** | 每次 `FixedArray::make` | ✅ 部分可攻（复用缓冲） | §3.1 的 slice 差额 |
| **外壳 · 引擎构造** | ~200 ns 常数项 | ⚠️ 收益小（3.9%，[S6 §2](../01-规格/S6-性能实测与M3裁决.md)） | [S6](../01-规格/S6-性能实测与M3裁决.md) |
| **内核 · 热循环** | 1.8–2.1× | ⚠️ 已磨过（[S10](../01-规格/S10-去内循环落地与端到端对照.md) 1.37×） | [E1 §3.3](E1-外部对照基线.md) |
| **内核 · 后缀判据（解码）** | 解码差距更大 | ✅ 可攻（判据分支） | §2.3 第 2 条 |
| **平台 · GC 对象访问** | 结构性 | ❌ 不可攻（本库层面） | §3.3 |

**下一步（按 ROI 排序，均**未**落地，仅登记）**：

1. **编码外壳物化**：`StringBuilder` 逐字符 `write_char` → 是否有批量写入路径？
   （待查 core 的 `StringBuilder` API；若无，考虑一次性构造。）
2. **解码后缀判据**：`decode_suffix` 的分支能否在热路径前移或合并。
3. **输出缓冲复用**：`encode_slice` / `decode_slice` 已在，外壳可提供「自持缓冲」形态。

> 本文**不实现**上述任一项：它们是独立立项（各自需口径 + 负向验证），
> 本文只负责**把「该攻哪里」变成有数据支撑的结论**。

## 6. 边界（本文不做什么）

- **不承诺绝对值**：全部是**同机相对量**；跨机 / 跨次无效（[E1 §6](E1-外部对照基线.md)）。
- **不与 [ISSUE #3](https://cnb.cool/tryandrun/moonbit_dev/base64-moon/-/issues/3) 混比**：
  那是同机自比口径（[S2 §5](../01-规格/S2-现状基线与迁移缺口.md)）。
- **分向不相减**：三段独立计时、只量级互校（§2.1）。
- **不实现任何优化**：§4 的三条只是**登记**，各自需独立立项。
- **不重述 E1**：体积、稳定性、负向验证见 [E1](E1-外部对照基线.md) §3.4/§3.5/§5。
- **不动 `lib/` 一行代码**：探针跑完即删，`.mbti` 不变（§5.2）。
