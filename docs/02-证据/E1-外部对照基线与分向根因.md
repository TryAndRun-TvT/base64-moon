# E1 · 外部对照基线 · 分向实测 · 差距根因

> **状态**：现行　｜　日期：2026-10-08　｜　索引：[docs/README.md](../README.md) §1.5

> 一句话结论：本库在 **wasm-gc 同平台**上比 MoonBit 官方 core 快 3–5×，
> 但比 **rust-base64 慢 6–9×**。而这一档差距**不是「对方用了 SIMD」**——
> 实测证明对照表里**每一家都是标量实现**（0 条 SIMD 指令），
> 差距来自**内存模型**（GC 对象 vs 线性内存）与**外壳物化**（编码占端到端 51–72%）。
>
> 本文合并原 **E1（往返基线）** 与 **E2（分向与根因）**：两者同机、同口径、同一次构建，
> 拆开来读会各自缺一半——E1 的「往返」掩盖了「哪条腿慢」，E2 的「根因」需要 E1 的往返数做分母。
> 合并后单篇给全：**往返 → 分向 → SIMD 裁决 → 根因 → 失败与负向**。

> **本章程承重的一句**：任何「谁比谁快」的结论，都必须同时报出**各方的 SIMD 启用状态**
> （§3.4）与**差距落在哪一段**（§5）。缺任一条，都可以被读成错误的东西。

**冲突时的优先级**：本文 > S10 > S9 > S7 > S6 > S5 > S4 > S3 > S2 > S1。
**但有一条例外**：本文的数字是**同机相对量**，与各规格篇的「本库 vs 本库旧版」比值
**不同量纲，不可互推**（[S2 §5](../01-规格/S2-现状基线与迁移缺口.md) 已立此规矩）。

**不回答**：不重述任何规格篇的裁决；不承诺与其它机器的可比性；不评各家 API 设计。

## 1. 结论速览（四句话，必须一起引用）

1. **同平台是本库名次最好的地方**：wasm-gc 上比官方 core 快 **3.3–5.1×**。
   这条**能作为对外口径**，与 [S9 §3.2](../01-规格/S9-M5语义矩阵与32位装载裁决.md) /
   [S10 §4](../01-规格/S10-去内循环落地与端到端对照.md) 同向。
2. **跨平台差一个档，但这一档里没有 SIMD**：rust-base64 快 5–7×，而**实测双方都是标量**
   （§3.4）。故差距只能归到**内存模型 + 外壳**，**不能**写成「它用了向量指令」（这是原 E1 的口径错误，本次更正）。
3. **本库编码 > 解码，但两条腿都要单独引用**：编码 61–113 MB/s、解码 54–88 MB/s；
   编码普遍快 15–30%，且**解码差距随尺寸扩大**（对 Rust 从 4.3× 到 7.7×）。
4. **和纯 JS 是同一档**：比 base64-js 快 1.1–1.8×、比 js-base64 快 1.3–1.9×——
   优势真实但不大，且**编码方向 n≥64K 时 js-base64 反超**（§4.2），**别把「比所有 JS 都快」当卖点**。

## 2. 口径：三条不变量 + 六条纪律

数字要可比，先要「各家在算同一件事」。这一步由**跨实现校验和逐位对账**兜住（§6），
不是口头约定。计时侧照 §2.2 的六条纪律。

### 2.1 被测量与层（分子分母同层）

| 层 | 被测量 | 参与方 | 为什么这样切 |
|----|--------|--------|-------------|
| **往返（端到端）** | 一次 encode + 一次 decode | **全部 6 家** | 各家**都有**这一层，是唯一能横向比的层 |
| **编码（端到端）** | 一次 encode | **全部 6 家** | 让「编码多快」成为可引用的一行 |
| **解码（端到端）** | 一次 decode | **全部 6 家** | 让「解码多快」成为可引用的一行（本库弱腿） |
| **内核段** | `encode_slice` / `decode_slice`（零分配） | 仅 base64-moon / rust-base64 | JS 与 core **没有**这一层，比了就是不同层 |

> **分向不相减**：三段各自独立计时（各自预热、各自交错、各自中位数）。
> 理由：`encode` 与 `decode` 各自都含「建引擎 / 分缓冲 / 物化」，相减会把共有常数项算错两次。
> 三者只在**量级一致性**上互校，不互推。

> **分子分母同层**（[S7 §2.1](../01-规格/S7-M4性能前提复跑与裁决.md) 要素 ①）：
> 不是选「更公平」的层，是**选双方都有**的层。

### 2.2 六条纪律（防的是哪次翻车）

| # | 纪律 | 防的是 |
|:-:|------|--------|
| ① | **数据在被测侧生成**（同 seed 派生） | 跨语言对比的头号假象：比数据搬运 |
| ② | **计时器唯一**（Node `hrtime.bigint`） | 各家 bench 框架计时精度不同 |
| ③ | **交错 A/B + 中位数 + min/p50/max** | [S7](../01-规格/S7-M4性能前提复跑与裁决.md) 的 0.78× 跨轮漂移 |
| ④ | **防 DCE**：结果必须被读回 | [S6 §6.1](../01-规格/S6-性能实测与M3裁决.md) 的「整段被删掉」 |
| ⑤ | **报告必带尺寸 + 平台限定** | [S2 §5](../01-规格/S2-现状基线与迁移缺口.md) 的「不可混比」 |
| ⑥ | **报告各方 SIMD 启用状态**（§3.4） | 把「对方用没用向量指令」记混 ⇒ 可攻差距被说成结构性差距 |

**①为什么是承重墙**：`wasm-gc` 的 `Bytes` 是 GC 数组、**没有线性内存指针**，
无法从 Node 灌入大 buffer；唯一干净的做法是**让被测侧按同一 seed 自己造**。
各侧都实现同一式子，于是「输入相同」**可验证**，不只是约定。

**③为什么必须交错**：不交错就会把「前 10 秒机器凉、后 10 秒机器热」记成实现差异。
实测最大跨轮漂移（`max/min`）见 §4.4——单次直测确实不可用。

**⑥为什么是本次新增**：原 E1 把跨平台差距写成「那两家没有 GC、走线性内存 **+ SIMD**」，
但**实测 rust-base64 在这一轮里没有任何 SIMD 指令**（§3.4）。
把「用了向量」记成「没用」会让结论偏向「追不上」；反之则会掩盖真实的可攻空间。
故 SIMD 状态必须像尺寸一样**每次随表报出**。

## 3. 实测（往返）

### 3.1 一致性校验（先证明各家在算同一件事）

13 个尺寸 × **6 家实现**，编码串校验和 + 往返校验和**全部逐位相同**：

```
  n       编码串校验和          往返校验和
  0       0               0
  1       294             18
  1024    116950          130560
  65536   7478038         8355840
  ✅ 13 个尺寸 × 6 家实现，校验和全部一致
```

> 这一步不是仪式：它**已经真抓到一个 bug**——JS 侧把
> `new Uint8Array(str, "base64")` 的第二个参数当成了编码（实为 **length**），
> 结果解码长度恒为 0。这类错误在单实现自测里**测不出来**（它自洽），
> 只有跨实现校验和能抓。取证见 §7.3。

### 3.2 往返耗时（全部 6 家，统一口径）

`ms/次`；`ratio` = 该家 p50 / base64-moon p50（**>1 即比本库慢**）；
`MB/s` 按**单向**计（往返耗时里含 encode + decode 两遍）。

| 实现 | 层 | n=1024 | n=8192 | n=65536 | n=262144 |
|------|:--:|---:|---:|---:|---:|
| **base64-moon（本库）** | wasm-gc | 0.0089ms / 1.00× | 0.0579ms / 1.00× | 0.632ms / 1.00× | 3.251ms / 1.00× |
| moonbit-core（官方） | wasm-gc | 0.0311ms / **3.49×** | 0.242ms / **4.18×** | 2.081ms / **3.29×** | 8.582ms / **2.64×** |
| rust-base64 0.23.1 | wasm32 | 0.0018ms / **0.20×** | 0.0142ms / **0.25×** | 0.114ms / **0.18×** | 0.455ms / **0.14×** |
| node Buffer | native | 0.0026ms / **0.30×** | 0.0150ms / **0.26×** | 0.115ms / **0.18×** | 0.704ms / **0.22×** |
| base64-js | JS | 0.0132ms / 1.48× | 0.103ms / 1.77× | 0.854ms / 1.35× | 3.549ms / 1.09× |
| js-base64 | JS | 0.0158ms / 1.78× | 0.0760ms / 1.31× | 1.226ms / 1.94× | 5.277ms / 1.62× |

**三条读法**（**必须一起引用**）：

1. **同平台赢**：比官方 core 快 3.3–4.2×。这是「本库在同语言生态内的位置」。
2. **跨平台慢**：rust-base64 快 5–7×、node Buffer 快 4.5–7×。**这是平台税**——
   那两家没有 GC、走**线性内存**，本库跑在 wasm-gc 的 GC 对象上。
   > ⚠️ **本次更正**：这一档里**没有 SIMD 的成分**——实测 rust-base64 侧 0 条 SIMD 指令（§3.4）。
   > 旧版写的「线性内存 + SIMD」中，**「+ SIMD」对 rust-base64 不成立**（node Buffer 另说，见 §3.4）。
3. **纯 JS 同档**：1.1–1.9×。优势真实但不大，且**大尺寸下收窄到 1.1×**。

> ⚠️ **本库略慢于 base64-js 的一格不存在**，但**接近**——
> n=262144 时只有 1.09×（三次独立跑 1.084–1.103）。**这个位置必须诚实标出**：
> 说「本库比所有 JS 实现都快」在 n=1K~8K 成立，在 n=256K 已接近噪声。

### 3.3 内核段（仅 base64-moon vs rust-base64，同层）

两侧都调各自的**零分配内核入口**（`*_slice`），`ratio` = moon / rust：

| 方向 | n=1024 | n=8192 | n=65536 | n=262144 |
|------|-------:|-------:|--------:|---------:|
| 编码 `encode_slice` | 3.30× | 2.33× | 2.32× | 3.08× |
| 解码 `decode_slice` | 5.09× | 4.20× | 6.34× | 7.66× |

**读法**：**解码是弱腿**（5–7.7× vs Rust；编码只 2.3–3.3×），且**随尺寸扩大而变差**。
这与 [S10 §6.1](../01-规格/S10-去内循环落地与端到端对照.md) 的「性能线到此可以收口」**不冲突**：
S10 说的是「同机自比的优化空间」收口，本文说的是「与 Rust 的绝对差距」仍大。
**两者是不同问题**——前者是「还能不能更快」，后者是「离别人多远」。

### 3.4 SIMD 启用裁决（**本次新增，也是本轮的核心澄清**）

**问题**：对照表里 rust-base64 快 6–9×。这差距是不是因为**它用了向量指令**？

**答案**：**不是。这一轮的每一家都是标量实现。** 证据是**可复跑、可复算**的产物检查。

**判据**：解析各自 wasm 产物的 code section，数 `0xFD`（SIMD 指令族前缀）指令。
标量实现不会产生该前缀。工具：`bench/simd-probe.mjs`（本次新增，已并入 `bench.sh` ③.5 段）。

| 实现 | 产物 | `0xFD` 指令数 | 判定 |
|------|------|:---:|------|
| **base64-moon**（本库 harness） | wasm-gc | **0** | 标量——本库从不自动向量化（[S1 §5.1](../01-规格/S1-rust-base64-移植可行性分析.md)） |
| **rust-base64 0.23.1** | wasm32-unknown-unknown | **0** | 标量——两条门都不满足，见下 |

**Rust 侧为什么是 0**（**两条独立的门**，任一不满足即标量）：

| # | 门 | 实测 | 来源 |
|:-:|----|------|------|
| 1 | **目标特性门**：`wasm32-unknown-unknown` 默认不开 `simd128` | `rustc --print cfg --target wasm32-unknown-unknown` **无** `target_feature="simd128"`；显式 `-C target-feature=+simd128` 才有 | 本机实测 |
| 2 | **crate 引擎门**：`base64` 的 AVX2/NEON 内核被 `target_arch` 门控 | 门是 `#[cfg(all(feature="simd-unsafe", any(target_arch="x86_64", all(target_arch="aarch64", target_feature="neon"))))]`——**`wasm32` 不在名单里** | `base64-0.23.1/src/engine/mod.rs:46` |

> 注：`base64` 的 `default = ["std", "simd-unsafe"]`，故 `simd-unsafe` **是开的**；
> 但第二条门的 `target_arch` 判断把 `wasm32` 挡在门外——**开了特性也没有 wasm 向量内核可调**。
> 即：Rust 侧即便开 `+simd128`，也只能靠 **LLVM 对标量内核做自动向量化**，而非调用 AVX2 引擎。

**对照实验（本机，同机隔离）**：把同一份 `base64 =0.23.1` 分别编成三种形态，
测「SIMD 到底值多少」：

| 形态 | `0xFD` 指令数 | 相对标量加速（编码/解码） | 说明 |
|------|:---:|:---:|------|
| wasm32 **默认**（= 本表口径） | 0 | 1.00× | 纯标量 |
| wasm32 **`+simd128`** | 27–89 | **~1.2–1.9×** | LLVM 自动向量化标量内核 |
| **native x86_64，`Simd`/AVX2 引擎** | （native，不产 wasm） | **~1.9–2.5×（编码）/ 2.3–4.0×（解码）** | 真正调 `_mm256_*` |

**三条结论（这才是「平台税」该有的写法）**：

1. **本表的 rust-base64 是标量**，所以那一档差距**与 SIMD 无关**——
   它是「GC 对象 vs 线性内存 + 外壳」的差距。旧文档的「+ SIMD」是**误归因**，本版更正。
2. **即便给 Rust 开满 wasm 原生向量化（`+simd128`）**，也只能拿到 ~1.2–1.9×——
   因为 `base64` **没有 wasm 向量内核**，只有 LLVM 自动向量化。
   **这恰好回应用户的问题**：浏览器端 wasm 只能用 wasm 原生向量化，
   而 rust-base64 在这条路上**没有手写 SIMD 可享受**。
3. **真正的 AVX2 引擎（native）值 ~2–4×**，但它是 `x86_64` 专属，**wasm 侧拿不到**。
   所以「把 AVX2 的距离」当成「本项目要追的距离」是**错的参照系**——
   正确的参照系是 **wasm 上各方都只能用的标量 + 有限向量化**，而那正是 §3.2/§4 的表。

> **对项目目标的直接含义**：本项目要做的是**浏览器端 wasm 的原生向量化（`@v128`）**。
> 既然外部对照在 wasm 上也拿不到手写 SIMD，**本库若落地 `@v128`，反而可能在 wasm 上取得
> 对外部对照的向量化优势**——但这是**未落地的方向**（[S2 §4](../01-规格/S2-现状基线与迁移缺口.md)
> 的 SIMD 恢复条件仍挂起），**本轮只登记，不实现**。

**复跑**：

```bash
node bench/simd-probe.mjs                    # 探默认产物（本表口径）
# 对照：给 Rust 开 simd128，看 0xFD 从 0 变多少
cd bench/rust && RUSTFLAGS="-C target-feature=+simd128" \
  cargo build --release --target wasm32-unknown-unknown
cd - && node bench/simd-probe.mjs rust/target/wasm32-unknown-unknown/release/base64_bench_rust.wasm
# native AVX2 对照（需 gcc）：见 §8.2
```

### 4.2 三条读法

1. **本库编码 > 解码**：所有尺寸下 `encode` 快于 `decode`（吞吐 61–113 vs 54–88 MB/s）。
   与 §3.3「解码是弱腿」一致，且**分向表让这条成为直接证据**，不再只能从内核段间接读出。
2. **与 Rust 的差距方向一致，幅度分向**：编码慢 4.8–9.1×、解码慢 4.3–7.1×。
   解码差距**在小尺寸更大**（7.1× @1K vs 4.3× @256K），因为解码有额外的后缀判据分支。
3. **纯 JS 的对照出现「翻盘」**：`js-base64` 在 n=65536/262144 的**编码**上反超本库
   （1.06× / 0.94×）。这**不是噪声**（§4.4 的抖动 ±10%），而是真实信号——
   恰好落在 §5 要解释的「物化成本」上：那两家 JS 的编码输出是**原生字符串**，
   没有本库这种「逐字符 `write_char`」的中间层。

> ⚠️ **必须诚实标出**：本库在**编码方向**已不是「比所有 JS 实现都快」——
> n≥64K 时 `js-base64` 反超。这与 §3.2 的提醒同源：
> **优势随尺寸收窄，且分向后各自不同**。

### 4.3 分向的比值区间（稳定性）

两次独立跑的分向比值区间（与 §3.2 同一台机、同一口径）：

| 方向 | vs rust-base64（n=1024 / 8192 / 65536 / 262144） |
|------|--------------------------------------------------|
| 编码 | 0.21–0.21 / 0.20–0.20 / 0.15–0.15 / 0.11–0.12 |
| 解码 | 0.23–0.24 / 0.24–0.24 / 0.18–0.18 / 0.14–0.14 |

**读法**：与 Rust 的分向比值**稳定**（±5% 内）。与 JS 的比值抖动更大（±10%），
故 §4.2 第 3 条的「`js-base64` 编码反超」在 n=65536 是**临界**（1.06×，需谨慎引用），
在 n=262144 更明确（0.94×）。

### 4.4 稳定性（三次独立跑，往返）

`ratio` 的三次独立跑区间（**同一台机、同一口径**）：

| 实现 | n=1024 | n=8192 | n=65536 | n=262144 |
|------|--------|--------|---------|----------|
| moonbit-core | 3.465–3.498 | 4.083–4.139 | 3.135–3.293 | 2.627–2.664 |
| rust-base64 | 0.201–0.202 | 0.240–0.242 | 0.170–0.179 | 0.139–0.142 |
| base64-js | 1.484–1.593 | 1.778–1.824 | 1.304–1.365 | 1.084–1.103 |
| js-base64 | 1.752–1.778 | 1.339–1.369 | 1.811–1.900 | 1.598–1.618 |
| node Buffer | 0.293–0.345 | 0.291–0.296 | 0.196–0.209 | 0.205–0.219 |

**读法**：与 core、Rust 的比值**稳定**（±5% 内）；与 JS 的比值抖动较大
（±10%，因为两边都在 JS 引擎里、受 JIT 影响）。
**单轮 `max/min` 漂移最高 3.02×**（n=1024 的 node Buffer）——
这就是为什么必须报 min/p50/max 三值、且**单次直测不可用**。

## 5. 根因：差距为什么这么大

### 5.1 同机拆解（本库内部，p50，ns/次）

用一次性的白盒探针**拆开本库自己的三个层次**（探针跑完即删，复跑见 §7.2）：

| n | 端到端 encode | `encode_slice`（含输出缓冲分配） | 差额 = 物化 (`StringBuilder`) | 空调用（仅引擎构造） |
|---:|---:|---:|---:|---:|
| 1024 | 5 318 | 2 591 | **2 727（51%）** | 274 |
| 8192 | 37 566 | 18 240 | **19 326（51%）** | 200 |
| 65536 | 523 976 | 145 381 | **378 596（72%）** | 193 |

| n | 端到端 decode | `decode_slice`（含输出缓冲分配） | 差额 = 物化 (`Bytes::from_array`) |
|---:|---:|---:|---:|
| 1024 | 3 220 | 2 396 | **824（26%）** |
| 8192 | 20 712 | 17 454 | **3 258（16%）** |
| 65536 | 162 222 | 137 076 | **25 146（16%）** |

**读法（这是本文的核心）**：

- **编码的物化是主成本**：`StringBuilder` 逐字符 `write_char` 占了端到端的 **51–72%**，
  且**随尺寸放大**。内核（`encode_slice`）反而只占 28–49%。
- **解码的物化次要**：`Bytes::from_array` 只占 16–26%，解码的成本**主要在 `decode_slice`**。
  这解释了 §4.2 的第 2 条：解码不能靠省物化来救，编码可以。
- **引擎构造是常数项**：~200–274 ns/次，与尺寸无关——这正是
  [S6 §1–§2](../01-规格/S6-性能实测与M3裁决.md) 判为「复用引擎收益仅 3.9%」的同一笔账，
  本文再次确认它**不是**大头。

### 5.2 与 Rust 的距离：内核 vs 外壳

把 §3.3 的内核段放在这张图里（内核段 = 零分配 `*_slice`）：

| n | 内核 enc (moon/rust) | 端到端 enc (moon/rust) | 内核占比 |
|---:|---:|---:|---:|
| 1024 | 2.10× | 4.80× | 44% |
| 8192 | 1.80× | 5.00× | 36% |
| 65536 | 1.84× | 6.83× | 27% |
| 262144 | 1.90× | 9.02× | 21% |

**读法**：

- **内核只慢 ~1.8–2.1×**，端到端却慢 4.8–9.0×——差额**几乎全部**是外壳（物化 + 分配 + 引擎）。
- 内核占比**随尺寸下降**（44%→21%）：大尺寸下外壳物化的绝对成本线性增长，
  而内核的相对劣势是常数。
- **结论**：要缩小与 Rust 的差距，**主战场在外壳**——而 §3.4 已证明**不在 SIMD**
  （各方都是标量），也不在热循环（[S10](../01-规格/S10-去内循环落地与端到端对照.md) 已磨到 1.37×）。

### 5.3 平台税：跨平台那一档怎么理解

比 rust-base64 慢 5–9×、比 node Buffer 慢 2.3–5.6×，这部分**不全是实现问题**：

- **rust-base64 / node Buffer 没有 GC**：输入输出都是**线性内存**里的连续 `&[u8]`，
  编码输出可以**直接写进调用方缓冲**（`encode_slice`），不经过任何 GC 对象。
- **本库跑在 wasm-gc 的 GC 对象上**：`Bytes` / `FixedArray` 是 GC 数组，
  外壳每次 `encode` 都要「建引擎 → 建输出 `FixedArray` → 逐字符塞进 `StringBuilder` → 物化 `String`」。
  这几步在 Rust 侧根本不发生（`encode` 返回 `String` 也只是一次线性内存写入）。
- **可量化的部分**：§5.1 的物化差额（51–72%）正是「平台税里可优化的那一块」；
  剩下的「GC 对象访问 vs 线性内存访问」是**结构性**的，短期无解。
- **不含 SIMD**：§3.4 已证各方都是标量。**旧版把「+ SIMD」算进平台税是错的**，本版已更正。

> **这条决定了优化路线**：外壳物化可攻（§6），GC 对象访问不可攻（至少不在本库层面），
> **SIMD 是另一条独立的路（要手写 `@v128`）**，不在「缩小与 Rust 差距」这条线上。

## 6. 差距归因小结与下一步

| 段 | 本库 vs Rust | 可攻性 | 依据 |
|----|-------------|--------|------|
| **外壳 · 编码物化**（`StringBuilder`） | **这里是最大单点**，占端到端 51–72% | ✅ 可攻 | §5.1 |
| **外壳 · 输出缓冲分配** | 每次 `FixedArray::make` | ✅ 部分可攻（复用缓冲） | §5.1 的 slice 差额 |
| **外壳 · 引擎构造** | ~200 ns 常数项 | ⚠️ 收益小（3.9%，[S6 §2](../01-规格/S6-性能实测与M3裁决.md)） | [S6](../01-规格/S6-性能实测与M3裁决.md) |
| **内核 · 热循环** | 1.8–2.1× | ⚠️ 已磨过（[S10](../01-规格/S10-去内循环落地与端到端对照.md) 1.37×） | §3.3 |
| **内核 · 后缀判据（解码）** | 解码差距更大 | ✅ 可攻（判据分支） | §4.2 |
| **平台 · GC 对象访问** | 结构性 | ❌ 不可攻（本库层面） | §5.3 |
| **平台 · SIMD** | **各方都是标量**（§3.4） | ⏸ 挂起（独立路线，非「追 Rust」） | §3.4 |

**下一步（按 ROI 排序，均**未**落地，仅登记）**：

1. **编码外壳物化**：`StringBuilder` 逐字符 `write_char` → 是否有批量写入路径？
   （待查 core 的 `StringBuilder` API；若无，考虑一次性构造。）
2. **解码后缀判据**：`decode_suffix` 的分支能否在热路径前移或合并。
3. **输出缓冲复用**：`encode_slice` / `decode_slice` 已在，外壳可提供「自持缓冲」形态。
4. **wasm 原生向量化（`@v128`）**：独立立项，**恢复条件见 [S2 §4](../01-规格/S2-现状基线与迁移缺口.md)**，
   本轮**不触发**（§3.4 第 3 条的意图是「参照系校准」，不是「现在就做」）。

> 本文**不实现**上述任一项：它们是独立立项（各自需口径 + 负向验证），
> 本文只负责**把「该攻哪里」变成有数据支撑的结论**。

## 8. 负向验证与对照实验（AGENTS.md §三.2 铁律 5）

### 8.1 框架自身能红（两种注入）

**注入一：实现算错（Rust 侧）**——把 `verify_encode` 的编码首字符替换掉：

```
   · n=1 编码串校验和：rust-base64=290 ≠ base64-moon=294
   · n=1024 编码串校验和：rust-base64=116946 ≠ base64-moon=116950
   · n=65536 编码串校验和：rust-base64=7478034 ≠ base64-moon=7478038
```

→ **13 条红**，直指 `rust-base64`；`bench.sh` 退出码 **1**。改回即绿。

**注入二：两侧输入不同（MoonBit 侧）**——把本库 harness 的数据式改成 `(i*37+11+seed+1)`：

```
   · n=65536 编码串校验和：rust-base64=7478038 ≠ base64-moon=7478197
   · n=65536 编码串校验和：base64-js=7478038 ≠ base64-moon=7478197
```

→ 红，且**四家一起指认 `base64-moon` 是离群者**。这类「只改了自己一侧」的
假象最难自察（每一家自测都绿），只有跨实现对账能定位。改回即绿。

**意外收获：JS 侧真实 bug**——`new Uint8Array(base64Str, "base64")` 的第二个形参是
**length**（不是编码），故那行静默产出长度 0 的数组。**单实现自测测不出**（自洽），
首次跑一致性校验时立刻暴露。已在 `bench/js/impls.mjs` 就地标注该坑。

### 8.2 SIMD 对照实验（§3.4 的表）

给 Rust 侧开满 wasm 原生向量化，验证「它不是 SIMD 赢的」：

```bash
# ① 本表口径（标量）—— 探针应报 0
cd bench/rust && cargo build --release --target wasm32-unknown-unknown
cd - && node bench/simd-probe.mjs

# ② +simd128（浏览器 wasm 的向量化上限）—— 探针应报 >0，但加速仅 ~1.2–1.9×
cd bench/rust && RUSTFLAGS="-C target-feature=+simd128" \
  cargo build --release --target wasm32-unknown-unknown
cd - && node bench/simd-probe.mjs rust/target/wasm32-unknown-unknown/release/base64_bench_rust.wasm

# ③ native AVX2（真正的 Simd 引擎）—— 需 gcc；证明「真正的向量差价」在此档，且 wasm 拿不到
#    （最小复现：base64 =0.23.1 同时用 STANDARD 与 Simd::standard，native x86_64 比）
```

**判定**：① 报 0 ⇒ 本表是「标量 vs 标量」；② 报 >0 但加速有限 ⇒ 开特性也追不回「AVX2 的距离」；
③ 证明 AVX2 值 2–4× 但属 `x86_64` 专属。**三条合起来**支撑 §3.4 的口径更正。

## 9. 边界（本文不做什么）

- **不承诺绝对值**：全部是**同机相对量**；跨机 / 跨次对比无效。
- **不与 [ISSUE #3](https://cnb.cool/tryandrun/moonbit_dev/base64-moon/-/issues/3) 混比**：
  那是既有的同机自比口径（[S2 §5](../01-规格/S2-现状基线与迁移缺口.md)）。
- **分向不相减**：三段独立计时、只量级互校（§2.1）。
- **不做 `native` 后端进主表**：[AGENTS.md §二.3](https://cnb.cool/tryandrun/moonbit_dev/base64-moon/-/blob/main/AGENTS.md) 明确 native 不得进门禁；
  且 native 与 wasm-gc 内存模型不同，混进同一张表会破坏纪律 ②。
  （§3.4/§8.2 的 native AVX2 是**对照实验**，不是主表行。）
- **不自动剔除离群点**：min/p50/max 三值原样报出，剔除是读数字的人的判断。
- **不给「本库很快」的结论**：见 §1——四句话必须一起引用。
- **不实现任何优化**：§6 的四条只是**登记**，各自需独立立项。
- **不动 `lib/` 一行代码**：本轮只加装置与证据，`.mbti` 不变。
