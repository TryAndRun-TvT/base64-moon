# E1 · 外部对照基线 · 分向实测 · 差距根因

> **状态**：现行　｜　日期：2026-10-15　｜　索引：[docs/README.md](../README.md) §1.5

> 一句话结论：本库在 **wasm-gc 同平台**上比 MoonBit 官方 core 快 3.4–4.5×、
> 比第三方 `gmlewis/base64` 快 3.6–4.2×，但比 **rust-base64 慢 4.3–5.9×**。

> 实测证明对照表里**每一家都是标量实现**（0 条 SIMD 指令），
> 差距来自**内存模型**（GC 对象 vs 线性内存）与**外壳物化**（S12 前编码占端到端 51–72%，
> 其中「容量」那一笔已攻下，见 §10.7）。
> **本文数字分四轮**：前三轮 `lib/` 在 S12 之前，第四轮（2026-10-15）起 `lib/` 已变，
> **绝对值不可跨轮混引**（§2.3 / §10.7）。
>
> 本文合并原 **E1（往返基线）** 与 **E2（分向与根因）**：两者同机、同口径、同一次构建，
> 拆开来读会各自缺一半——E1 的「往返」掩盖了「哪条腿慢」，E2 的「根因」需要 E1 的往返数做分母。
> 合并后单篇给全：**往返 → 分向 → SIMD 裁决 → 根因 → 失败与负向**。

> **本章程承重的一句**：任何「谁比谁快」的结论，都必须同时报出**各方的 SIMD 启用状态**
> （§3.4）与**差距落在哪一段**（§5）。缺任一条，都可以被读成错误的东西。
> **2026-10-15 补一条**：还必须报出**「被测量是哪一轮的 `lib/`」**——
> 第四轮起 `lib/` 已带 S12 改动，拿它的绝对值去对前三轮是把两次不同的测量当成一次。

## 1. 结论速览（五句话，必须一起引用）

1. **同平台是本库名次最好的地方**：wasm-gc 上比官方 core 快 **3.4–4.5×**。
   这条**能作为对外口径**，与 [S9 §3.2](../01-规格/S9-M5语义矩阵与32位装载裁决.md) /
   [S10 §4](../01-规格/S10-去内循环落地与端到端对照.md) 同向。
   **S12 落地后这一档反而拉大**（同门没有这笔容量账可省）。
2. **跨平台差一个档，但这一档里没有 SIMD**：rust-base64 快 4.3–5.9×，而**实测双方都是标量**
   （§3.4）。故差距只能归到**内存模型 + 外壳**，**不能**写成「它用了向量指令」（这是原 E1 的口径错误，已更正）。
   **S12 后这一档收窄**（前三轮 5–7×）——可攻的那部分削掉了一截（§10.7）。
3. **本库编码 > 解码，但两条腿都要单独引用**：编码 85–116 MB/s、解码 67–94 MB/s；
   编码普遍快 20–30%，且**解码差距随尺寸扩大**（对 Rust 从 4.0× 到 5.9×）。
4. **和纯 JS 不是全面优势，编码方向已落后**：比 base64-js 快 1.35–1.73×（往返），
   但 `js-base64` 在**编码分向 n≥8192 全面反超**（1.31–1.55×，§4.2）。
   **别把「比所有 JS 都快」当卖点**——本库的优势位置在**同语言生态内**。
5. **同平台同门，本库领先第三方 MoonBit 实现**：比 `gmlewis/base64`（mooncakes 上
   独立发布的 Go 移植版）快 **3.6–4.2×**（往返），编码 2.4–2.6× / 解码 3.7–4.0×；
   且它**更胖**（体积增量 17.98 KB vs 本库 5.23 KB，3.4×）。这是同语言生态内**第二个**可比对手（§3.5）。

> **复跑可核**：以上五句经**三次复跑**（换机 2026-10-11 / 加对照 2026-10-12 / 被测量变更 2026-10-15）
> 验证——七家比值**全部同向**（§10 / §10.7.2）。
> 故结论对换机稳健；但**绝对值不可跨轮跨机引用**（本文一律是同机相对量，且第四轮起 `lib/` 已变）。

## 2. 口径：三条不变量 + 七条纪律

数字要可比，先要「各家在算同一件事」。这一步由**跨实现校验和逐位对账**兜住（§6），
不是口头约定。计时侧照 §2.2 的七条纪律。

### 2.1 被测量与层（分子分母同层）

| 层 | 被测量 | 参与方 | 为什么这样切 |
|----|--------|--------|-------------|
| **往返（端到端）** | 一次 encode + 一次 decode | **全部 7 家** | 各家**都有**这一层，是唯一能横向比的层 |
| **编码（端到端）** | 一次 encode | **全部 7 家** | 让「编码多快」成为可引用的一行 |
| **解码（端到端）** | 一次 decode | **全部 7 家** | 让「解码多快」成为可引用的一行（本库弱腿） |
| **内核段** | `encode_slice` / `decode_slice`（零分配） | 仅 base64-moon / rust-base64 | JS 与 core **没有**这一层，比了就是不同层 |

> **分向不相减**：三段各自独立计时（各自预热、各自交错、各自中位数）。
> 理由：`encode` 与 `decode` 各自都含「建引擎 / 分缓冲 / 物化」，相减会把共有常数项算错两次。
> 三者只在**量级一致性**上互校，不互推。

> **分子分母同层**（[S7 §2.1](../01-规格/S7-M4性能前提复跑与裁决.md) 要素 ①）：
> 不是选「更公平」的层，是**选双方都有**的层。

### 2.2 七条纪律（防的是哪次翻车）

| # | 纪律 | 防的是 |
|:-:|------|--------|
| ① | **数据在被测侧生成**（同 seed 派生） | 跨语言对比的头号假象：比数据搬运 |
| ② | **计时器唯一**（Node `hrtime.bigint`） | 各家 bench 框架计时精度不同 |
| ③ | **交错 A/B + 中位数 + min/p50/max** | [S7](../01-规格/S7-M4性能前提复跑与裁决.md) 的 0.78× 跨轮漂移 |
| ④ | **防 DCE**：结果必须被读回 | [S6 §6.1](../01-规格/S6-性能实测与M3裁决.md) 的「整段被删掉」 |
| ⑤ | **报告必带尺寸 + 平台限定** | [S2 §5](../01-规格/S2-现状基线与迁移缺口.md) 的「不可混比」 |
| ⑥ | **报告各方 SIMD 启用状态**（§3.4） | 把「对方用没用向量指令」记混 ⇒ 可攻差距被说成结构性差距 |

**①为什么是承重墙**：`wasm-gc` 的 `Bytes` 是 GC 数组、**没有线性内存指针**，
无法从 Node 灌入大 buffer；唯一干净的做法是**让被测侧按同一 seed 自己造**。
各侧都实现同一式子，于是「输入相同」**可验证**，不只是约定。

**③为什么必须交错**：不交错就会把「前 10 秒机器凉、后 10 秒机器热」记成实现差异。
实测最大跨轮漂移（`max/min`）见 §4.4——单次直测确实不可用。
**⑦（2026-10-15 补）比「改动前 vs 改动后」必须同进程双产物交错 + self 对照**：
只跑一份产物的 `bench.sh` 看不到副作用，单次直测又会把副作用记成漂移（§10.7.4）。

## 3. 实测（往返）

### 3.1 一致性校验（先证明各家在算同一件事）

13 个尺寸 × **7 家实现**，编码串校验和 + 往返校验和**全部逐位相同**：

```
  n       编码串校验和          往返校验和
  0       0               0
  1       294             18
  1024    116950          130560
  65536   7478038         8355840
  ✅ 13 个尺寸 × 7 家实现，校验和全部一致
```

> 这一步不是仪式：它**已经真抓到一个 bug**——JS 侧把
> `new Uint8Array(str, "base64")` 的第二个参数当成了编码（实为 **length**），
> 结果解码长度恒为 0。这类错误在单实现自测里**测不出来**（它自洽），
> 只有跨实现校验和能抓。取证见 §7.3。

### 3.2 往返耗时（全部 7 家，统一口径）

`ms/次`；`ratio` = 该家 p50 / base64-moon p50（**>1 即比本库慢**）；
`MB/s` 按**单向**计（往返耗时里含 encode + decode 两遍）。
下表为 **2026-10-12 轮次**（含新增的 `gmlewis/base64`），三次独立跑取中位数。

| 实现 | 层 | n=1024 | n=8192 | n=65536 | n=262144 |
|------|:--:|---:|---:|---:|---:|
| **base64-moon（本库）** | wasm-gc | 0.0123ms / 1.00× | 0.0845ms / 1.00× | 0.745ms / 1.00× | 3.884ms / 1.00× |
| moonbit-core（官方） | wasm-gc | 0.0482ms / **3.93×** | 0.376ms / **4.45×** | 3.199ms / **4.29×** | 13.107ms / **3.37×** |
| gmlewis/base64（第三方） | wasm-gc | 0.0454ms / **3.70×** | 0.348ms / **4.12×** | 3.118ms / **4.19×** | 13.633ms / **3.51×** |
| rust-base64 0.23.1 | wasm32 | 0.0027ms / **0.22×** | 0.0209ms / **0.25×** | 0.168ms / **0.23×** | 0.673ms / **0.17×** |
| node Buffer | native | 0.0041ms / **0.34×** | 0.0226ms / **0.27×** | 0.160ms / **0.21×** | 0.906ms / **0.23×** |
| base64-js | JS | 0.0212ms / 1.73× | 0.155ms / 1.84× | 1.290ms / 1.73× | 5.262ms / 1.35× |
| js-base64 | JS | 0.0248ms / 2.02× | 0.128ms / 1.52× | 1.810ms / 2.43× | 7.651ms / 1.97× |

（三跑中位数；绝对值见 §10.7。**与前三轮不可混引**——`lib/` 已带 S12 改动，见 §2.3。）

**三条读法**（**必须一起引用**）：

1. **同平台赢，且赢两门**：比官方 core 快 3.4–4.5×、比第三方 `gmlewis/base64` 快 3.7–4.2×。
   这是「本库在同语言生态内的位置」——**唯一带 GC 运行时的对照组**（§3.5）。
   **S12 落地后这一档反而拉大**（前三轮 3.3–4.2× → 本轮 3.4–4.5×）：同门没有这一笔容量账可省。
2. **跨平台慢**：rust-base64 快 4.3–5.9×、node Buffer 快 3.0–4.5×。**这是平台税**——
   那两家没有 GC、走**线性内存**，本库跑在 wasm-gc 的 GC 对象上。
   > ⚠️ **本轮更正**：这一档里**没有 SIMD 的成分**——实测 rust-base64 侧 0 条 SIMD 指令（§3.4）。
   > 旧版写的「线性内存 + SIMD」中，**「+ SIMD」对 rust-base64 不成立**（node Buffer 另说，见 §3.4）。
   > **S12 后这一档收窄**（前三轮 5–7× → 本轮 4.3–5.9×）：可攻的那部分被削掉了一截（§10.7）。
3. **纯 JS 同档，但已不是全面领先**：1.35–2.43×，且**大尺寸下 `js-base64` 反超的缺口拉大**
   （n=262144 往返 1.97×、n=65536 往返 2.43×；编码分向见 §4.2）。

> ⚠️ **「本库比所有 JS 实现都快」本轮不成立**：n=65536 / n=262144 上
> `js-base64` 往返已到 **2.43× / 1.97×**（前三轮 1.91× / 1.55×）——
> 差距不是收窄而是**拉大**了。**这个位置必须诚实标出**：
> 本库在**同语言生态内**领先（core / gmlewis），在**纯 JS 面前不占全面优势**。
> 根因不在内核而在物化：JS 那两家的编码输出是原生字符串（§5.1）。

### 3.3 内核段（仅 base64-moon vs rust-base64，同层）

两侧都调各自的**零分配内核入口**（`*_slice`），`ratio` = moon / rust
（**2026-10-12 轮次**，三次独立跑取中位数；只在本库与 Rust 之间比——JS/core/gmlewis 没有这一层）：

| 方向 | n=1024 | n=8192 | n=65536 | n=262144 |
|------|-------:|-------:|--------:|---------:|
| 编码 `encode_slice` | 3.16× | 2.09× | 2.07× | 2.90× |
| 解码 `decode_slice` | 4.70× | 4.24× | 4.89× | 5.51× |

**读法**：**解码仍是弱腿**（4.7–5.5× vs Rust；编码 2.1–3.2×），且**大尺寸下更差**。
**内核段与 `lib/` 改动无关**：S12 只动外壳物化，`*_slice` 的函数体在改动前后**逐字节相同**
（§10.7 的产物对账），故本表的跨轮变化只来自同机漂移。
这与 [S10 §6.1](../01-规格/S10-去内循环落地与端到端对照.md) 的「性能线到此可以收口」**不冲突**：
S10 说的是「同机自比的优化空间」收口，本文说的是「与 Rust 的绝对差距」仍大。
**两者是不同问题**——前者是「还能不能更快」，后者是「离别人多远」。

### 3.4 SIMD 启用裁决（本文的核心澄清）

**问题**：对照表里 rust-base64 快 5–9×。这差距是不是因为**它用了向量指令**？

**答案**：**不是。这一轮的每一家都是标量实现。** 证据是**可复跑、可复算**的产物检查。

**判据**：解析各自 wasm 产物的 code section，数 `0xFD`（SIMD 指令族前缀）指令。
标量实现不会产生该前缀。工具：`bench/simd-probe.mjs`（本次新增，已并入 `bench.sh` ③.5 段）。

| 实现 | 产物 | `0xFD` 指令数 | 判定 |
|------|------|:---:|------|
| **MoonBit 侧三家**（本库 + core + gmlewis harness） | wasm-gc | **0** | 标量——三家**共用一个产物**，合计 0；本库从不自动向量化（[S1 §5.1](../01-规格/S1-rust-base64-移植可行性分析.md)） |
| **rust-base64 0.23.1** | wasm32-unknown-unknown | **0** | 标量——两条门都不满足，见下 |

**Rust 侧为什么是 0**（**两条独立的门**，任一不满足即标量）：

| # | 门 | 实测 | 来源 |
|:-:|----|------|------|
| 1 | **目标特性门**：`wasm32-unknown-unknown` 默认不开 `simd128` | `rustc --print cfg --target wasm32-unknown-unknown` **无** `target_feature="simd128"`；显式 `-C target-feature=+simd128` 才有 | 本机实测 |
| 2 | **crate 引擎门**：`base64` 的 AVX2/NEON 内核被 `target_arch` 门控 | 门是 `#[cfg(all(feature="simd-unsafe", any(target_arch="x86_64", all(target_arch="aarch64", target_feature="neon"))))]`——**`wasm32` 不在名单里** | `base64-0.23.1/src/engine/mod.rs:46` |

> 注：`base64` 的 `default = ["std", "simd-unsafe"]`，故 `simd-unsafe` **是开的**；
> 但第二条门的 `target_arch` 判断把 `wasm32` 挡在门外——**开了特性也没有 wasm 向量内核可调**。
> 即：Rust 侧即便开 `+simd128`，也只能靠 **LLVM 对标量内核做自动向量化**，而非调用 AVX2 引擎。

**对照实验（本机，同机隔离）**：把同一份 `base64 =0.23.1` 分别编成三种形态，
测「SIMD 到底值多少」：

| 形态 | `0xFD` 指令数 | 相对标量加速（编码/解码） | 说明 |
|------|:---:|:---:|------|
| wasm32 **默认**（= 本表口径） | 0 | 1.00× | 纯标量 |
| wasm32 **`+simd128`** | 27–89 | **~1.2–1.9×** | LLVM 自动向量化标量内核 |
| **native x86_64，`Simd`/AVX2 引擎** | （native，不产 wasm） | **~1.9–2.5×（编码）/ 2.3–4.0×（解码）** | 真正调 `_mm256_*` |

**三条结论（这才是「平台税」该有的写法）**：

1. **本表的 rust-base64 是标量**，所以那一档差距**与 SIMD 无关**——
   它是「GC 对象 vs 线性内存 + 外壳」的差距。旧文档的「+ SIMD」是**误归因**，本版更正。
2. **即便给 Rust 开满 wasm 原生向量化（`+simd128`）**，也只能拿到 ~1.2–1.9×——
   因为 `base64` **没有 wasm 向量内核**，只有 LLVM 自动向量化。
   **这恰好回应用户的问题**：浏览器端 wasm 只能用 wasm 原生向量化，
   而 rust-base64 在这条路上**没有手写 SIMD 可享受**。
3. **真正的 AVX2 引擎（native）值 ~2–4×**，但它是 `x86_64` 专属，**wasm 侧拿不到**。
   所以「把 AVX2 的距离」当成「本项目要追的距离」是**错的参照系**——
   正确的参照系是 **wasm 上各方都只能用的标量 + 有限向量化**，而那正是 §3.2/§4 的表。

> **对项目目标的直接含义**：本项目要做的是**浏览器端 wasm 的原生向量化（`@v128`）**。
> 外部对照在 wasm 上同样拿不到手写 SIMD，故**本库若落地 `@v128`，反而可能在 wasm 上取得
> 对外部对照的向量化优势**——但这是**未落地的方向**（恢复条件见
> [S2 §4](../01-规格/S2-现状基线与迁移缺口.md)，仍挂起），**只登记，不实现**。

**复跑**：

```bash
node bench/simd-probe.mjs                    # 探默认产物（本表口径）
# 对照：给 Rust 开 simd128，看 0xFD 从 0 变多少
cd bench/rust && RUSTFLAGS="-C target-feature=+simd128" \
  cargo build --release --target wasm32-unknown-unknown
cd - && node bench/simd-probe.mjs rust/target/wasm32-unknown-unknown/release/base64_bench_rust.wasm
# native AVX2 对照（需 gcc）：见 §8.2
```

### 3.5 第三方 MoonBit 同行：`gmlewis/base64@0.16.13`（新增对照）

**为什么加这一家**：本文原有的同平台对照只有**官方 core**。但 core 是「语言自带」，
未必代表「同一个 mooncakes 生态里，别人写的 base64 有多快」。
`gmlewis/base64` 是 mooncakes 上**独立发布**的第三方实现（Go `encoding/base64` 的 MoonBit 移植），
它才是**同门竞争**的直接参照——故 2026-10-12 轮次把它编进 MoonBit harness（第 3 家、全表第 7 家）。

| 体积增量（本库 / gmlewis） | — | — | 5.23 KB / **17.98 KB** | — |

> **口径**：本轮（2026-10-15）数据；`<1` = 本库更快。体积为全尺寸单一值、与前三轮一致（非计时量）。

（`<1` = 本库更快；体积为全尺寸单一值。）

**四条读法**：

1. **本库在同门里领先一个身位**：往返快 **3.6–4.2×**、编码快 2.4–2.6×、解码快 3.7–4.0×。
   即：本文 §3.2 的「同平台赢」**不只对 core 成立**，对第三方 MoonBit 实现同样成立。
2. **gmlewis 与 core 几乎同速**（往返比值 3.7/3.9 @1K、4.2/4.3 @64K），

3. **它比本库胖 3.4×**（增量 17.98 KB vs 5.23 KB；core 仅 4.22 KB，本轮复测不变）：

   体积代价显著。**本库在同门里是「又小又快」的那一档**（体积亦优于 core 之外的全部对照）。
4. **归因不涉 SIMD**：它与本库同编进 harness 产物，实测合计 **0 条 SIMD 指令**（§3.4）——
   这个差距是**算法与外殼**的差距，不是向量指令的差距。

> **口径提醒**：三家的调用形态对齐到「端到端 encode/decode」（gmlewis 与 core 都没有
> 零分配内核段），故这一格与 §3.3 的内核段**不同层**，不可互推。

## 5. 根因：差距为什么这么大

### 5.1 同机拆解（本库内部，p50，ns/次）

用一次性的白盒探针**拆开本库自己的三个层次**（探针跑完即删，复跑见 §7.2）：
以下数字产自**首轮（2026-10-08，S12 之前）**——**占比**（51–72% / 16–26%）与尺寸关系**跨轮稳定**，
故本节**未随 §3/§4 切轮**（§3/§4 是外部对照表，本节是**本库内部拆解**，两者口径不同层）。
> ⚠️ **本轮提示**：S12 落地后，「外壳 · 编码物化」这一行的绝对值已**不再适用**
> （恰好容量把翻倍增长与出口再拷两笔账同时消掉，§10.7 给了改动前后的对照）。
> 但**占比的量级判断**（物化是编码主成本、解码物化次要）**仍成立**——
> 否则本轮不可能看到编码端到端 0.75–0.78× 的改善。

| n | 端到端 encode | `encode_slice`（含输出缓冲分配） | 差额 = 物化 (`StringBuilder`) | 空调用（仅引擎构造） |
|---:|---:|---:|---:|---:|
| 1024 | 5 318 | 2 591 | **2 727（51%）** | 274 |
| 8192 | 37 566 | 18 240 | **19 326（51%）** | 200 |
| 65536 | 523 976 | 145 381 | **378 596（72%）** | 193 |

| n | 端到端 decode | `decode_slice`（含输出缓冲分配） | 差额 = 物化 (`Bytes::from_array`) |
|---:|---:|---:|---:|
| 1024 | 3 220 | 2 396 | **824（26%）** |
| 8192 | 20 712 | 17 454 | **3 258（16%）** |
| 65536 | 162 222 | 137 076 | **25 146（16%）** |

**读法（这是本文的核心）**：

- **编码的物化是主成本**：`StringBuilder` 逐字符 `write_char` 占了端到端的 **51–72%**，
  且**随尺寸放大**。内核（`encode_slice`）反而只占 28–49%。
- **解码的物化次要**：`Bytes::from_array` 只占 16–26%，成本**主要在 `decode_slice`**。
  这解释了 §4.2 的第 2 条：解码不能靠省物化来救，编码可以。
- **引擎构造是常数项**：~200–274 ns/次，与尺寸无关——即
  [S6 §1–§2](../01-规格/S6-性能实测与M3裁决.md) 判「复用引擎收益仅 3.9%」的同一笔账，**不是大头**。

### 5.2 与 Rust 的距离：内核 vs 外壳

把 §3.3 的内核段放在这张图里（内核段 = 零分配 `*_slice`）：

| n | 内核 enc (moon/rust) | 端到端 enc (moon/rust) | 内核占比 |
|---:|---:|---:|---:|
| 1024 | 2.10× | 4.80× | 44% |
| 8192 | 1.80× | 5.00× | 36% |
| 65536 | 1.84× | 6.83× | 27% |
| 262144 | 1.90× | 9.02× | 21% |

**读法**：

- **内核只慢 ~1.8–2.1×**，端到端却慢 4.8–9.0×——差额**几乎全部**是外壳（物化 + 分配 + 引擎）。
- 内核占比**随尺寸下降**（44%→21%）：大尺寸下外壳物化的绝对成本线性增长，
  而内核的相对劣势是常数。
- **结论**：要缩小与 Rust 的差距，**主战场在外壳**——而 §3.4 已证明**不在 SIMD**
  （各方都是标量），也不在热循环（[S10](../01-规格/S10-去内循环落地与端到端对照.md) 已磨到 1.37×）。

### 5.3 平台税：跨平台那一档怎么理解

比 rust-base64 慢 5–9×、比 node Buffer 慢 2.3–5.6×，这部分**不全是实现问题**：

- **rust-base64 / node Buffer 没有 GC**：输入输出都是**线性内存**里的连续 `&[u8]`，
  编码输出可以**直接写进调用方缓冲**（`encode_slice`），不经过任何 GC 对象。
- **本库跑在 wasm-gc 的 GC 对象上**：`Bytes` / `FixedArray` 是 GC 数组，
  外壳每次 `encode` 都要「建引擎 → 建输出 `FixedArray` → 逐字符塞进 `StringBuilder` → 物化 `String`」。
  这几步在 Rust 侧根本不发生（`encode` 返回 `String` 也只是一次线性内存写入）。
- **可量化的部分**：§5.1 的物化差额（51–72%）正是「平台税里可优化的那一块」；
  剩下的「GC 对象访问 vs 线性内存访问」是**结构性**的，短期无解。
- **不含 SIMD**：§3.4 已证各方都是标量。**旧版把「+ SIMD」算进平台税是错的**，本版已更正。

> **这条决定了优化路线**：外壳物化可攻（§6），GC 对象访问不可攻（至少不在本库层面），
> **SIMD 是另一条独立的路（要手写 `@v128`）**，不在「缩小与 Rust 差距」这条线上。

### 8.1 框架自身能红（两种注入）

**环境**：AMD EPYC 9754 128-Core / Node v24.21.0 / MoonBit `0.1.20261012` / rustc 1.99.0。

### 10.7.1 一致性校验（仍全绿）

1. **同门两门变远**：core 3.4–4.5×、gmlewis 3.7–4.2×（第三轮 3.3–4.2×）。

### 10.7.3 同机隔离 A/B（本轮新增的第三类被测量）

上表只说明「本库比各家快了」，**不能说明「S12 这一行值多少」**——
它混着同机漂移。要答后一个问题，必须在**同一进程**里对「改动前产物 vs 改动后产物」交错计时
（复跑见 §7.1.1）。

**self 对照先行**：同一份 pre 产物加载两份实例，五出口 × 四尺寸的比值
**全部落在 0.98–1.01** ⇒ 交错本身无系统偏差，下面的 post/pre 可信。

**产物对账**（先证明两侧在算同一件事）：

| 判据 | 结果 |
|------|------|
| 13 尺寸编码串 / 往返校验和 | pre 与 post **逐位相同** |
| `encode_slice` / `decode_slice` **函数体**（解析 wasm code section） | **逐字节相同** |
| `verify_*` 出口输出 | 逐位相同 |

**端到端（post/pre，稳态三跑，去掉首轮冷启动）**：

| 方向 | n=1024 | n=8192 | n=65536 | n=262144 |
|------|-------:|-------:|--------:|---------:|
| **编码** | 0.96–1.01 | 0.96–1.01 | **0.75–0.78** | **0.75–0.78** |
| **解码** | 0.85–0.99 | 0.85–0.88 | **0.72–0.74** | **0.74–0.76** |
| 往返 | 0.86–1.03 | 0.86–0.87 | **0.70–0.78** | **0.74–0.79** |

**三条读法（必须一起引用）**：

1. **编码的收益真实、且随尺寸放大**：n≥64K 稳定 **0.75–0.78×**（越大越省）；
   小尺寸落在噪声内（容量差异被固定成本稀释）——这正是「引用数字必须带尺寸」的又一例。
2. **小尺寸的 A/B 比值不可单独引用**：n=1024 的三跑区间宽达 0.86–1.03，
   横跨 1.00。**只报 n≥64K 的四格**才不会把漂移说成收益。
3. **解码也变快了（0.72–0.79×），但这不是 S12 的语义目标**——见下。

### 10.7.4 一个必须写清的副作用：解码为何也变快

S12 只改了 `encode` 的物化容量，**没有碰 `decode` 一行**。但 A/B 显示
`bench_decode_only` / `bench_decode_slice` 也快了 **0.72–0.79×**。
把这件事随随便便归给 S12 会**高估**那一行的价值，故本节给出定位过程与结论。

**五步定位**（每一步只排一个解释）：

| 步 | 动作 | 结果 | 排除/确认 |
|:-:|------|------|-----------|
| ① | 对比两侧 `decode_slice` 的 wasm 函数体 | **逐字节相同** | 差异不在被测函数本身 |
| ② | 同进程只测 decode、交换加载顺序 | 比值不变（0.78× 稳定） | 不是「先加载者占便宜」 |
| ③ | pre 产物与自身第二实例交错 | 0.98–1.01 | 交错口径无偏 |
| ④ | pre 源码上**只改一行注释**重编译 | 产物与 pre **md5 相同**，比值 1.00 | 「重编译」本身不导致变化 |
| ⑤ | pre 源码上**只切 `size_hint` 一行**（`none` vs `exact`） | decode **0.77–0.80×** | 确认由这一行触发 |

**结论（产物层的直接证据）**：`size_hint` 那一行改变了整个编译单元的代码生成——
harness 产物里 MoonBit 运行时的大函数（wasm code section 中 29 KB 那个）
被重新生成，两处差异：某临时量槽位重编号，以及插入 `i32.const 2; local.get 7; i32.mul`
（正是 `2 * total` 的乘 2）。`decode` 路径**共享**这部分运行时代码，于是**连带变快**。

> **这条要这样引用**：
> **「S12 让编码端到端 0.75–0.78×」是它的语义目标，可归因给它。**
> **「解码也快了 ~0.78×」是同一行改动触发的编译单元重生成的副作用，不是 S12 的设计意图。**
> 二者合起来 = 本轮观察到的「改动后整体更快」。
> **不可把解码那 0.78× 算进 S12 的收益账**——它依赖编译器的内联/分配决策，
> 换工具链版本可能消失（本仓「工具链不钉死」是已知取舍，见 §10.6）。

> **这也是「同机隔离 A/B」必须进框架的理由**：只跑一份产物的 `bench.sh`
> **看**不到这层副作用；只看单次直测又会把它记成漂移。只有同进程双产物交错 + self 对照
> 能同时给出「有没有变化」与「变化该归因给谁」。

### 10.7.5 体积与 SIMD（本轮）· 复跑命令

- **体积**（增量口径，非计时量）：本库 **5232 B** / core **4220 B** / gmlewis **17984 B**
  ——与前三轮一致（S12 只改容量参数，不引入新代码）。**同门最胖的仍是 gmlewis（3.4×）。**
- **SIMD**：探针报 MoonBit harness **0 条** / rust-base64 **0 条** ⇒ 仍是「标量 vs 标量」。
  §3.4 的裁决（那一档差距与 SIMD 无关）**第四轮复跑成立**。

**复跑**：`bash scripts/setup-bench-runtimes.sh && bash scripts/bench.sh`（七家表）；
A/B 见 §7.1.1。

> **本轮对结论的影响汇总**：§1 的五句话**逐句仍成立**，其中第 1 句（同平台赢）**变强**，
> 第 2 句（跨平台差一档）**差距收窄**，第 4 句（与纯 JS 同档）**需改口径为「编码方向已落后」**。
> §6 归因表里「外壳 · 编码物化」一格从「✅ 可攻」改为「✅ 已攻下一部分」。
